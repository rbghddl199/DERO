# dero-api — Gradle project root

Real Spring Boot module. Every build/run command runs from this folder (command list:
`backend/CLAUDE.md`).

Evidence for every trap below — measurements, ticket numbers, failure narratives, discarded
alternatives — is in `docs/context/backend-runtime.md` §1 (local dev; ports · image-pipeline
sections still staged in `.claude/rules/backend/*.md`). Prod-DB tunnelling procedure is
`docs/context/deployment.md` §9. File-scoped rules auto-load from `.claude/rules/backend/`:
`gradle-build.md` (starter names · QueryDSL apt) · `spring-config.md` (profiles · actuator ·
metrics · OAuth) · `flyway-migration.md` (V1 frozen · migration tests) · `testing-runtime.md`
(test layering · health endpoint · daemon contention · ArchUnit store).

## Traps

- **`ddl-auto: validate` cannot see a sequence owned by `GENERATED BY DEFAULT AS IDENTITY`.**
  Hibernate reads `information_schema.sequences`, which excludes identity-owned sequences, so
  `@SequenceGenerator(sequenceName = "<table>_id_seq")` kills boot with
  `Schema-validation: missing sequence [brand_id_seq]` even though the sequence exists with that
  exact name and `INCREMENT BY`. **The symptom says "sequence missing" so you suspect DDL; the cause
  is the view being queried.** Explicit `CREATE SEQUENCE` and `BIGSERIAL` are visible.
- **Toolchain is 21, but the default `java` on PATH may be lower and that is not a failure** —
  Gradle detects the toolchain separately. On `JAVA_HOME is not set and no 'java' command could be
  found`, **do not conclude there is no JDK — check `~/.jdks/` first** and pass
  `JAVA_HOME=$HOME/.jdks/<jdk> ./gradlew ...`. Install a JDK only when truly absent.
- **Testcontainers cannot find Docker on WSL — set `DOCKER_HOST=unix:///var/run/docker.sock`
  explicitly.** The socket itself is fine; Testcontainers picks the Docker Desktop strategy first
  and NPEs before the unix-socket strategy is tried. Failures surface as
  `NoClassDefFoundError`/`ExceptionInInitializerError` and look like code bugs.
  - **If the env var alone does not work, kill the Gradle daemon first** (`./gradlew --stop`) — a
    daemon reuses the environment it first started with and never passes the new one to the test
    JVM. **Attach `JAVA_HOME` to `--stop` too**, or the wrapper dies looking for a JVM just to stop.
- **Local postgres/redis come from repo-root `compose.data.yaml`** (project `dero-data`; this
  folder's dev `compose.yaml` was deleted). From repo root:
  `docker compose -f compose.data.yaml up -d` — ports bind `127.0.0.1:5432` / `127.0.0.1:6379`.
  **`spring-boot-docker-compose` was removed**, so nothing starts containers for you and nothing
  injects connection details; without the `local` profile there is no datasource and boot dies.
  `bootRun` hardcodes the profile, but an IntelliJ Run Configuration needs `local` in Active
  profiles.
- **Local connection details are a pair — change one file and change the other**:
  `application-local.yaml` datasource/redis blocks and root `.env` `POSTGRES_*` dummies
  (`dero`/`derobe`/`dero_be`, never reused in deploy config — ADR-0010). Drift between them is what
  produces `Unable to determine Dialect without JDBC metadata`, and **that message does not prove
  the `local` profile is off** — it appears both when datasource properties are absent and when they
  exist but the connection fails, with no SQLException chain to tell you which. Read the container's
  real values with `docker exec dero-data-postgres-1 psql -U <role> -d <db> -c '\du'` and align the
  yaml to them.
- **`POSTGRES_*` only applies to an empty volume.** Changing `.env` credentials leaves the roles
  inside the existing `dero-data_postgres-data` volume untouched, and Postgres answers a *missing
  role* identically to a wrong password — so `password authentication failed for user "dero"` can
  mean the role was never created. Password-only mismatch: `ALTER USER ... WITH PASSWORD` through
  the trust socket. Role truly missing: `docker compose -f compose.data.yaml down -v` and back up
  (Flyway rebuilds the schema).
- **Pointing a local backend at a remote DB requires matching `app.storage.mode`, or the API
  returns 200 and every image/GLB 404s.** A prod DB's `asset_key`/`image_key` point at real S3
  objects, so `mode: local` presigns fine and every `GET` is `STORAGE_FILE_NOT_FOUND` — it surfaces
  only as "frontend preview images missing", so you suspect the frontend. Keep
  `application-local.yaml` at `${APP_STORAGE_MODE:local}` (team-shared file) and put
  `APP_STORAGE_MODE=s3` in your own `.env.local`.
- **Turn Flyway off before attaching to the prod DB — and turn it back on when you detach.**
  It runs on every local boot, invisibly, because a matching checksum is a no-op; over a tunnel the
  same run can **silently migrate the prod schema** (irreversible). Put `spring.flyway.enabled=false`
  in `.env.local` **together with the datasource lines, and comment both out together** — leaving it
  off against a local container means later migrations never apply and boot dies days later with
  `Schema validation: missing table [...]`, which sends you hunting through migrations and entities
  for a one-property cause. **The signal is that the log contains no Flyway line at all** (healthy
  boot prints `Current version of schema "public": N`). `.env.local` outranks
  `application-local.yaml`, so one line there wins over an empty yaml. Full procedure:
  `docs/context/deployment.md` §9, which also covers tunnel port choice and `host.docker.internal`.
- **Running `./gradlew test` with an ES tunnel open destroys the production index.** Every context
  runs `prepareIndex` on `ApplicationReadyEvent`, and a branch whose index definition changed will
  swap the prod `products` alias to an empty index and delete the old one — **with no error and no
  warning**, so it reads as a deploy accident. `application-test.yaml` pins
  `spring.elasticsearch.uris` to a closed port to block this; **`application-local.yaml` is not
  guarded, so `bootRun` is the same path.** Check with
  `lsof -nP -iTCP -sTCP:LISTEN | grep 9200`. Recovery is one
  `POST /api/v1/admin/search/reindex` (Postgres is canon, so no data is lost).
- **A tunnel round trip costs ~25ms, which alone breaks any per-keystroke endpoint.** When
  autocomplete feels slow, check for live tunnels before suspecting debounce, transactions or query
  design: `lsof -nP -iTCP -sTCP:ESTABLISHED | grep -E ':(55432|9200|6379)'`. A dead local data
  container (`docker ps -a` showing `Exited`) usually means a tunnel was left on and forgotten.
- **No Docker means no Postgres, so SQL/migration verification is impossible.** WSL: enable the
  distro in Docker Desktop > Settings > Resources > WSL Integration. macOS: the CLI exists but
  `docker info` cannot reach the socket — start Docker Desktop itself.
- Container image pins, PG 18's changed volume path and the major-version support window are
  canonical in root `compose.data.yaml` and `docs/context/deployment.md`.

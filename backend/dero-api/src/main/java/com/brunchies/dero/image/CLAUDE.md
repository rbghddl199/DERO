# image — AI imagery + upload pipeline

Root is `GeneratedImage`. Feed-entry gate, Redis queue, stub worker live here.
Design: `docs/adr/0015-placement-upload-async-pipeline.md` · stub decision `docs/CONTEXT.md` D27-보 ·
API surface `docs/context/api-spec.md` §4 · trap evidence `docs/context/backend-runtime.md` §3.

## Traps

- **`PUT`/`DELETE /placements/{id}/feed-entry` lives here, not in `placement`.** Gate ③ is the daily image quota, counted from `generated_image`, and the dependency is one-way `image → placement` (`LayerDependencyTest.placement는_위를_모른다`), so `placement` cannot see that table. URL = resource layer, package = dependency layer; the `backend-api SPEC` module table saying otherwise is a sketch and the machine rule wins.
- **Editing tags after publishing is `PUT .../feed-entry/tags`, never a second `PUT .../feed-entry`.** That endpoint is the retry button, so re-calling it sends a `PUBLIC` placement back to `PENDING`, regenerates the image and charges daily quota — for a one-word tag edit. `FeedEntryService.replaceTags` skips every gate, swaps only the junction rows, then republishes `PlacementChangedEvent` so the search document follows. **Its request body inverts `FeedEntryRequest`'s `null` rule** (`@NotNull`, empty = clear all): with no retry call here, "unchanged" has no meaning to express.
- **Gate order is the contract: ①judge ②screenshot ③quota ④transition+enqueue.** Judging late burns generation cost plus quota, then reverses an "uploaded" message minutes later. **Only `INCOMPATIBLE` blocks** — `CONDITIONAL` means catalog spec is unregistered, and our missing data must not block a user's publish.
- **Read the placement under judgment via `PlacementRepository.findForJudgmentById`.** `PlacementJudge` branches on `PlacedItem.product` with `instanceof`; **a LAZY proxy makes every branch silently false and judgment rows vanish**. Symptom is not an exception but **"zero violations"**, misread as a pass. The save path is safe only because merge just set concrete types, not because `instanceof` is safe.
- **Enqueue in `afterCommit`.** Inside the transaction the worker picks up a still-`PRIVATE` placement and drops it — job lost, user waits forever. Inverted in tests: a `@Transactional` MockMvc test never commits, so nothing enters the queue and happy-path assertions go false (use `Propagation.NOT_SUPPORTED` + truncate isolation).
- **Idempotency belongs on the consume side, not the request side.** The guard in `publish()` (no-op unless `PENDING`) blocks three accidents: ①a late job re-publishing a placement the user took down via `DELETE .../feed-entry` ②duplicate publish writing more image rows and charging quota twice ③two overlapping publishes where the primary-row partial unique kills the later one, leaving good rows but a `FAILED` placement. **Do not guard in `requestFeedEntry`** — enqueue is `afterCommit`, so a Redis drop in that window leaves DB `PENDING` with an empty queue, and blocking re-enqueue makes that placement unrecoverable by any user action.
  - **The guard runs twice and both are load-bearing.** `publish` splits into `prepare` (short tx) → generation **outside any transaction** → `attach` (short tx), so the user has minutes to withdraw while the image is being made; only `attach`'s re-check closes that window, and when it fires the finished image is discarded on purpose (an explicit cancel must win, and unwritten rows charge no quota).
- **The external generation call must stay outside the transaction, and `@Transactional(propagation = NEVER)` on `publish` is what keeps it there.** Delete it and the class-level `readOnly = true` revives: both `TransactionTemplate` blocks join it under REQUIRED, so ①it is one long transaction again (a pooled connection and `demotePrimaries`' row locks held for the whole GMS `read-timeout`) and ②Hibernate's read-only `FlushMode.MANUAL` makes the **INSERTs silently vanish**. **No functional test catches the first half**, so `GeneratedImagePublishTransactionTest` asserts `isActualTransactionActive()` at the port call. Rationale: ADR-0025 decision 3.
  - **`NEVER`, not `NOT_SUPPORTED`** — `NOT_SUPPORTED` merely *suspends* a caller's transaction, and a suspended transaction still owns its connection, so the long hold comes back invisibly the day a transactional caller appears (`.claude/rules/backend/upload-image-pipeline.md`).
- **Make queue ops fail toward duplication, never loss** — `requeueStale` pushes back to the waiting list **first** and removes from processing after; reverse the order and a crash between the two commands loses the job and the placement stays `PENDING` forever. Same reason `complete` clears the claim timestamp first. **Duplicates are absorbed by the consume-side guard above; loss is absorbed by nobody.**
- **`complete`/`requeueStale` need the original payload string** — Redis `LREM` deletes by value, so `claim` returns `ClaimedJob(payload, job)`. Re-serializing to delete leaves a ghost in the processing list on any one-character drift (field order, time format), and the sweeper resurrects it forever.
- **`GeneratedImage.createPrimary` allows one row per placement** — partial unique `uq_generated_image_placement_id ... WHERE is_primary` enforces it in DB. Re-upload = **one transaction: `demotePrimaries` first, then the new primary**; that bulk UPDATE clears the persistence context, so **re-read the placement afterwards** or the following `markPublished()` misses dirty checking.
- **`IMAGES_PER_UPLOAD` is the one source of truth for how many images an upload makes** (1 since D29/ADR-0025, was 3). The port request's `count`, the contract check in `publish`, the detail-list `Limit` and the quota pre-charge all read it. **Never write the number anywhere else**, and don't "simplify away" the port's `count`, `GmsImageGeneration`'s loop or the frontend's 2-column grid just because they now run once — keeping them is what makes going back to N a one-line change. The left/right three-quarter prompts in `DeskScenePrompt` **were** deleted (a stale angle instruction would corrupt the single image); restore those if N returns.
- **Daily quota counts `generated_image` rows, so stub consumption really charges.** D27-보 ("stub does not charge quota") is **not literally implementable** — no column distinguishes stub rows and the schema doc is frozen. The single decision point is `FeedEntryService.requireWithinDailyQuota`, so a billing or marker column would change only that. Tuning: `app.image.daily-quota`. **Awaiting 박동규 decision.**
- **"How images are made" sits behind `infra/ImageGenerationPort`.** `GeneratedImageService.publish` only **receives** keys and writes rows; the stub↔GMS switch is `app.image.generation.mode` alone. **Changing mode must never require editing this package.**
  - `publish` reads prompt material via `findForJudgmentById`, not `findByIdAndDeletedAtIsNull` — the latter does not fetch items, costing one query per product.
  - Domain values are passed **flattened to strings** (`ImageGenerationRequest`) — `infra` cannot import `Placement`/`DeskTexture`/`FrameType` (`LayerDependencyTest.infra는_도메인을_모른다`).
- **The stub writes the screenshot key straight into the row** — no file copy, because the domain knows only `PresignPort` and S3 mode has no copy op. In stub mode the concept image *is* the screenshot file.
- **Worker flag off = the bean does not exist** (`@ConditionalOnProperty`) — "no loop", not "thread up doing nothing". **`application-prod.yaml` turns it on; off means every upload stalls in `PENDING`.**
- **Redis also holds refresh tokens** (ADR-0005), so `ImagePublishQueue` touches only its own 3 keys — **no global commands like `FLUSHDB`** — and its blocking `BLMOVE` uses a dedicated Lettuce connection rather than pinning the shared one and stalling token lookups.
- **No presigned URL in queue messages** — presign has a TTL, queue wait has no upper bound, so a late worker gets an expired URL. The message carries only `{placementId, requestedAt}` and presign happens when the worker claims. ADR-0015 decision 5's richer shape (`sourceImageUrl` + `uploadTargets[3]`) **will never be built**: the local-notebook python worker was scrapped (D29, ADR-0025) and the generator now lives inside the WAS.
- Redis integration tests extend `AbstractRedisIntegrationTest` — see `.claude/rules/backend/testing-runtime.md` §1.

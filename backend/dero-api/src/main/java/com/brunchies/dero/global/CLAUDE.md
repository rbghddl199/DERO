# global — global layer

Only things that intercept every request live here (handling one request → domain package). Nobody knows `global`.

## Rules

- **`ErrorCode` interface here, code enums in each domain package** (`product/ProductErrorCode` etc.). No single giant enum — two people appending to the end of one file means constant merge conflicts, and `global` would learn every domain's vocabulary (ADR-0008 decision 3).
- **One exception type: `BusinessException`.** Do not create per-domain exception classes.
- **Never hand-build `ProblemDetail`; pass through `ProblemDetails.of`** — that is what guarantees the Korean `detail` and the `code` extension field. Otherwise Spring's default English text reaches the user's screen.
- **Override framework default `detail` only where it breaks our contract.** Test: does English text / an internal type / a path reach the user's screen? Example: type mismatch's `"Failed to convert 'id' with value: 'abc'"` was replaced via a `handleTypeMismatch` override with Korean + `code` + `errors`. Do not put the expected type name in `reason` (keep it at "숫자 형식이어야 합니다." level); keep the original message in logs only. **Conversely, leave 404/405/415 alone** — default behavior already satisfies the contract, and duplicating it only creates drift.
- **The 4 `SecurityErrorCode` values live in `security/`, not the `auth` domain** — they are the intercepting layer's vocabulary, not domain vocabulary, and putting them in `auth` would make `global` reference a domain, breaking ADR-0007 decision 7's dependency direction. This is a **deliberate departure** from ADR-0008 decision 3's "only interfaces in global".
- **`SecurityConfig` wires `oauth2ResourceServer` + `oauth2Login`** (2026-07-29, Kakao/Google login) — the 401/403 handlers are registered inside `oauth2ResourceServer(...)`, not `exceptionHandling` (ADR-0008 decision 4). `JwtDecoder` (`JwtConfig`) carries a `typ=access` claim validator so a refresh token (same signing secret, 14-day life) cannot be replayed as an access token — remove that validator and a leaked refresh token walks straight into protected APIs.
- **`BaseEntity`'s `OffsetDateTime` requires a custom `DateTimeProvider`** — Spring Data's default provider yields `LocalDateTime` and there is no `LocalDateTime → OffsetDateTime` converter, so saves die with `Cannot convert unsupported date type`. Do not delete `JpaAuditingConfig.auditingDateTimeProvider`. Whether audit fields actually get filled is still unverified (no schema yet, since DERO-196).
- **`JpaAuditingConfig.auditorAware` trusts `sub` only for `JwtAuthenticationToken`** (implemented 2026-07-29). `OAuth2AuthenticationToken` (mid social-login exchange — exactly the context `OAuth2LoginSuccessHandler` lives in) returns Kakao's own member number / Google's `sub` from `getName()`; both look numeric so `Long.valueOf` passes without throwing — used untyped, a signup insert's `created_by` would silently hold someone else's provider member number. Why the two columns have neither FK nor index: `docs/context/erd.md` global rules, "감사 컬럼" section.
- **Do not remove `@EnableJpaAuditing(modifyOnCreate = false)`** (2026-07-28, DERO-217). The default is `true`, so `AuditingHandler.markCreated()` stamps `@CreatedDate` and `@LastModifiedDate` **together** — a plain INSERT fills `updated_at`, falsifying the rule erd.md, GLOSSARY and `BaseEntity` nail down: "`updated_at` on junction/toggle/history tables is NULL forever" (9 tables incl. `follow`, `user_consent`). `ddl-auto: validate` passes (column is nullable), so **boot is fine and only the data quietly diverges** — caught only by integration assertions (`UserPersistenceTest`, `ConsentPersistenceTest`). Attribute existence confirmed in `spring-data-jpa-4.1.0` source (`EnableJpaAuditing.modifyOnCreate` → `AuditingHandlerSupport.setModifyOnCreation`); the official auditing docs do not list it.
- **Do not add `spring.mvc.problemdetails.enabled`** — Boot 4.1 also defaults it false, and the bean it creates is `@ConditionalOnMissingBean(ResponseEntityExceptionHandler.class)`, so it backs off anyway once `GlobalExceptionHandler` exists. 404/405/415 and static-resource 404 all go through our advice (test-confirmed). Note: Spring omits `type` from the body when it is `about:blank` — differs from ADR-0008's example JSON.
- **`@WebMvcTest` attaches the default security chain even without our `SecurityConfig`** — tests that only inspect exception handlers need `@AutoConfigureMockMvc(addFilters = false)` (otherwise everything 401s, POST 403s on CSRF). Boot 4's slice annotation package is `org.springframework.boot.webmvc.test.autoconfigure`.
- **Without `.cors(...)` in `SecurityConfig`, every fetch from a frontend client component is silently blocked in the browser** (2026-07-29, found during DERO-177 craft integration). Server logs, Postman and curl all return 200, so it is easily misjudged as "backend is fine" — the failure appears only in the browser console (CORS error or `Failed to fetch`). Next.js Server Component fetches (SSR, server-to-server) are unaffected, so the symptom splits confusingly into "GET list works but POST create doesn't". Fix: the `corsConfigurationSource` bean + `app.cors.allowed-origins` (local `http://localhost:3000`, safe default empty string) — when adding a new client-side fetch, check that config already allows its origin.
- **`new NimbusJwtEncoder(JWKSource)` (the generic constructor) defaults its signing header to RS256** — wrapping an HMAC `SecretKey` in `ImmutableSecret` and passing it there compiles and boots fine, then every `encode()` dies with `JwtEncodingException: Failed to select a JWK signing key` (it looks for an RSA/EC JWK). Controller and security tests missed it because real app code only encodes via `JwtIssuer` and that path was always stubbed with `@MockitoBean`; it surfaced only when `JwtIssuerTest` (a unit test that really issues) was first written (2026-07-29). `JwtConfig.jwtEncoder` must use `NimbusJwtEncoder.withSecretKey(secretKey).build()` (HS256 derived from the key) — the symmetric counterpart of `JwtDecoder`'s `NimbusJwtDecoder.withSecretKey(...)`, easy to miss because only the encoder side has a different constructor shape.
- **Flipping the last base64url character does not tamper a JWT** (fixed 2026-08-02, DERO-346, !268 — `SecurityProblemDetailTest.변조된_토큰은_거절` used to fail ~6–17% of runs). A base64url final char carries 4 valid + 2 ignored bits, so 4 different chars decode to the same byte (HS256 signature 32 bytes → 43 chars): if the signature ends in `A`/`B`/`C`/`D`, the "tampered" token is byte-identical, stays valid, passes the filter and returns 404 instead of 401. Signatures vary per run (`Instant.now()` claims), so it **does not reproduce** and shows up during unrelated work. Flip a **middle signature char** instead (`lastIndexOf('.') + 5`) — all 6 bits are signature bits, so invalidation is guaranteed.

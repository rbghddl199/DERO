# KNOWN_LIMITATIONS

`imagine_img` 를 실제로 만들고 돌려본 뒤 남은 한계. 추측이 아니라 코드와 실행에서 확인한 것만 적는다.

---

## 0. 출력 크기는 입력 크기를 따른다 (2026-07-31 정책 변경)

이전에는 생성 1152x1024 / 최종 1328x1184 고정이었고 비율이 다른 입력을 거부했다.
사용자 지시로 `SIZE_MODE=follow_input` 이 기본이 되어 **출력 크기 = 입력 크기**다.

남은 제약:

- **생성 크기는 입력 크기와 다르다.** SDXL 이 약 1M 픽셀 부근에서 학습됐고 8GB 에서는 픽셀 수가
  곧 OOM 이라, 비율만 입력에 맞추고 픽셀 수는 `GENERATION_PIXEL_BUDGET`(기본 1152x1024) 안에 넣는다.
  그 뒤 Lanczos 로 입력 크기까지 확대한다 — **확대는 디테일을 만들지 않는다.**
- 비율을 정확히 맞추려면 64의 배수 조합이 필요해서, 비율에 따라 예산을 크게 남기는 경우가 있다.
  예: 16:9 입력은 1024x576(0.59M px)이 되어 1920x1080 까지 1.88배 확대된다. 확대 배율이 1.6배를
  넘으면 응답 경고로 알린다. 이때는 캡처를 생성 크기에 가깝게 하거나 예산을 올려야 한다.
- 실측 예: 1125x1449 입력 → 생성 896x1152(SDXL 표준 세로 버킷, 비율 오차 0.18%) → 출력 1125x1449.
- `SIZE_MODE=fixed` 로 두면 구 규격(1328x1184)과 비율 거부가 그대로 돌아온다.

## 1. strength 가 실제 denoise step 수를 줄인다 — steps 를 9로 둔 이유

diffusers 의 img2img 는 `int(num_inference_steps × strength)` 만큼만 돈다
(`pipeline_stable_diffusion_xl_img2img.py:650`).

`num_inference_steps=4` 였다면 정책 값 0.25/0.35/0.45 가 **모두 1 step** 이 되어
세 결과가 픽셀 단위로 완전히 동일해진다. 실측으로 확인했다(MAE 0.0000, maxdiff 0).
즉 §5·§17 이 요구한 세 값 비교가 성립하지 않는다.

그래서 8-step checkpoint + `steps=9` 를 쓴다.

| preset | strength | 실제 step | 실측 inference |
|---|---|---|---|
| PRESERVE | 0.25 | 2 | 7.9초 |
| BALANCED | 0.35 | 3 | 8.5초 |
| REALISTIC | 0.45 | 4 | 8.9초 |

남은 제약:

- `steps=9` 는 8-step checkpoint 의 설계점에서 1 만큼 벗어난 값이다. `steps=8` 로 두면
  0.25 와 0.35 가 둘 다 2 step 이 되어 다시 구별되지 않는다.
- 세 값의 결과 차이는 여전히 작다 (MAE 0.43 ~ 1.00). "구조 보존 / 균형 / 실사화 증가" 라는
  §5 의 의미 구분이 육안으로 뚜렷하게 갈리지는 않는다.
- `COMPENSATE_STEPS_FOR_STRENGTH=true` (기본 OFF) 를 켜면 실제 step 이 요청 step 과 같아지지만
  distilled 모델의 학습 조건에서 크게 벗어난다(0.25 → 36 step). 품질 보장이 없다.

## 1-1. 조명 상태는 **입력 캡처에 구워져 있어야** 반영된다 (실측, 2026-07-31 갱신)

이전 판에서 "낮/밤·조명이 결과에 반영되지 않는다"고 적었다. 그 측정은 **조명이 구워지지 않은
평면 fixture** 에 프롬프트만으로 낮/밤을 지시한 경우였다. 조명이 구워진 입력으로 다시 재니
결론이 뒤집혔다.

조명이 구워진 fixture 4종, 같은 seed, strength 0.35:

| 입력 | 입력 평균 밝기 | 출력 평균 밝기 |
|---|---|---|
| DAY / 조명 ON | 196.3 | 195.3 |
| DAY / 조명 OFF | 177.2 | 176.1 |
| NIGHT / 조명 ON | 115.1 | 115.1 |
| NIGHT / 조명 OFF | 55.4 | 56.7 |

출력 간 차이가 입력 간 차이와 거의 같다 — 즉 조명 상태가 그대로 유지된다.

```text
DAY/ON vs NIGHT/OFF   출력 MAE 139.0   (입력 MAE 141.0)
NIGHT/ON vs NIGHT/OFF 출력 MAE  58.8   (입력 MAE  59.7)
DAY/ON vs DAY/OFF     출력 MAE  19.5   (입력 MAE  19.1)
```

반면 조명이 구워지지 않은 평면 입력에 프롬프트로만 지시하면 출력 MAE 가 **0.20**(육안 구별 불가)이다.

**따라서 제약은 이것이다: 시뮬레이터가 조명을 적용한 화면을 캡처해서 보내야 한다.**
프롬프트는 조명을 새로 만들어내지 못하고, 낮은 strength 는 입력에 있는 조명을 보존하는 역할만 한다.
새 지시문 §8 의 마지막 문장이 정확히 이것을 요구하고 있었다.

부수적으로 확인된 사실: step 수를 올려도(2→4) 프롬프트의 조명 반응은 전혀 개선되지 않았고,
strength 를 올리면(0.5→0.75) 10배 커졌다. 프롬프트가 결과를 바꿀 여지는 strength 가 정한다.
단 strength 0.75 에서는 제품이 다른 물건으로 교체되는 것을 관측했다(머그컵 → 책 더미).
현재 정책의 상한 0.45 는 그 위험을 피하는 쪽을 택한 값이다.

## 2. 기본 프로필에서 네거티브 프롬프트가 무효다

`guidance_scale=0` 이면 `do_classifier_free_guidance` 가 False 라(`...img2img.py:951`) CFG 가 꺼지고
네거티브 프롬프트는 계산에 들어가지 않는다.

새 지시문은 §2 에서 `guidance_scale=0` 을 고정하고 §10 에서 네거티브 프롬프트 2종 프로필을
요구한다 — 이 둘은 함께 성립하지 않는다. 현재 처리:

- `sdxl_lightning` 프로필: 네거티브를 아예 만들지 않고 `negativePromptEffective: false` +
  경고를 응답에 남긴다. **§10 의 CGI·플라스틱·중복 객체 억제 목표는 이 프로필에서 달성되지 않는다.**
- CFG 가 켜진 프로필(`sdxl_photoreal`) 또는 `GUIDANCE_SCALE>1` 을 주면 실제로 작동한다.
  대가는 생성 시간 약 2배(UNet 호출 2배)와 Lightning 권장 조건 이탈이다.
- `full` 프로필(실측 128 토큰)은 CFG 를 켜도 77 토큰에서 잘린다. 앞쪽부터 지키고
  버린 항목을 `warnings` 에 남긴다. `compact`(44 토큰)는 잘리지 않는다.

즉 기본 설정에서 "이상한 제품 추가"를 막는 수단은 프롬프트 앞부분의 보존 지시문과
낮은 strength 뿐이다.

## 2-1. img2img 로는 렌더를 사진으로 바꿀 수 없다 (실측으로 확정)

실제 시뮬레이터 렌더(1125x1449)로 두 모델을 비교한 결과다. 지표는 국소 대비(laplacianVar,
입력 46.50 이 기준선이며 낮을수록 모델이 디테일을 지운 것이다).

```text
sdxl_lightning        31.77   (입력 대비 -32%, 손그림처럼 뭉개진다)
sdxl_photoreal 0.35   39.26   (Lightning 대비 +24%)
sdxl_photoreal 0.45   38.04   (0.35 과 사실상 동일)
```

- **모델 교체는 효과가 있다.** RealVisXL 이 Lightning 의 디테일 손실을 절반으로 줄인다.
- **strength 를 상한(0.45)까지 올려도 더 나아지지 않는다.** 0.35 와 0.45 가 같다.
- 육안으로도 결과는 "깔끔하게 정리된 3D 렌더"이고 **사진이 아니다.** 벽은 평면이고
  사진 특유의 노이즈·피사계심도가 없다.

즉 §1 의 "AI 일러스트가 아닌 실제 사진처럼" 은 **현재 구조(img2img + strength <= 0.45)로는
달성할 수 없다.** low strength 는 입력의 평면 셰이딩과 조명을 보존하는 방향으로 작동하기 때문이다.

**추가 확인(2026-07-31)**: strength 를 0.9 까지 올리면 모델은 실제로 사진급 재질을 만든다
(국소 대비 99.5 → 194.3, 나뭇결·의자·화분·바닥까지). 그러나 **제품이 전부 교체된다**
(모니터 → iMac, 보라 키보드 → 애플 키보드, 텀블러·머그 소멸). 즉 재질 실사화와 제품 보존이
strength 하나의 축에서 배타적이다. 0.6/0.75 는 개선도 없이 뭉개지기만 한다.

그리고 목표 사진과의 격차는 **대부분 실사화가 아니라 씬 구성 차이**다 —
평탄 영역 87% vs 47~60%, 채도 5% vs 34~44%. 자세한 분해는
[docs/QUALITY_GAP_ANALYSIS.md](docs/QUALITY_GAP_ANALYSIS.md) 를 보라.

## 3. 구조 보존은 프롬프트로만 유도한다 — 강제 수단이 없다

ControlNet, IP-Adapter, depth/edge 조건이 POC 범위에서 빠져 있다.
따라서 다음은 **막을 수 없고, 사람이 눈으로 확인해야 한다**.

- 모니터 개수가 바뀌는 것
- 제품이 사라지거나 추가되는 것
- 키캡·포트·로고가 그럴듯한 가짜로 바뀌는 것

품질 평가 항목(설계서 §17) 11·12번이 여기에 해당한다.

## 4. 입력 캡처는 1장만 실물로 확인했다

실제 시뮬레이터 렌더 **1장**(`inputs/image.png`, 1125×1449)으로 검증했다.
`SIZE_MODE=follow_input` 이후 비율 때문에 거부되는 문제는 없어졌다(0절 참고).

남은 한계:

- 실물 검증 표본이 1장이다. 다른 카메라 각도·제품 구성·조명 상태에서의 동작은 미확인이다.
  특히 **조명 4조합을 실제 렌더로는 측정하지 못했다** — 받은 캡처가 한 가지 조명 상태뿐이다.
  조명 반영은 합성 fixture 4종으로만 확인했다(1-1절).
- 회귀 테스트 fixture(`tests/fixtures/desk_capture*.png`)는 실제 캡처가 아니라
  `scripts/make_fixture_capture.py` 가 그린 도형 이미지다. 실제 렌더보다 단순하므로
  품질 판단의 근거로는 약하다. 지표로도 확인된다 — 합성 fixture 결과의 국소 대비는 20.5,
  실제 렌더 결과는 31.8~39.8 이다.

## 5. 4bit 양자화는 이 경로에서 지원되지 않는다

diffusers 의 bnb 양자화는 `from_pretrained(quantization_config=...)` 지점에서만 들어간다.
이 POC 의 기본 경로는 Lightning full checkpoint 의 `state_dict` 를 직접 주입하므로
그 지점이 없다. 그래서 `QUANTIZATION_MODE=bnb_nf4` 는 **`QUANTIZATION_NOT_SUPPORTED` 로
즉시 실패**한다 (fp16 으로 조용히 대체하지 않는다).
`torchao_int8` 은 코드 경로가 있지만 `torchao` 미설치 상태이며 실측하지 않았다.
설계서 §9.5 의 검증 매트릭스 중 C~F 는 **미검증**이다.

## 6. LoRA 는 인터페이스만 있다

DERO 스타일 LoRA 파일이 존재하지 않아 실제 로드·품질 비교를 하지 못했다.
구현·검증한 것은 여기까지다.

- 기본 OFF
- 경로 없음/파일 없음/다른 계열(SDXL 아님) → `LORA_LOAD_FAILED` 로 기동 실패
- scale 설정과 unload (fuse 상태에서는 거부)

계열 판정은 safetensors 키에 `text_encoder_2` / `add_embedding` 류가 있는지로 한다.
**이 판정은 "SDXL 계열인가"만 본다.** 일반 SDXL Base 에 학습된 LoRA 가
distilled Lightning UNet 에서 같은 품질을 내는지는 별개 문제이며 검증되지 않았다.

## 7. fp16 VAE 오버플로 가능성

SDXL Base 의 VAE config 는 `force_upcast=true` 라 디코드 시 fp32 로 올라가고,
`enable_vae_tiling()` 이 1152×1024 디코드를 8GB 안에 넣는다.
그래도 fp16 파이프라인에서 VAE 오버플로로 검은 이미지가 나오는 사례가 알려져 있다.
현재는 **검은 이미지를 감지해 `INFERENCE_FAILED` 로 알린다**(조용히 저장하지 않는다).
재현되면 `madebyollin/sdxl-vae-fp16-fix` 로 바꾸는 것이 다음 수단이며 POC 범위 밖이다.

## 8. 동시 처리가 1개다 — 대기열이 없다

두 번째 요청은 기다리지 않고 즉시 `409 JOB_ALREADY_RUNNING` 이다.
여러 사용자를 붙이려면 이 Worker 앞에 큐를 두어야 한다. POC 에는 없다.

## 8-1. 프롬프트가 CLIP 77 토큰 안에 들어가야 한다

설계서 §10 의 예시 프롬프트는 실측 101 토큰이고, 초과분은 조용히 잘린다.
지금은 문장을 압축하고 우선순위를 매겨 **보존 지시 3문장은 항상 남기고** 낮은 우선순위부터 버린다.
그래서 다음이 실제로 일어난다.

- `productSummary` 가 길면 `moodTags` 나 "High detail product photography." 가 버려진다.
- 무엇이 버려졌는지는 응답의 `warnings` 와 metadata 에 남지만, **버려진 정보는 반영되지 않는다.**

제품 목록을 길게 넣을수록 프롬프트에서 밀려나는 항목이 늘어난다.
77 토큰을 넘겨 쓰려면 프롬프트 임베딩을 직접 이어붙이는 방식(compel 등)이 필요하고 POC 범위 밖이다.

## 8-2. fp32 로 조용히 올라가면 오류 없이 45배 느려진다

diffusers 0.39 의 `from_pipe()` 는 `torch_dtype` 을 다시 넘기지 않으면 전체를 fp32 로 캐스팅한다.
8GB 카드에서 fp32 SDXL UNet(9.56 GiB)은 OOM 을 내지 않는다 — WDDM 이 공유 시스템 메모리로
밀어내기 때문에 **조용히 130초/장**이 된다.

지금은 기동 시 `_assert_component_dtypes()` 가 unet/vae/text_encoder 2개의 dtype 을 검사해
fp16 이 아니면 `MODEL_LOAD_FAILED` 로 실패한다. 다만 **이 검사는 파이프라인 조립 직후 1회만** 한다.
런타임에 누군가 `pipe.to(torch.float32)` 를 호출하면 잡지 못한다.

## 9. 성능 수치의 범위

`BENCHMARK_RESULTS.md` 의 값은 **한 대의 RTX 4070 Laptop 8GB, WDDM, 모델 CPU offload** 조건이다.

- 실측 `nvidiaSmiVramMb` 최대 **7589 MB / 8188 MB** — 여유가 약 600 MB 뿐이다.
  브라우저 하드웨어 가속 등 다른 GPU 앱이 붙으면 그 여유가 사라지고 공유 메모리로 밀려나
  **오류 없이 수십 배 느려진다.** 벤치마크를 다시 잴 때는 다른 GPU 앱을 닫아야 한다.
- `peakVramMb`(torch 할당, 5356 MB)와 `nvidiaSmiVramMb`(프로세스 전체, 7589 MB)는 다른 값이다.
  8GB 여유 판단의 기준은 후자다. 전자만 보면 2.8 GB 를 잘못 여유로 계산한다.
- 첫 요청은 warm-up 이후에도 캐시 효과가 있어 이후 요청보다 느릴 수 있다.
- warm-up 은 512×512 로 한다(설계서 §15). 이것은 1152×1024 경로를 예열하지 않는다.
  실측에서는 그래도 첫 회와 이후 회차의 차이가 없었지만(8117 ms vs median 8165 ms),
  다른 환경에서는 첫 요청만 느릴 수 있다.

## 10. 재현성의 범위

`GENERATOR_DEVICE=cpu` 기본값으로 같은 seed·같은 입력이면 같은 결과가 나온다(GPU 테스트로 확인).

# 시뮬레이터 캡처 스펙

`imagine_img` 가 사진 품질 결과를 내려면 **캡처가 무엇을 담고 있어야 하는지**.

2026-08-01 결정: 제품 정체성·조명·배치는 **시뮬레이터가 3D 단계에서 해결**하고,
imagine_img 는 재질과 조명을 사진처럼 바꾸는 일만 한다.
2D 제품컷 합성과 조명 프리셋 근사는 이 결정으로 폐기했다(아래 6절).

아래 항목은 전부 이 저장소에서 **실측한 근거**가 있다. 근거 없는 요구는 넣지 않았다.

> 구현 코드는 [simulator/captureForAI.ts](simulator/captureForAI.ts) 에 있다.
> 이 문서의 1절 요구사항을 그대로 코드로 옮긴 것이고, 사용법은
> [simulator/README.md](simulator/README.md) 를 본다.
>
> **화면을 캡처하지 말 것.** 같은 씬을 실사화 전용 설정으로 다시 렌더한다.
> 화면 캡처는 DOM 오버레이(툴바·성능 패널·가이드선)를 함께 담고, AI 가 그것을
> 물체로 해석한다 (실측 2026-08-01: WEB VITALS 패널 → 책상 밑 검은 명패).

---

## 1. 반드시 지켜야 하는 것

### 1.1 실제 제품 GLB 를 배치해서 렌더한다

프록시 박스로 렌더하고 나중에 AI 가 제품을 만들어 넣게 하면 안 된다.

- strength 를 올려 재질을 사진처럼 만들면 **제품이 다른 물건으로 교체된다**
  (실측: 모니터 → iMac, 보라 키보드 → 애플 키보드, 텀블러·머그 소멸)
- ControlNet 으로 구조를 고정하면 교체는 막히지만, 고정되는 건 **프록시의 형상**이다
- 제품컷(2D 이미지)을 붙이는 방식은 **원근이 원리적으로 맞지 않는다**.
  3/4 각도로 찍힌 제품 사진을 정면 씬에 넣을 수 없다 — 보이지 않던 면이 필요하기 때문이다

→ **제품의 정체성은 3D 가 정하고, AI 는 그 위에 재질·조명만 입힌다.**

### 1.2 조명 상태를 렌더에 구워서 준다

프롬프트로 낮/밤·조명을 바꿀 수 없다. 여러 조건에서 반복 측정했다.

| 입력 | 프롬프트 | 출력 평균 밝기 |
|---|---|---|
| 밝은 캡처 (193.6) | "nighttime, room lights off", strength 0.75 | 186.4 (거의 그대로) |
| 밝은 캡처 (193.6) | 같은 프롬프트, strength 0.90 | 173.0 (여전히 밝은 방) |
| 어두운 캡처 (67.1) | 같은 프롬프트, strength 0.75 | **62.1** (제대로 어두움) |

조명이 구워진 캡처를 넣으면 출력 밝기가 입력을 그대로 따라간다(오차 1~2).
조명이 없는 캡처에 프롬프트로만 지시하면 결과 차이가 MAE 0.20/255 — 육안 구별 불가다.

→ **요청하는 조명 상태(방 불 ON/OFF, 낮/밤)로 렌더해서 보낸다.**
사용자가 생성 페이지에서 고른 조건 하나만 만들면 된다. 조건을 바꾸면 다시 렌더한다.

### 1.3 발광 표면을 낮춘다 (실제 조명은 그대로)

`product_emitter` 가 붙은 제품 — RGB 케이스·조명·선반 언더라이트·벽 스트립 — 은 발광 재질이
표면을 흰색으로 클리핑해서 **형태가 사라진다.** 그러면 모델이 붙잡을 것이 없어 그 자리를
매번 다르게 채운다.

```text
실측 (2026-08-02, RGB 케이스가 붙은 실제 배치)
  같은 케이스가 각도마다  흰 판 · 환기구 패널 · 빈 공간 으로 그려졌다
```

구분해야 할 두 가지가 있다.

| | 캡처에서 | 왜 |
|---|---|---|
| 발광 **표면**(`emissiveIntensity`) | **낮춘다** (0.25배) | 하얗게 타서 형태를 지운다 |
| 실제 **빛**(light) | 그대로 | 책상 위 빛 웅덩이·색 번짐은 필요한 정보다 |

`emissive` **색은 바꾸지 않는다** — 색을 없애면 "따뜻한 색온도 스탠드"와 "RGB 케이스"를
모델이 구별하지 못한다. 완전히 끄지 않는 이유도 같다: "켜져 있다"는 단서까지 사라진다.

**블룸은 따로 끌 필요가 없다.** `EffectComposer` 후처리라, `renderer.render()` 를 직접 부르면
자동으로 빠진다(2026-08-02 확인). 나중에 블룸을 composer 밖으로 옮기면 이 가정이 깨진다.

### 1.4 툰 아웃라인을 끈다

현재 캡처에는 책상 모서리·벽 코너에 검은 윤곽선이 있다. 이것이 두 가지를 망친다.

- 낮은 strength 에서 윤곽선이 그대로 보존되어 "일러스트" 신호가 남는다
- ControlNet canny 조건이 **선화가 되어**, 모델이 선 안을 평면으로 칠한다
  (실측: conditioning_scale 0.7 이상에서 채도가 5.2% → 2.8% 로 오히려 하락)

### 1.5 음영이 있어야 실사화가 걸린다

평면 셰이딩 렌더는 실사화되지 않는다. 같은 설정으로 입력만 바꿔 확인했다.

| 입력 | 국소 표준편차(음영량) | 결과 |
|---|---|---|
| 3D 렌더 (그라데이션·그림자 있음) | **1.71** | 사진처럼 변환됨 |
| 평면 도형 (DAY/ON) | 0.86 | 그대로 일러스트 |
| 평면 도형 (NIGHT/OFF) | 0.56 | 사진은 되나 물체가 사라짐 |

→ soft shadow, IBL(환경맵), 접지 그림자, 재질 반사를 켠다.
모델은 입력에 있는 음영 단서를 **증폭**할 뿐, 없는 것을 만들지 않는다.

**워커가 이 값을 재서 1.2 미만이면 응답 `warnings` 에 남긴다.** 거부하지는 않으므로,
백엔드가 그 경고를 로그에 남기면 렌더 설정이 잘못됐을 때 바로 드러난다.

주의: 이 수치는 **3x3 창, 생성 크기로 축소한 뒤** 잰 값이다. 창 크기나 해상도가 다르면
값이 달라지므로 다른 척도로 잰 숫자와 비교하면 안 된다.

> **⚠️ 2026-08-02 정정 — 임계값 1.2 는 이 경우를 잘못 판정한다**
>
> 실제 시뮬레이터 렌더로 재보니 위 표의 전제가 깨진다.
>
> | 캡처 | 음영량 | 실사화 |
> |---|---|---|
> | 툰 외곽선 **ON** | 0.91~0.98 | 거의 안 걸림 |
> | 툰 외곽선 **OFF** | 0.74~0.79 | **걸림** (평탄 92→79%) |
>
> **외곽선을 끄면 음영량이 내려간다** — 검은 윤곽선 자체가 국소 대비에 기여하고 있었다.
> 그런데 결과는 좋아진다. 즉 이 지표는 "외곽선이 꺼졌는지"를 재는 데 쓸 수 없고,
> 0.75 처럼 낮은 값에서도 실사화가 걸린다.
>
> 임계값 1.2 는 "합성 도형 0.86 ↔ GLB 렌더 1.71" 사이에서 잡은 값인데, 그 사이에
> **외곽선 없는 시뮬레이터 렌더**라는 제3의 경우가 있고 거기서는 통하지 않는다.
> 경고 문구를 고쳐야 하고(§4 체크리스트 참고), 임계값은 표본을 더 모아 다시 잡아야 한다.

## 2. 품질을 크게 올리는 것 (선택이지만 효과 큼)

### 2.1 씬을 채운다

목표로 제시된 데스크테리어 사진과 현재 캡처의 가장 큰 차이는 실사화가 아니라 **밀도와 색**이다.

| 지표 | 현재 캡처 | 목표 사진 |
|---|---|---|
| 평탄 영역 비율 | 87% | 47~60% |
| 채도 | 5% | 34~44% |
| 경계 밀도 | 3.3% | 5.5~7.3% |

화면의 87% 가 빈 단색 벽·바닥이고 색이 거의 없다.
**img2img 는 방을 꾸며주지 않는다** — 페그보드·책·식물·러그·직물·의자는 없으면 생기지 않는다.

효과 순: 소품(필기구·책·트레이) → 식물 → 직물(러그·매트) → 가구(의자·서랍장) →
벽/바닥 텍스처 → 화면을 채우는 카메라 프레이밍.

### 2.2 depth 버퍼를 함께 준다

ControlNet 조건을 canny(엣지) 대신 depth 로 쓸 수 있다.

- canny 는 입력의 툰 윤곽선을 그대로 조건으로 옮긴다(1.3 참고)
- depth 는 형상만 전달하므로 스타일이 옮겨붙지 않는다
- 시뮬레이터의 depth 버퍼는 **추정이 아니라 정확한 값**이다

`diffusers/controlnet-depth-sdxl-1.0-small`(0.30GB)은 이미 받아두었다.
요청의 `controlImagePath` 로 넣으면 된다.

## 3. 캡처 형식

```text
포맷      PNG (권장) 또는 JPEG
크기      2048x1152 로 보낸다 (아래 참고)
비율      16:9
최소      가로·세로 512 이상
```

### 크기는 2048×1152 로 **고정**한다 (2026-08-02 확정)

워커의 생성 픽셀 예산이 `2048*1152` 라, 그 크기로 보내면 **확대가 0배**가 되어 선명도
손실이 없다. 다르게 보내면 그 차이만큼 Lanczos 확대되어 흐려진다.

```text
캡처 2400x1350 → 생성 1344x768 → 출력 2400x1350   선명도 34  (1.79배 확대)
캡처 2048x1152 → 생성 2048x1152 → 출력 2048x1152   선명도 55  (확대 없음)
                                    캡처 원본 선명도 68
```

**⚠️ `renderer.setSize` 는 DPR 을 곱한다.** 그래서 `setSize(2048, 1152)` 만으로는 부족하다 —
DPR 1.5 화면에서는 3072×1728, DPR 2 에서는 4096×2304 가 나온다. 즉 **사용자 모니터가
상상도 화질을 좌우한다.** 캡처 동안 픽셀 비율을 1 로 고정하고 원복해야 한다.

```ts
const prevPixelRatio = renderer.getPixelRatio()
try {
  renderer.setPixelRatio(1)
  renderer.setSize(2048, 1152, false)   // 세 번째 false: CSS 크기는 그대로
  // ... 3 프레임 대기 후 캡처
} finally {
  renderer.setPixelRatio(prevPixelRatio)
  renderer.setSize(prevWidth, prevHeight, false)
}
```

이 값은 워커의 `generation_pixel_budget` 과 **짝이다** — 한쪽만 바꾸면 확대가 다시 생긴다.

## 4. 요청에 함께 보내는 값

```json
{
  "jobId": 184,
  "mode": "REALISTIC",
  "timeOfDay": "NIGHT",
  "roomLightOn": true,
  "productLights": [{ "productId": 501, "enabled": true, "color": "#6FA8FF" }],
  "moodTags": ["WHITE_MINIMAL", "BLUE"],
  "productSummary": ["monitor", "keyboard", "desk lamp"],
  "seed": 42
}
```

- `timeOfDay` / `roomLightOn` 은 **캡처의 조명 상태와 일치해야 한다.**
  이 값은 조명을 만들지 않고, 모델에게 어떤 장면인지 알려 재질 표현을 그쪽으로 민다.
- `productSummary` 는 일반 명사로 짧게. 제품 정체성은 3D 가 정하므로 길게 쓸 필요가 없다.
  프롬프트가 이미 71~75/77 토큰이라 길어지면 다른 지시가 밀려난다.
- `moodTags` 는 `WHITE_MINIMAL` / `BLUE` / `PINK` / `BLACK` / `WOOD`.
- `productLights[].color` 는 색 이름으로 변환되어 들어간다(`#6FA8FF` → `cool blue`).
  **주의**: 색 지정은 화면 전체에 걸려 다른 물체까지 물들 수 있다(실측: 텀블러가 보라색이 됨).
  제품 색은 3D 재질로 표현하는 편이 정확하다.

## 5. 현재 처리 성능 (RTX 4070 Laptop 8GB)

```text
모델 로드      18초 (Worker 기동 시 1회)
생성           18.7초/장  (RealVisXL + ControlNet canny, 16 step, CFG 5.0)
VRAM           6004 MB / nvidia-smi 7546 MB (8188 중)
동시 처리      1건 (백엔드 큐가 줄을 세운다)
```

**요청 1건 = 1장 = 약 18초.** 사용자가 생성 페이지에서 고른 조명 조건 하나로만 만든다
(2026-08-01 결정). 조건을 바꿔 다시 누르면 그때 한 장을 더 만든다.

미리 네 조건을 다 만들어 두지 않는다 — 렌더는 0.3초로 싸지만 생성이 장당 18초라,
사용자가 안 볼 세 장에 54초와 GPU 를 쓰게 된다.

## 6. 폐기한 접근 (기록)

시뮬레이터가 3D 단계에서 해결하기로 하면서 아래 두 가지를 코드에서 제거했다.
사본은 대화 기록과 `docs/QUALITY_GAP_ANALYSIS.md` 에 남아 있다.

| 폐기 | 이유 |
|---|---|
| 2D 제품컷 합성 (`products[].imagePath`, `box`, `quad`) | 원근을 맞출 수 없다. 흰 제품+흰 배경에서 누끼가 21.5% 만 남았고, quad 로 강제 변형하니 모니터가 더 어색해졌다 |
| 조명 프리셋 근사 (톤 커브·방향 그라디언트) | 그림자 방향이 안 바뀌고 빛 웅덩이·바운스가 없다. 시뮬레이터가 조명을 바꿔 렌더하는 편이 싸고 정확하다 |

## 7. 요약 체크리스트

캡처를 보내기 전에:

```text
[ ] 화면 캡처가 아니라 별도 렌더인가 (DOM 오버레이가 안 들어갔는가)
[ ] 실제 제품 GLB 로 배치했는가 (프록시 박스 아님)
[ ] 요청할 조명 상태로 렌더했는가 (프롬프트가 조명을 만들지 못한다)
[ ] 발광 표면을 낮췄는가 (RGB 케이스·조명이 흰 덩어리로 안 나오는가)
[ ]   단, **모니터 화면은 예외** — 감쇠하면 액자 그림으로 읽힌다 (FINDINGS §1.10)
[ ] 툰 아웃라인을 껐는가
[ ] soft shadow / GI 를 켰는가
[ ] **2048×1152 인가, 그리고 픽셀 비율을 1 로 고정했는가** (§3 — DPR 이 화질을 좌우한다)
[ ] 책상+제품이 프레임을 채우는가 (§3 구도 — 물체 비율 40% 대가 목표)
[ ] timeOfDay / roomLightOn 이 렌더 상태와 일치하는가
[ ] (선택) 소품·식물·직물로 씬을 채웠는가
[ ] (선택) depth 버퍼를 함께 보내는가

**보내기 전에 이걸로 재본다** — GPU 없이 1초다.

```powershell
.\.venv\Scripts\python.exe scripts\check_capture.py <캡처들>
```

음영량이 1.2 미만이면 그대로는 실사화가 안 걸린다. 실측(2026-08-02) 0.76 짜리 캡처는
선명도가 42.6 → 40.9 로 **오히려 나빠졌다.**
```

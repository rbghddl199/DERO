# 0023. 아이템 자세는 사용자가 정한다 — 접촉 솔버 대체

상태: **확정** (2026-08-04, 승인 박동규 — 그릴링 세션) · **결정 1·10의 지지면 정의는 0024가 개정**(모니터는 규격 박스 상단이 아니라 스탠드 발판만 내놓는다) · **결정 3의 높이 상한만 2026-08-11 개정**(1000→2600mm, 승인 박동규 — DERO-588). ADR-0022를 대체한다.

## 맥락

- ADR-0022(2026-08-03)가 도입한 표면 접촉 솔버는 아이템 밑면 vs 아래 아이템 실메쉬에서 관입 없는 안착 자세(위치 + 기울기)를 기하로 계산했다. 구현·배포까지 끝났으나 **시각 판정에서 또 반려됐다**(2026-08-04, 박동규) — 아이패드↔거치대가 여전히 원하는 자세로 앉지 않고, 무엇보다 **솔버가 자세를 매 프레임 재계산하니 사용자가 각도를 손으로 고칠 수 없다.** tilt는 "솔버 자세 위의 보정 오프셋"(ADR-0022 결정 6)이라 사용자 입력과 솔버가 서로 싸운다.
- 즉 이 자리의 실패는 알고리즘의 정확도가 아니라 **권한**이었다. cradle 휴리스틱(형태 가정) → 접촉 솔버(기하 계산) 두 세대 모두 "엔진이 자세를 정한다"를 전제했고, 두 세대 모두 반려됐다. 세 번째 알고리즘을 쓰는 대신 전제를 뒤집는다.
- 자세를 사용자가 정하면 **저장해야 한다.** ADR-0022는 저장 자리가 없다는 제약(`placed_item`은 위치 x/y/z + yaw 하나)을 "로드 때 재계산"으로 우회했고, 그 우회가 곧 사용자에게서 권한을 빼앗은 구조였다. 제약을 우회하지 말고 컬럼을 하나 늘린다.
- 부동 선택 툴바(ADR-0022 결정 8)도 폐기됐는데, 남은 우측 패널은 숫자 입력 두 칸뿐이라 "여러 각도를 만져보는" 조작감이 사라졌다. 폐기 사유는 "높이 조절 시 패널·마우스 동반 상승"이었고 그 원인은 **조작 중에도** 좌표를 따라간 것이지 부동 그 자체가 아니었다.

## 결정

1. **접촉 솔버 폐기.** `frontend/src/three/core/contact.ts`·`three/scene/contactSample.ts`와 회귀 테스트를 삭제하고, ADR-0022가 흡수했던 **규격 박스 스태킹(`core/snap.ts` `supportTopY` = `center.y + heightMm/2`)으로 되돌린다.** 얹기 높이는 아래 아이템 규격 박스 상단이고, 실메쉬 형상은 읽지 않는다 — 루트 CLAUDE.md의 "호환은 스펙 메타 DB(mm)만으로 판정, 메쉬 치수는 절대 읽지 않는다"와 다시 정렬된다.
2. **자세는 사용자 입력이고 저장한다.** `placed_item.pitch_deg NUMERIC(6,2) NOT NULL DEFAULT 0` 신설(ERD 언락 2026-08-04, 승인 박동규). 타입 근거는 `placed_item.rotation_deg`와 같다 — 사용자가 연속 조작하는 인스턴스 각도라 정수로 자르면 경계 배치가 재로드 후 뒤집힌다(`erd.md` 전역 규칙). **로드 시 자세 재계산은 없다** — 저장값이 정본이다.
3. **수동 3축.** 회전(yaw, 저장) · 앞뒤 기울기(pitch, **±75°**, 저장) · 높이(y, **0~2600mm**, 저장 — 원안 1000은 근거 없는 임의값이었고 월드 바닥 기준 절대값이라 상판(~720mm) 위 여유가 280mm뿐이어서 결정 4가 명시한 "모니터 위 예외는 수동 높이"(모니터 상단 ~1260mm)를 스스로 막았다. 벽 높이(`WALL_HEIGHT_M` 2.6m)와 일치하는 2600으로 개정, 2026-08-11 승인 박동규 — DERO-588). pitch 상한 75°는 솔버가 "아이템을 통째로 눕히는 것을 막는다"며 쓰던 값(`MAX_CONTACT_TILT_RAD`)을 계승한다 — 거치대에 세운 태블릿의 실제 각도가 45°를 넘어 종전 `PITCH_LIMIT_DEG = 45`로는 원하는 자세가 안 나온다. **좌우 기울기(roll)는 넣지 않는다**(요청된 사례 없음 — 필요해지면 같은 방식으로 `roll_deg` 추가).
4. **높이는 절대값이다.** 드롭 순간만 `supportTopY`로 초기화하고, 이후 사용자가 준 y가 정본이다. 받침을 치우면 위 아이템은 **그 자리에 남는다**(따라 내려오지 않는다). 상대 오프셋을 택하면 저장 컬럼이 하나 더 필요하거나 로드 시 받침을 추정해야 하고, 그 추정이 곧 이 ADR이 폐기하는 휴리스틱이다. "놓은 자리에 그대로 있다"는 ADR-0022가 물리엔진을 부결한 근거와 같은 철학이다.
5. **얹힘 충돌 예외.** 자유 높이·기울기는 필연적으로 규격 박스 관입을 만든다(아이패드를 거치대 홈에 넣는 정상 조작이 그렇다). XZ 겹침 + 아이템 밑면이 상대 박스 상단 근처/아래면 **얹힘으로 런타임 추론해 그 쌍의 충돌 경고만 억제**한다. 저장하지 않고 로드 시 같은 규칙으로 재추론한다. 이 추론은 **자세를 정하지 않는다 — 경고만 정한다**. 틀려도 아이템 위치는 사용자가 준 값 그대로이고, 그래서 휴리스틱 두 세대를 반려시킨 실패 모드가 여기서는 재현되지 않는다.
6. **부동 선택 툴바 복구.** 아이템 위에 뜨는 툴바를 되살리되(`selectionAnchor.ts`·`utils/selectionToolbarPos.ts` 부활) **조작이 시작되면 그 순간 화면 좌표를 동결하고, 조작이 끝나면 다시 추적한다.** 폐기 사유(동반 상승)의 원인만 도려낸다. 3축 모두 숫자 입력 + 꾹 누르기 ±(회전 120°/s, 기울기 30°/s) — 같은 문제는 같은 방식으로 푼다.
7. **링 기즈모·R 키는 유지하고 병존한다**(ADR-0022 결정 7의 직접 조작 부분). 링은 씬에서 큰 각을 휙 돌리는 도구, ± 버튼은 1~5° 미세 조정 도구로 역할이 갈린다. 45° 자석 스냅·6° 임계도 그대로다.
8. **게이트 없음은 유지한다**(ADR-0022 결정 3). `CRADLE_ACCEPTS` 카테고리 표와 `stackable` 지지 게이트를 되살리지 않는다 — 아래 표면이 있으면 얹힌다.
9. **결합(mount) 층은 무변경**(ADR-0022 결정 5 유지). 모니터↔암·암↔책상의 규격 판정·엣지락·VESA 자석은 그대로다. 결합은 실물에서 볼트로 체결되는 관계라 위치 자유도가 없는 것이 맞고, 각도 자유도는 관절이 준다 — 얹기와 물리적으로 다른 행위다.
10. **용어 개정.** `표면 안착 (seat)` → **`얹기 (stack)`**, `안착면` → **`지지면 (support surface)` = 아래 아이템 규격 박스 상단**. "실표면 안착"이라는 이름이 메쉬를 읽으라고 계속 유혹했다 — 이름에 규칙을 박는다. `형태 페어링 (accepts)`은 폐기 상태 유지.

## 대안과 버린 이유

- **솔버 4차 수정 / 다른 알고리즘(높이장·SDF)**: 실패 원인이 정확도가 아니라 권한이라 알고리즘을 바꿔도 "내가 각도를 못 정한다"가 남는다. 두 세대(휴리스틱·솔버) 반려가 실측 근거다.
- **기울기를 저장하지 않고 세션 한정으로 두기**: ADR-0022의 tilt가 그랬고, 불만이 "리로드하면 날아간다"로 이름만 바뀐다. 자유도를 주기로 한 순간 pitch는 파생값이 아니라 원본 입력이다.
- **`joint_values` JSONB에 pitch를 얹어 ERD 동결 우회**: 그 컬럼 정의는 "`asset.rig_manifest`의 관절 키"(`erd.md` `placed_item` 절)다. 관절 아닌 값을 넣으면 코드베이스가 영구히 예외를 기억해야 하고, 컬럼 하나 추가보다 총비용이 크다.
- **하드 클램프(받침 상단 아래로 못 내려감)**: 아이패드를 홈에 넣으려면 등받이 규격 박스를 지나 내려가야 한다 — 사용자가 하려는 조작 자체를 막는다.
- **예외 없는 소프트 블록**: 정상적인 얹기가 전부 빨강·저장 거부가 된다. 경고 피로가 저장 게이트를 무의미하게 만든다.
- **아이템 간 충돌 경고 전면 폐기**(자유도 철학의 극단): 가장 단순하지만 모니터 두 대가 서로 관통해도 조용해지고, 이미 쓰이는 빨강 피드백 삭제 파급이 크다.
- **물리엔진**: ADR-0022의 부결 근거(비결정성 → 자세 저장 필요, pixel-bound 씬에 상시 시뮬 예산 없음)가 그대로 유효하다. 미끄러짐·중력도 그대로 부결 — 놓은 자리에 안 놓이는 것은 배치 도구에서 통제 상실이다.
- **좌우 기울기(roll) 동시 도입**: 요청된 배치 사례가 없다. 컬럼 하나가 영구히 0으로 남을 위험.

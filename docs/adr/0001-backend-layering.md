# ADR-0001. 계층형 유지 + 깊은 엔티티 + 외부 경계 3곳 포트

## 상태

**확정** — 2026-07-24, 승인 박동규.
결정 티켓 DERO-128 (에픽 DERO-125). 설계 맵: `docs/context/architecture-map.md`.

## 맥락

백엔드 2명 / 4주. 팀은 Spring MVC 계층형만 경험했고 포트/어댑터는 처음이다. 학습 목적이 있어 헥사고날 채택 의사는 열려 있었고, 이 티켓이 그 판단을 맡았다.

**백엔드 Must 요구사항에는 계층을 나눠 지킬 도메인 로직이 없다.** 로직이 있는 요구사항은 전부 Should다:

- REQ-REC-02 질문 기반 세팅 추천 (Should)
- REQ-CMP-06 "불가" 판정 시 대안 제품 제시 (Should)
- REQ-ADM-04 사용자 업로드 검수 워크플로 (Should)

Should는 4주 2명에서 잘릴 후보다. 잘릴 로직을 위해 계층을 나누면 남는 건 CRUD를 감싼 인터페이스뿐이다.

**반면 엔티티 단위 로직은 Must급으로 실재한다:**

| 로직 | 근거 |
|---|---|
| `asset.review_status` 전이 (`PENDING`→`APPROVED`/`REJECTED`) | `docs/CONTEXT.md` D20 |
| 규격 등록 검증 — 서브타입 boolean 필수, clamp NULL 방어 | `docs/context/compatibility.md` 물림 규격 결측 방어 |
| GLB 업로드 한도 판정 — "경량화 후 구간 상한 초과 시 반려" | `docs/CONTEXT.md` 미결 절(자작 제품 GLB 업로드 한도) |
| 견적 합산 제외 — `product.source = USER`는 가격이 없어 제외 | REQ-REC-01 |

이 로직들은 상태와 붙어 있다. 엔티티 안에 두면 서비스 계층을 쪼개지 않고도 단위 테스트가 된다. **깊은 엔티티가 "도메인 모델 ↔ JPA 엔티티 분리 + 매퍼"의 테스트 가능성을 매퍼 비용 없이 준다** — 그게 이 결정의 핵심이다.

## 결정

### 1. 헥사고날·클린 아키텍처를 전면 채택하지 않는다

`backend/CLAUDE.md`의 현 규칙을 유지한다 — `com.brunchies.dero.<도메인>/{controller,service,repository}`.

### 2. 깊은 엔티티 모델

상태 불변식과 전이 규칙은 **엔티티 메서드**로 쓴다. 서비스는 조회·조립·트랜잭션만 맡는다.

- **엔티티는 리포지토리를 모른다.** 자기 필드와 인자로 받은 값만 쓴다. 엔티티에 `@Autowired`나 정적 접근을 넣지 않는다 — 넣는 순간 엔티티 단위 테스트가 스프링 컨텍스트를 요구하게 되고, 이 결정의 값이 통째로 날아간다.
- **기본 생성자는 `protected`**, 생성은 정적 팩터리로 한다. JPA가 요구하는 no-arg 생성자를 외부에 열어두면 불변식을 건너뛴 인스턴스가 만들어진다.
- **`equals`/`hashCode`를 id 기반으로 만들지 않는다.** 미저장 엔티티는 id가 전부 `null`이라 서로 같아진다 — 단위 테스트가 조용히 거짓 통과한다.

### 3. 포트/어댑터는 외부 경계 3곳에만 둔다

| 포트 | 왜 |
|---|---|
| 추천 엔진 | 룰베이스 → RAG 교체가 예정된 갈아끼움 지점 |
| AI 상상도 provider | 티켓 DERO-139 미결 — provider를 아직 못 골랐다 |
| 오브젝트 스토리지 | 티켓 DERO-131 미결 — 전달 경로 6안이 살아 있다 |

**추천 포트 시그니처는 RAG 제약(실패·타임아웃·근거 필드) 기준으로 짠다.** 룰베이스 기준(동기·무실패)으로 짜면 RAG를 붙이는 날 시그니처를 갈아엎게 되고, 포트를 둔 의미가 사라진다.

**소셜 로그인엔 포트를 두지 않는다** — Spring Security OAuth2 client가 이미 provider 추상화다. 그 위에 우리 인터페이스를 얹으면 추상화가 두 겹이 된다.

**리포지토리엔 포트를 두지 않는다** — ERD가 동결이고 Postgres JSONB 컬럼(`asset.rig_manifest`·`monitor.ports`·`placed_item.joint_values`)에 묶여 있어 바꿀 수가 없다. fake 리포지토리 단위 테스트는 FK·제약·JSONB 매핑·트랜잭션을 전부 통과시켜 가짜 안정감만 준다.

### 4. 테스트 전략

| 대상 | 방식 |
|---|---|
| 엔티티·순수 로직 | 단위 테스트 — 스프링 컨텍스트 0 |
| 영속성·CRUD | Testcontainers 통합 테스트 |
| API | e2e |

**outside-in TDD**로 간다 — 실패하는 e2e를 먼저 쓰고, 통합으로 좁히고, 구현한다.

**H2는 쓸 수 없다.** JSONB 컬럼 3곳(`asset.rig_manifest`·`monitor.ports`·`placed_item.joint_values`)과 `docs/context/erd.md` 전역 규칙의 타입 정밀도(`NUMERIC(6,2)` 각도 예외 등) 때문에 통합 테스트는 진짜 Postgres여야 한다. Testcontainers를 `reuse=true`로 띄워 컨테이너를 재사용한다.

### 5. 깊은 TDD 실습장은 프론트 `collision.ts`

호환성 판정을 TDD로 깊게 연습할 자리는 백엔드가 아니라 `frontend/src/three/core/collision.ts`다.

- vitest 4.1.10을 이미 쓰고 있다 (`frontend/package.json`, `npm test`)
- 순수 함수라 셋업이 없다
- 케이스가 `docs/context/compatibility.md`에 이미 정리돼 있다 — 클램프 물림 두께 `max` 규칙의 양방향 오판(상판 18/엣지 40, 상판 25/엣지 15), NULL 방어("적합으로 떨어뜨리지 않는다"), `is_clamp_mountable = false` 시 판정 행 부재

## 대안과 버린 이유

**① 전면 클린 아키텍처 — 도메인 모델·JPA 엔티티 분리 + 매퍼**
28테이블 × 매퍼면 코드량이 2배가 된다. 지킬 로직이 CRUD라 매퍼 타이핑만 남는다. 매퍼가 사주는 테스트 가능성은 깊은 엔티티가 공짜로 준다.

**② 전 도메인 유스케이스 포트**
인터페이스 개수만 늘고 테스트 가능성은 그대로다 — 깊은 엔티티가 이미 그걸 준다.

**③ 리포지토리 포트 + fake 구현**
ERD 동결 + JSONB로 교체 가능성이 0이다. fake는 FK·제약·JSONB 매핑·트랜잭션을 전부 통과시켜 통합 테스트에서 터질 것을 단위 테스트에서 초록으로 만든다 — 가짜 안정감이 없느니만 못하다.

## 파급

- `backend/CLAUDE.md` 필수 규칙에 깊은 엔티티 3항목과 포트 3곳을 반영했다.
- [DERO-133 영속성 도구 결정](DERO-133)·[DERO-134 패키지 구조 결정](DERO-134)의 블로킹이 풀렸다.
- **애그리거트 경계는 아직 미결.** 깊은 엔티티로 확정됐으니 다음 질문은 "어떤 엔티티가 애그리거트 루트인가"이고, 134 패키지 구조와 함께 잡힌다.
- 호환성 판정을 서버가 맡을지 클라이언트가 맡을지는 DERO-152로 떼어냈다. 이 ADR의 5번은 "연습을 어디서 하나"이지 "판정이 어디 사나"가 아니다.
- Testcontainers 도입이 확정 사항이 됐다 — 빌드 의존성·CI 실행 시간에 반영된다.

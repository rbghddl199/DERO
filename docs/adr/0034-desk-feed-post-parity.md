# ADR-0034. 데스크피드 post 동형 전환 — 제목·마크다운 본문·인라인 이미지

## 상태

**확정** — 2026-08-11, 승인 박동규 (그릴링 세션). **결정 1(스키마 post 동형)·결정 3(UI post형
아티클)은 같은 날 [ADR-0036](0036-desk-feed-instagram-rollback.md)이 대체**한다(그 0036 결정 1은
다시 [ADR-0037](0037-desk-feed-editor-return-and-seo.md)이 대체 — 현행 정본은 0037) — `title` 추가,
사진 규칙(결정 2), 재이관(결정 4), `desk_feed_product`(결정 5), 불변(결정 6)은 유효.
[ADR-0033](0033-desk-feed-dedicated-domain.md) **결정 2(사진 우선 콘텐츠 모델)를 대체**한다 —
전용 도메인(결정 1)·배치 단일 FK(결정 3)·양방향(결정 4)·엣지(결정 5)·범위(결정 6)는 유효.
기획급 근거는 `docs/CONTEXT.md` D32 개정, 스키마 정본은 `docs/context/erd.md` `desk_feed` 절.

## 맥락

ADR-0033 결정 2는 "인스타형 사진 글에 제목이라는 개념이 없다"를 전제로 제목·마크다운 본문·
에디터를 뺐다. 출시 하루 뒤 운영 실데이터가 그 전제를 반증했다:

1. **운영 4행 전원이 첫 줄을 제목처럼 쓴다** — "DERO 개발자의 R.E.A.L 책상 공개",
   "심플한 내책상", "저는 키보드만 따로 써요", "생존물품만 있는 나만의 데스크". 목록 카드
   오버레이도 이 첫 줄을 제목처럼 그리고 있었다.
2. 이 4행은 전부 **post 502·552·553·554의 마이그레이션 사본**이다(V11이 이관) — 원본은
   title + 마크다운 본문 + 인라인 이미지(`![alt](post-images/...)`)를 온전히 갖고 있는데,
   사본은 그 구조를 캡션 하나로 뭉갠 것이었다.
3. 사용자 요구가 확정됐다: **목록은 지금처럼 사진이 부각된 인스타형 그리드**를 유지하되,
   **상세를 누르면 글(본문 중간에 이미지가 박힌 아티클)이 보여야 한다**.

"에디터가 유입 문턱"이라는 결정 2의 우려는 UI 배치로 상쇄한다 — 문턱은 에디터의 존재가
아니라 작성 폼의 첫인상이었다.

## 결정

### 1. 스키마 — post 동형

- `desk_feed.title VARCHAR(100) NOT NULL` 추가(`post.title`과 동형).
- `desk_feed.content`는 캡션(nullable)에서 **마크다운 본문(NOT NULL)** 으로 — 이미지
  `![alt](key)`가 여기 살고 본문 안 위치가 곧 순서다(ADR-0013과 같은 정본 규칙).
- `desk_feed_image`는 `post_image` 동형으로: `display_order`·복합 유니크 삭제 →
  `is_primary` + 부분 유니크 `uq_desk_feed_image_desk_feed_id`(`WHERE is_primary`) +
  FK 인덱스 신설. 대표는 순서 0번이 아니라 `is_primary` 한 장이다.

### 2. 사진 규칙 — 데스크피드 정체성은 유지

- **최소 1장 강제 유지**(노출 게이트 — 0장 글은 목록 제외·상세 작성자 전용). post는 0장을
  허용하지만 사진 그리드에 사진 없는 카드는 구멍이다.
- **상한 10장 유지**(post는 20). 사진 피드의 스크롤 밀도가 근거였고 바뀔 이유가 없다.

### 3. UI — "사진 부각"은 화면 배치가 답한다

- 목록: 현행 유지 — `is_primary` 썸네일 그리드 + title 오버레이 + "N장" 배지.
- 상세: post형 아티클 뷰(마크다운 렌더, 본문 중간 인라인 이미지).
- 작성: post 에디터(Tiptap) 재사용 + **사진 업로드 존을 상단에 크게** 배치.
  REQ-COM-16의 "에디터 없음"은 철회한다.

### 4. 데이터 — 삭제 후 원본 재이관

- 기존 desk_feed 4행 삭제(CASCADE로 좋아요·댓글·사진·태그 동반) — **좋아요·댓글 리셋 승인**.
- post 502·552·553·554에서 재이관: title·본문(이미지 토큰 포함)·작성자·감사 복사,
  `like_count`는 0. 이미지 키는 `post-images/` **그대로 참조**한다 — 오브젝트 정리 로직이
  어디에도 없어 post 행이 지워져도 파일은 남는다(`requireOwnKeys`는 신규 등록 경로에만
  적용되므로 legacy 키와 충돌하지 않는다).
- **원본 post 4건은 재이관 배포 후 작성자들이 커뮤니티 화면에서 직접 삭제**한다 — 순서가
  뒤집히면 소스가 사라진다(post는 hard delete). 두 벌 공존은 과도기 며칠만 감수한다.

### 5. 사용된 제품 태그 — `desk_feed_product` 정션 (같은 세션 추가 확정)

글에 "이 책상에 쓰인 제품"을 **product id 목록**으로 붙인다 — 상세 하단 "사용된 제품" 카드
섹션(대표 이미지·이름·가격)에서 **내부 링크**(`/product/{id}`)로 이동한다. 외부(쿠팡류) 링크
아님.

- 저장은 정션 `desk_feed_product`(desk_feed N:M product, FK 양쪽 CASCADE — `product_hashtag`
  등 기존 product 정션과 같은 규칙) + `idx_desk_feed_product_product_id`. **토큰이 아닌
  이유**: 요구가 "어떤 제품이 쓰였나"라는 구조화된 목록이고, 역방향("이 제품이 쓰인
  데스크피드")이 인덱스 하나로 성립한다 — 화면은 후속, 인덱스는 지금.
- 상한 10개(WAS 강제, 사진 상한과 같은 결). 검증은 배치 첨부와 같은 패턴(존재+미삭제 아니면
  422 한 코드 — 존재 여부를 흘리지 않는다). 소프트삭제된 제품은 행 유지·화면 숨김(배치
  카드와 같은 규칙). 목록 카드에는 안 싣는다.
- 선택 UI는 **수동 피커 + 배치 프리필** — 배치를 첨부했으면 "배치에서 제품 불러오기"가 그
  배치의 제품들을 프리필하고 사용자가 가감한다. 자동 파생만 쓰는 안은 배치 없는 사진 글에서
  제품 태그가 불가능해져 부결.

### 6. 불변

배치 단일 nullable FK·첨부 자격(본인 PUBLIC, 422)·태그 ≤5·게시 상태 없음·북마크 없음·
플랫 댓글·presign 2단계 — 전부 ADR-0033 그대로.

## 대안과 버린 이유

- **갤러리 정본 유지 + title만 추가(최소 변경)**: 본문 중간 임의 위치에 이미지가 박히는
  요구를 충족하지 못한다 — "UI만 부각"의 실체가 저장 구조가 아니라 화면 배치임이 확인돼
  저장은 post 동형으로 통일했다.
- **title nullable**: 운영 4행 전원이 제목을 쓰고 있었고 post와 검증 규칙이 갈라지면
  에디터 재사용이 지저분해진다.
- **좋아요·댓글 보존 이관**: 사본 4행의 상호작용(좋아요 6·댓글 소수)을 id 매핑으로 옮기는
  비용 대비 가치가 없다 — 승인된 리셋.

## 대가

- ADR-0033 결정 2가 하루 만에 대체된다. 정직하게 적는다: "인스타형에 제목 없음"은 레퍼런스
  (인스타그램)에서 온 가정이었고, 우리 사용자의 실데이터 4건이 하루 만에 반증했다 — 콘텐츠
  모델 결정은 레퍼런스가 아니라 실사용 패턴을 기다렸다 내려도 늦지 않았다.
- `desk_feed`와 `post`의 콘텐츠 모양이 같아져 "왜 테이블이 두 벌인가"가 다시 물어질 수 있다.
  답은 ADR-0033 결정 1에 있다 — 분리 근거는 콘텐츠 모양이 아니라 피드 축(태그 필터·역방향
  조회·배치 FK)이었고 그 근거는 그대로 유효하다.
- 2026-08-10 구현분 중 사진 순서 파이프라인(`display_order` 전체 교체·`imageKeys` PUT)이
  폐기된다.

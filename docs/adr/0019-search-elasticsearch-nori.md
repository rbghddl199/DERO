# ADR-0019. 제품 검색은 Elasticsearch + Nori — 색인은 `AFTER_COMMIT`, 정본은 Postgres

## 상태

**확정** — 2026-08-03, 승인 박동규 · **결정 2의 `min_gram`은 [0028](0028-autocomplete-min-gram-two.md)이 개정**(1 → 2, 나머지 결정은 유효) ·
**결정 1의 질의 대상 필드는 [0029](0029-category-path-in-product-index.md)가 넓힌다**(`categoryPath` 추가, 문서에 담기는 값은 여전히 검색어가 맞아야 하는 것뿐이다).
[ADR-0017](0017-catalog-list-returns-full-detail.md)이 파급 절에 *"`?q=` 서버 검색(ES 예정)"*으로 미뤄 둔 항목의 후속이다.
컨테이너 계층·관측은 [ADR-0020](0020-observability-stack.md), 배선 정본은 `docs/context/observability.md`.

## 맥락

**지금 제품 검색은 전부 클라이언트 필터다.** 백엔드에 제품 이름을 조건으로 거는 쿼리가 **0건**이다 — `Containing`도 `LIKE`도 없다. 프론트가 목록을 받아 자바스크립트로 거른다.

그동안은 성립하는 구조였다. ADR-0017이 카탈로그 목록을 **통짜 상세**로 만들면서 라이브러리가 카테고리별로 **끝까지 프리페치**했고, 손에 전량이 있으니 클라 필터가 곧 전체 검색이었다. 그래서 ADR-0017은 이렇게 예약해 두고 넘어갔다.

> 검색은 전량 프리페치 후 클라 필터 유지 — 서버 `?q=`는 ES 붙일 때까지 안 만든다.
> (`docs/SPEC.md` REQ-SIM-01, 2026-08-01 ADR-0017 결정 기록)

**2026-08-03에 그 전제가 깨졌다.** 라이브러리 지연 로딩(DERO-374)이 `GET /products`를 **20개 커서 페이징**으로 바꿨다. 손에 20개밖에 없는데 필터는 그 20개 위에서만 돈다 — **"불러온 목록 안에서만 검색"이 최적화가 아니라 실제 결함이 됐다.** SPEC.md가 그 상태를 그대로 적고 있다.

> **검색은 여전히 클라이언트다**(백엔드에 검색 파라미터 없음) — 불러온 목록 한정임을 UI에 명시했다.
> (`docs/SPEC.md` REQ-SIM-01)

데스크피드(REQ-COM-13)도 같은 상태다 — *"검색은 받아 온 페이지 안에서만 도는 클라이언트 필터다."* **UI에 한계를 명시한 것은 결함을 문서화한 것이지 고친 것이 아니다.** 다만 **데스크피드가 찾는 것은 제품이 아니라 배치(placement)라 이 ADR이 고치지 못한다** — 같은 병이되 다른 인덱스다(파급 절 "범위 밖").

**실측 제약**

- **카탈로그 규모는 수십~수백 제품.** 변경 경로는 관리자 등록/수정 **하나뿐**이고, 여기에 사용자 자작 제품 승인(REQ-COM-11)이 붙어도 여전히 우리 Spring 한 곳이다.
- **서버는 EC2 1대** — 15GiB RAM(여유 12GiB), 4 vCPU, 디스크 276GB 여유. Spring Boot 4.1.0.
- 교육 과정 종료 후 **AWS 관리형 노드 분리**(RDS·ElastiCache·ALB) 이전이 예정돼 있다.

## 결정

### 1. Elasticsearch를 도입한다 — 요구는 범위·부분어/오타·자동완성 셋

사용자 요구를 셋으로 갈랐다.

| 요구 | 내용 |
|---|---|
| ① 범위 | 페이징 너머 **카탈로그 전체**에서 찾는다 |
| ② 관용 | **부분어·오타**를 흡수한다 |
| ③ 자동완성 | 타이핑 중 결과가 갱신되고, 드롭다운에 추천어가 뜬다 |

**①②만이면 Postgres `pg_trgm` + GIN으로 충분하다.** 그 판단은 바뀌지 않았다 — ES를 정당화한 것은 **③이다.** 자동완성은 매 키 입력마다 쿼리가 나가는 기능이라 지연과 랭킹이 곧 품질이고, 그 자리에 쓸 도구를 Postgres는 갖고 있지 않다.

**자동완성은 두 수단을 역할을 갈라 쓴다.** 하나로 보이지만 다른 물건이다.

| 수단 | 무엇을 돌려주나 | 화면의 어디 |
|---|---|---|
| **edge n-gram** (`name.autocomplete` 하위필드) | **제품** — 접두 일치 문서 | 결과 목록 실시간 갱신 |
| **completion suggester** (별도 FST) | **추천어** — 문자열 | 입력창 아래 드롭다운 |

**한글 초성 검색(`ㅁㄴㅌ` → 모니터)은 이 ADR의 범위 밖이다.** 색인 시 초성을 추출해 넣는 **별도 필드**가 필요하고, 그건 위 세 요구와 다른 별건이다. 필요해지면 그때 필드를 추가한다(결정 5의 별칭이 그 재색인을 무중단으로 만든다).

### 2. 분석기는 Nori + edge_ngram + keyword 멀티필드

`name` 하나를 세 갈래로 색인한다.

| 필드 | 분석기 | 쓰는 자리 |
|---|---|---|
| `name` | **Nori** | 본검색 |
| `name.autocomplete` | **edge_ngram** | 타이핑 중 접두 매치 |
| `name.keyword` | (없음) | 정확 매치·정렬 |

**Nori를 쓰는 결정적 이유는 형태소 분석 일반론이 아니라 띄어쓰기 불일치다.** 색인된 이름이 `모니터 암`인데 사용자가 `모니터암`을 친다. edge n-gram이 만든 접두 토큰은 `모`·`모니`·`모니터`·`암`이고 **`모니터암`은 그중 어느 것과도 안 맞아 0건이 나온다.** Nori는 `[모니터, 암]`으로 분해하므로 잡힌다. **한국어 서비스에서 띄어쓰기 불일치는 오타보다 흔하다** — 같은 제품을 부르는 표기가 사람마다 갈린다.

**비용**: Nori는 ES 기본 이미지에 없다. `elasticsearch-plugin install analysis-nori`를 넣은 **커스텀 이미지 빌드**가 배포에 추가된다.

**함정 — 브랜드명 오분해.** Nori는 사전에 없는 고유명사를 쪼갠다. `라이트크래프트`가 `[라이트, 크래프트]`로 분해되면 **`라이트`(조명) 검색에 엉뚱한 브랜드의 제품이 전부 걸린다.** 따라서 **`user_dictionary`에 브랜드명 등록은 선택이 아니라 필수다.** 목록은 `brand` 테이블에서 굽는다 — 손으로 관리하는 사전은 브랜드가 늘 때 조용히 낡는다.

### 3. 색인은 `AFTER_COMMIT` 이벤트 + 수동 전량 재색인 커맨드

```
[관리자 등록/수정]  →  Postgres 커밋
                         │  @TransactionalEventListener(AFTER_COMMIT)
                         ▼
                       ES 색인

[복구]  POST /admin/search/reindex  →  전량 재색인 (수백 건이면 몇 초)
```

`@TransactionalEventListener(AFTER_COMMIT)` 하나와, 짝으로 **전량 재색인 엔드포인트** 하나. 이 둘이 세트다.

- **커밋 확정 후에만 색인하므로 롤백된 유령 문서가 없다.** 트랜잭션 안에서 색인하면 롤백돼도 ES에는 남는다.
- **이벤트 색인이 실패해도(ES 다운·네트워크) 재색인 버튼 한 번이면 복구된다.** 수백 건 규모에서 전량 재색인이 몇 초라는 사실이 이 설계를 성립시킨다 — **유실 추적 인프라 없이 유실을 감당할 수 있다.**
- 즉 이 데이터 규모에서 **Outbox와 실질적으로 동등하게 안전하고 훨씬 싸다.** 규모가 바뀌면 판단도 바뀐다(대안 절).

**다중 인스턴스로 갈 때의 주의**: WAS가 여러 대가 된 뒤 **스케줄 재색인**을 붙이면 인스턴스마다 돌아 같은 일을 N번 한다. 그때는 리더 선출(ShedLock 등)이 필요하다. **지금은 수동 트리거라 무관하고, 그래서 만들지 않는다.** 여기 적어 두는 이유는 나중에 스케줄을 붙이는 사람이 이 함정을 모를 것이기 때문이다.

### 4. 정본은 Postgres, ES는 검색 전용

**ES는 제품 id 목록(+하이라이트)만 돌려준다.** 제품 상세는 Postgres에서 읽는다.

`docs/CONTEXT.md` **D7 "메쉬-규격 분리"와 같은 결이다** — 같은 사실의 정본이 두 곳에 있으면 갈렸을 때 어느 쪽이 맞는지 판정할 수단이 없다. ES 문서에 가격·규격을 실어 두면 그 값이 응답에 실려 나가고, 색인이 한 번 밀린 순간 **화면이 조용히 옛 값을 보여준다.**

**대가는 조회 1회 추가다**(수십 ms). 받아들인다.

**실제 형태**: `GET /products` 목록 원소가 통짜 상세이므로([ADR-0017](0017-catalog-list-returns-full-detail.md) 결정 1) **"ES에서 id 20개 → Postgres에서 그 20개 상세"**가 된다. 기존 목록 조회 경로에 id 필터가 하나 붙는 모양이지, 새 응답 형태가 아니다.

### 5. 인덱스는 별칭(alias) 뒤에 둔다

애플리케이션은 **`products`(별칭)**만 안다. 실체는 **`products_v1`**이다.

**ES 매핑은 한번 만들면 필드 타입·analyzer를 바꿀 수 없다.** 그런데 이 ADR이 정한 것들이 전부 **튜닝 대상**이다 — Nori 사용자 사전에 브랜드가 추가되고(결정 2), `min_gram`을 조정하고, 초성 필드가 붙을 수도 있다(결정 1). **바꿀 때마다 재색인이 온다.**

별칭이 있으면 `products_v2`를 새로 만들어 색인해 두고 별칭만 스왑한다 — **무중단**이다. 없으면 인덱스를 지우고 다시 만드는 동안 **검색이 죽는다.** 그리고 결정 6이 폴백을 두지 않기로 했으므로, **그 죽음은 그대로 서비스 장애다.** 두 결정은 같이 읽어야 한다.

### 6. ES가 죽으면 검색만 죽는다 — 폴백 없음

- 검색 API는 **503** + `ProblemDetail` / `ErrorCode`([ADR-0008](0008-api-response-contract.md) 규약).
- 프론트는 **"검색 일시 중단"** 배너를 띄운다.
- **카테고리 탐색·목록·상세는 Postgres라 전부 산다.** 죽는 것은 검색 입력창 하나다.

**Postgres `ILIKE` 폴백과 클라이언트 필터 폴백을 둘 다 부결했다.**

- **검색 로직이 두 벌이면 관련도 순서가 달라진다.** 같은 질의에 어제와 다른 순서가 나오고, **"왜 어제랑 결과가 다르지"를 아무도 풀 수 없다** — 재현하려면 그 시각에 ES가 살아 있었는지를 알아야 한다.
- **조용한 폴백은 장애를 숨긴다.** 품질이 떨어진 채로 화면이 그럴듯하게 동작하면 **ES가 3일째 죽어 있어도 아무도 모른다.** 503으로 눈에 보이게 죽는 편이 낫다.

감시는 폴백이 아니라 관측이 맡는다 — Prometheus/Grafana([ADR-0020](0020-observability-stack.md)).

### 7. Elasticsearch를 쓴다 — OpenSearch가 아니다

교육 과정 종료 후 관리형 노드 분리가 예정돼 있으므로 **목적지를 지금 정한다: Elastic Cloud on AWS.**

**Amazon OpenSearch Service는 ES 7.10에서 갈라진 포크다.** 이름이 비슷하다고 같은 물건이 아니다.

- Kibana가 아니라 **OpenSearch Dashboards**다 — 익힌 화면이 그대로 쓰이지 않는다.
- 결정적으로 **Filebeat 7.13+ 는 OpenSearch에 접속을 거부한다.** 제품 체크에 걸려 *"the client noticed that the server is not Elasticsearch"*로 끊긴다. **수집기를 Fluent Bit 또는 Data Prepper로 통째로 갈아야 한다** — [ADR-0020](0020-observability-stack.md)이 정하는 로그 수집 계층이 그대로 날아간다.

**"지금 ES로 배우고 나중에 OpenSearch로 간다"는 안이 가장 나쁘다.** 두 제품을 두 번 배우고, 그 시점에 수집기까지 갈아엎는다. 목적지를 Elastic Cloud로 고정하면 지금 쓰는 클라이언트·Kibana·Filebeat가 전부 그대로 간다.

## 대안과 버린 이유

| 대안 | 판정 | 이유 |
|---|---|---|
| Postgres `pg_trgm`/`tsvector` 전문검색 | 부결 | 요구 ①②는 충분하나 **completion suggester·edge n-gram 랭킹이 없다.** 한글 형태소 미지원 |
| 이중 쓰기 (서비스에서 `save` 직후 ES index) | 부결 | **트랜잭션이 롤백되면 ES에 유령 문서가 남는다.** 결정 3이 `AFTER_COMMIT`인 이유 |
| Outbox 테이블 + 워커 | 부결 | **누락이 치명적이고 재색인이 비쌀 때** 값을 한다. 이 카탈로그는 **둘 다 아니다** — 수백 건 전량 재색인이 몇 초다 |
| **CDC (Debezium + Kafka Connect)** | 부결 | 아래 상세 |
| 일반 n-gram (`min_gram=2`) | 부결 | **`모니`가 든 모든 제품이 걸려 관련도가 죽는다.** 인덱스도 몇 배로 부푼다 |
| Nori 없이 standard/whitespace | 부결 | **띄어쓰기 불일치를 원리적으로 못 잡는다**(결정 2) |
| OpenSearch | 부결 | 결정 7 |

### CDC를 부결한 이유

색인 누락을 원천봉쇄하는 정공법이고, "DB가 정본이니 DB 변경을 그대로 따라간다"는 논리도 옳다. **그럼에도 이 프로젝트에서는 부결이다.**

- **운영 비용이 계단식으로 뛴다.** Kafka Connect 클러스터(별도 JVM)가 추가되고, `wal_level=logical` 전환에 **운영 Postgres 재시작**이 따른다.
- **replication slot이 디스크를 먹는다.** 슬롯을 소비하는 쪽이 죽으면 **Postgres가 그 WAL을 지우지 못하고 무한히 쌓는다 → 디스크가 차고 → DB가 선다.** 검색 색인을 붙이려다 **DB 전체를 죽이는 경로**가 생긴다. 그리고 이 프로젝트는 **워커가 노트북**이라([ADR-0015](0015-placement-upload-async-pipeline.md) 결정 3) 소비자가 자주 죽는 것이 예외가 아니라 **상시 시나리오**다.
- **CDC가 값을 하는 조건이 성립하지 않는다.** CDC는 **쓰기 경로를 못 건드릴 때**(레거시 시스템·여러 서비스가 공유하는 테이블) 값을 한다. **제품 테이블에 쓰는 코드는 우리 Spring 하나다** — 이벤트 훅을 못 넣을 이유가 없다.
- **전환 비용이 싸다.** `AFTER_COMMIT` → CDC 전환은 **색인 진입점 1곳**이 바뀌는 일이다. 인덱스 매핑·검색 쿼리·API·프론트가 **전부 그대로다.** 지금 미리 짓는 것은 요청하지 않은 flexibility이고, 값은 나중에 필요해진 그날 같은 가격에 살 수 있다.

### Kafka도 같이 부결한다 — 그리고 MQ 채택은 이 ADR의 범위가 아니다

검토 계기는 CDC가 아니라 **"AI 상상도 생성 큐 + meshopt/KTX2 압축 큐로 MQ가 어차피 온다"**였다. `docs/context/architecture-map.md`의 미결 항목 *"큐를 Kafka/RabbitMQ로 옮기는 시점"*이 여기 걸린다.

**MQ 도입 자체는 정당하다.** ADR-0015 결정 2가 정의한 이관 트리거 *"작업 종류가 늘거나"*가 실제로 충족됐다. **그러나 그 MQ는 Kafka가 아니다** — 우리 워크로드는 이벤트 스트림이 아니라 **작업 큐**다.

1. **작업당 수십 초~분이다.** `max.poll.interval.ms`(기본 5분)를 넘기면 컨슈머가 죽은 것으로 간주돼 리밸런싱이 돌고, **같은 작업이 중복 실행된다.**
2. **파티션 수가 동시성 상한이고, 파티션은 줄일 수 없다.** 워커 수를 유연하게 바꾸는 모델이 아니다.
3. **오프셋 커밋이라 건별 ack가 없다.** *"3번 실패, 4번 성공"*을 표현할 수 없어 **재시도 토픽 사다리를 손으로 짜야 한다.** 지금 `BLMOVE` + 처리중 리스트가 하는 일을 더 복잡하게 다시 만드는 것이다.
4. **이 프로젝트 고유의 결정타** — 워커가 **SSH 터널 뒤 노트북**인데(ADR-0015 결정 3), Kafka는 부트스트랩 응답의 **`advertised.listeners` 주소로 재접속**한다. 터널 뒤에서 그 주소가 닿지 않아 깨진다. **Redis가 먹혔던 건 단일 커넥션이라서다.**

→ 작업 큐가 필요해지면 **Redis Streams**(`XAUTOCLAIM` — ADR-0015 결정 2가 이미 중간 단계로 지목했다) 또는 **RabbitMQ**다.

**MQ 채택 자체는 이 ADR이 결정하지 않는다 — 별도 ADR이다.** 여기서 기록하는 것은 *"검색 색인 때문에 Kafka를 들이는 일은 없다"*와 *"MQ를 논할 때 Kafka는 이 네 가지 이유로 후보가 아니다"* 둘뿐이다.

**이 ADR은 `product` 인덱스 하나만 만든다.** 데스크피드가 찾는 배치(`placement`)와 커뮤니티 게시글(`post`)은 **다른 인덱스이고 다른 결정**이다. 지금 같이 하지 않는 이유는 둘이다.

- **쓰기 빈도가 자릿수로 다르다.** 제품은 관리자만 바꾸지만 배치는 사용자가 수시로 저장·공개한다. *"수백 건 전량 재색인이 몇 초"*라는 **결정 3의 전제가 배치에는 성립하지 않는다** — 색인 실패 복구 전략부터 다시 정해야 한다.
- **무엇을 색인할지가 아직 없다.** `placement`에는 태그 컬럼이 없어(`docs/SPEC.md` REQ-COM-13) 제목·설명뿐이고, 게시글은 본문에 `[[placement:ID]]` 토큰이 섞인다([ADR-0013](0013-placement-embed-as-content-token.md)) — 토큰을 어떻게 다룰지가 선결이다.

**둘 다 [ADR-0027](0027-placement-post-author-search.md)이 닫았다 (2026-08-07).** 재색인 전제는 실측으로 성립을 확인했고(prod `placement` 188 · `post` 19 — 제품 167과 같은 자릿수), 태그는 `placement_hashtag` 정션 신설로, 토큰 처리는 구현 시점 판단으로 각각 자리를 잡았다.

**확장은 전제로 깔고 간다 (2026-08-03, 승인 박동규).** 목적지는 *"검색이 필요한 모든 곳"*이고, 이 ADR이 세우는 것들 — ES 클러스터·Nori 사용자 사전·별칭 재색인 절차·`AFTER_COMMIT` 색인 패턴·503 폴백 규약 — 은 **인덱스가 늘어도 그대로 재사용된다.** 늘어나는 것은 인덱스와 매핑이지 이 결정들이 아니다. 후속은 인덱스별로 ADR을 따로 쓴다.

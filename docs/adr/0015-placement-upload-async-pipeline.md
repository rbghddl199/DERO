# ADR-0015. 배치 업로드는 비동기 파이프라인 — Redis 큐 + 로컬 워커 + presigned URL

## 상태

**확정** — 2026-07-31, 승인 박동규. · **결정 3·4·5·6·8은 [ADR-0025](0025-single-concept-image-and-generation-outside-transaction.md)가 개정**(2026-08-06)
기획 근거는 `docs/CONTEXT.md` D27. 스키마 개정 3건은 같은 날 동결 언락으로 `docs/context/erd.md`에 반영됐다.
API 표면은 `docs/context/api-spec.md` §4.

> **아래 본문은 2026-07-31 시점의 결정 그대로다.** 개정분을 여기 덮어쓰지 않는다(ADR 규약) —
> 무엇이 왜 바뀌었는지는 ADR-0025가 답한다. 요약: **상상도는 3장이 아니라 1장**(결정 6),
> **한도 기본값은 21이 아니라 7**이고 "전부 성공했을 때만"은 원자성이지 트랜잭션 경계의 크기가
> 아니다(결정 8), **워커는 로컬 노트북 python + SSH 터널이 아니라 WAS 안 스레드 + GMS**이고
> 그래서 결정 5의 presigned URL 메시지는 실현되지 않았다(결정 3·4·5). 유실 방지 `BLMOVE` +
> 처리중 리스트 + 스위퍼(결정 4)와 Redis 포트 비공개는 그대로 유효하다.

## 맥락

기획이 바뀌었다. **배치 업로드가 단순한 공개/비공개 토글이 아니라 하나의 기능이 됐다.**

1. 사용자가 배치를 완성한다.
2. **업로드**를 누른다.
3. 데스크 피드(구 커뮤니티)에 올라간다 — 공개 상태다.
4. 즉시 "업로드됐다"는 피드백을 주지만, **실제 노출은 AI 상상도가 만들어진 뒤**다.

그리고 상상도를 만드는 모델은 외부 API가 아니라 **우리 로컬 노트북에서 도는 python 프로세스**다.

이 ADR이 답하는 것은 하나다 — **그 파이프라인을 어떤 구조로 세우는가.** 왜 필요한지·어떤 화면인지는
D27과 `docs/REQUIREMENTS.md` 소관이다.

**이미 걸려 있는 것들**

- **[ADR-0001](0001-backend-layering.md)** — 포트는 정확히 3곳이고 그중 하나가 **AI 상상도 provider**다.
  전송 수단은 그 포트의 구현 교체일 뿐이어야 한다.
- **[ADR-0004](0004-judgment-frontend-mirror-server-authority.md)** — 판정 정본은 WAS, 결과는 저장하지 않는다.
- **[ADR-0008](0008-api-response-contract.md)** — 엔벨로프 없음, `ProblemDetail` + `ErrorCode`, 커서 페이지네이션.
  **202는 이 ADR이 처음 쓴다.**
- **[ADR-0009](0009-placement-save-payload.md) 결정 5** — 저장 게이트를 **공개 게이트**로 옮겼다.
  위반 배치는 저장은 되지만 `PUBLIC` 전환이 422로 막힌다.
- **[ADR-0013](0013-placement-embed-as-content-token.md) 결정 3** — 게시글에 꽂을 배치는
  **본인의 공개 배치**로 제한된다. 즉 "공개"라는 상태가 다른 기능의 입력이다.
- **인프라 실측** — Lightsail 1대(월 6TB 전송 포함), Redis는 `127.0.0.1:6379` 바인딩이고
  **거기에 리프레시 토큰이 산다**(ADR-0005). S3 presign은 이미 배선돼 있다(`S3PresignService`,
  PUT 5분·GET 15분).
- **`docs/context/erd.md`는 동결**이다. 이 ADR이 요구한 3건은 승인 후 언락으로 반영했다.

## 결정

```
[브라우저]  PUT /placements/{id}/feed-entry
                │  ① 판정 게이트  ② 스크린샷 존재  ③ 한도
                ▼
[WAS]      publish_status = PENDING  ·  Redis LPUSH  ──────► 202 Accepted
                │
                │   요청 큐 ── BLMOVE ──► 처리중 리스트
                ▼
[노트북]    SSH 터널 → BRPOP/BLMOVE
           presigned GET 1개로 스크린샷 읽기 → 상상도 3장 → presigned PUT 3개로 업로드
                │
                ▼   결과 큐
[WAS]      3장 전부 OK ─► generated_image 3행(1행 is_primary) + publish_status = PUBLIC
           하나라도 실패 ─► 행 0개 + publish_status = FAILED
```

### 1. 게시 상태는 컬럼 하나가 답한다 — `publish_status` 4값

`placement.visibility`(PUBLIC/PRIVATE)를 **`publish_status`로 개명하고 4값으로 확장**한다.

| 값 | 뜻 | 피드 노출 |
|---|---|---|
| `PRIVATE` | 내 작업실. 기본값 | 없음 |
| `PENDING` | 업로드 눌렀고 상상도 생성 대기 | 없음 |
| `PUBLIC` | 상상도 붙음 | **있음** |
| `FAILED` | 생성 실패, 재시도 대상 | 없음 |

**`PUBLIC`과 `FAILED`는 서버만 정한다.** 클라이언트는 올림/내림만 요청한다.

**버린 대안 — 2컬럼 조합.** `visibility = PUBLIC` **그리고** `thumbnail_key IS NOT NULL`로 피드를 거르면
스키마를 한 글자도 안 건드린다. 그럼에도 버린 이유 셋:

- **피드 쿼리마다 두 조건을 정확히 같이 써야 한다.** 하나 빠뜨리면 이미지 없는 배치가 피드에 뜬다.
- **후임이 "공개인데 왜 피드에 없지"를 한 컬럼으로 답할 수 없다.** 인수인계 비용이 영구적으로 붙는다.
- **"생성 중"과 "생성 실패"를 구별할 수 없다.** 실패한 배치가 무한히 스피너를 돌린다.

**개명까지 한 이유**: `visibility = PENDING`은 말이 안 된다("가시성이 대기 중"). 이름이 거짓말을 하면
다음 사람이 뜻을 되묻는다. 그리고 **개명 창이 지금뿐이다** — 백엔드 DTO·서비스·컨트롤러가 어차피
전량 재작성 대상(2026-07-31 API 재설계)이라 개명 비용의 대부분이 이미 지불된 상태다.

### 2. 전송은 Redis 큐다 — gRPC도, 터널을 통한 인바운드도 아니다

**핵심 제약: 노트북은 NAT 뒤에 있고 공인 IP가 없다.** WAS가 노트북으로 연결을 열 수 없다.

검토한 셋:

| 안 | 방식 | 판정 |
|---|---|---|
| A | **워커 풀(gRPC 서버 스트리밍)** — 노트북이 WAS에 스트림을 열고 작업을 받아간다 | 부결 |
| B | **터널로 노트북 노출** — Cloudflare Tunnel/Tailscale + WAS가 gRPC 단항 호출 | 부결 |
| C | **Redis 큐** — WAS `LPUSH`, 노트북이 소비 | **채택** |

A는 NAT을 정면으로 풀고 gRPC를 써보고 싶다는 요구도 만족시킨다. 그럼에도 C를 고른 이유:

- **Redis가 이미 배포돼 있다.** `compose.data.yaml`에 떠 있고 리프레시 토큰이 이미 그 위에서 돈다.
  코드 몇십 줄이면 끝난다.
- **Spring Boot 4.1에 gRPC 서버를 얹는 비용이 있다.** protobuf Gradle 플러그인 + `grpc-java` +
  Boot 4의 바뀐 스타터 이름(`dero-api/CLAUDE.md`가 이미 경고한 함정). **백엔드 2명 / 4주**에서
  학습 동기만으로 지불하기엔 크다.
- **큐가 버퍼가 된다** — 워커가 없어도 작업이 쌓이고, 돌아오면 이어 처리한다. **끊김이 유실이 아니라
  지연이 된다.** 이게 노트북 워커라는 선택의 유일한 안전장치다.

B는 터널이 실패 지점을 하나 더 만들고, 인증·인증서를 새로 관리해야 해서 부결했다.

**마이그레이션 여지를 열어 둔다.** Redis 리스트는 큐로서 최소한이다 — 컨슈머 그룹·재처리·DLQ·
관측이 전부 손으로 짠 것이다. **워커가 여러 대가 되거나, 작업 종류가 늘거나, 유실 추적이 필요해지면
Kafka 또는 RabbitMQ로 옮긴다.** 그때 바뀌는 것은 `infra`의 AI provider 포트 구현 하나이고
(ADR-0001이 그 경계를 이미 그어 뒀다), 도메인 코드·API 표면·`publish_status` 상태 기계는 그대로다.
Redis Streams(컨슈머 그룹 + `XAUTOCLAIM`)는 그 중간 단계로 검토 대상이지만, 워커가 하나뿐인 지금
분산 컨슈머 인프라를 운영할 값어치가 없어 미뤘다 — **그 시점이 곧 Kafka/RabbitMQ 검토 시점이라
어차피 같이 재검토된다.**

### 3. 노트북은 SSH 터널로 붙는다 — Redis 포트를 열지 않는다

> **보안**: Lightsail의 Redis에는 **로그인 리프레시 토큰이 들어 있다**(ADR-0005). 이 포트를
> 인터넷에 노출하면 전 사용자 세션 탈취 경로가 된다. `127.0.0.1` 바인딩을 유지한다.

노트북이 `ssh -L 6379:127.0.0.1:6379 …`로 터널을 열고 자기 로컬 포트로 붙는다.

- **노트북이 아웃바운드만 한다** — NAT·공인 IP 문제가 그대로 해결된다.
- **Redis 설정을 한 글자도 안 바꾼다** — 바인딩·포트·인증 전부 현행 유지.
- **자격증명이 이미 있다** — 팀의 Lightsail SSH 접근(`docs/context/deployment.md`). 새 시크릿이 없다.
- **워커가 죽으면 터널도 죽는다** — "워커 살아 있음"과 "연결 살아 있음"이 같은 상태가 된다.

부결: Redis에 비밀번호+TLS를 걸고 포트를 여는 안(사고 반경이 리프레시 토큰까지), 큐 전용 Redis를
따로 띄워 그것만 여는 안(어차피 공개 포트고 컨테이너·인증을 새로 관리해야 한다).

**터널 끊김에 "완벽한" 해법은 없다.** 노트북 + 가정용 네트워크는 본질적으로 불안정하고, 진짜 완벽은
클라우드 GPU나 외부 API(원래 139가 향하던 방향)뿐이며 둘 다 돈이 든다. 세 겹으로 **사용자에게 안 보이게**만
한다: ①`autossh`/launchd `KeepAlive` 자동 재연결 ②큐가 버퍼 ③아래 결정 4의 처리중 리스트.

### 4. 작업 유실은 `BLMOVE` + 처리중 리스트로 막는다

`BRPOP`은 꺼내는 순간 큐에서 사라진다. 워커가 3장 중 2장 만들다 노트북이 잠자기로 들어가면
**작업이 증발하고 배치는 `PENDING`에 영원히 남는다.**

- 워커는 `BLMOVE`로 **대기열 → 처리중 리스트**로 원자적으로 옮겨 가져간다.
- 완료하면 처리중 리스트에서 제거한다.
- 죽으면 처리중에 남아 있으므로 **재투입할 수 있다.**
- 스위퍼가 `PENDING`이 **10분**(잠정)을 넘으면 재투입하거나 `FAILED`로 내린다.

**10분은 추측이다.** 로컬 모델의 3장 생성 시간이 실측된 적이 없다(138은 외부 provider용이라 무의미해졌다).
**첫 실측 후 조정한다.**

부결: `BRPOP` + 타임아웃 스위퍼만 두는 안 — 우리 노트북이 잠든 게 원인인데 사용자가 다시 눌러야 한다.

### 5. 워커는 자격증명을 갖지 않는다 — presigned URL을 메시지에 담는다

```
요청 큐   { jobId, placementId,
           sourceImageUrl      presigned GET — 스크린샷(thumbnail_key)
           uploadTargets[3]    { key, url }  presigned PUT
           timeOfDay           DAY | NIGHT }

결과 큐   { jobId, placementId, status: OK | FAILED, keys[3] | errorMessage }
```

- **개인 노트북에 장기 AWS 자격증명을 두지 않는다.** 분실·유출 시 S3 전체가 열리고 회수 수단도 마땅치 않다.
- **인프라가 이미 있다** — `S3PresignService`가 PUT·GET presign을 둘 다 만든다.
- **유출돼도 시한부다** — URL 하나가 새도 그 객체 하나, 그 시간까지다.
- 완료 알림도 **결과 큐**로 받는다. 워커는 Redis만 알면 되고(터널로 이미 붙어 있다) HTTP 콜백용
  토큰을 새로 만들 필요가 없다.

**고쳐야 할 값**: `S3PresignService.UPLOAD_URL_TTL`이 **5분**이다. 3장 생성이 5분을 넘기면 URL이
만료돼 업로드가 통째로 실패한다. **작업용 presign은 별도 TTL(잠정 30분)로 분리한다** — 이것도
실측 후 조정 대상이다.

부결: 워커에 AWS 키를 주는 안. 그리고 이미지 바이트를 Redis로 되돌리는 안 — Redis는 메모리 저장소고
**리프레시 토큰과 같은 인스턴스**라 이미지 3장이 세션 저장소의 메모리를 먹는다.

### 6. 상상도는 3장 고정. 각도 컬럼을 만들지 않는다

한 업로드가 `generated_image`에 **3행**을 만든다. 각도가 다르고 `time_of_day`는 셋 다 같다.

- **각도를 구분하는 컬럼을 두지 않는다.** 로컬 모델이 `SIDE`라고 라벨된 것을 정말 측면으로 그렸는지
  검증할 방법이 없다 — **미검증 값이 사실처럼 굳는다.** `erd.md` 전역 규칙이 규격 서브타입 boolean에
  기본값을 금지한 것과 같은 부류의 함정이다. 순서는 `created_at`이 답한다.
- **피드 대표 1장은 `generated_image.is_primary`**다 + 부분 유니크 `WHERE is_primary`.
  `product_image.is_primary`(ADR-0011 결정 6)·`post_image.is_primary`(ADR-0013 결정 5)의 **세 번째
  적용이지 새 결정이 아니다.** 서버가 첫 장을 자동 지정하고, 사용자는 나중에 바꿀 수 있다.
- 대가: 피드 목록이 `placement ⋈ generated_image` 조인이 된다. 부분 유니크 인덱스가 사실상 그 조인의
  인덱스 역할을 한다. 대안이던 `placement.feed_image_key` 비정규화는 정본을 둘로 만들어 부결했다
  (ADR-0013 결정 2가 `post_placement` 정션을 버린 것과 같은 논리).

### 7. 이미지는 두 종류다 — 스크린샷과 상상도는 다른 것

| | `placement.thumbnail_key` | `generated_image` |
|---|---|---|
| 무엇 | 시뮬레이터 캔버스 **스크린샷** | AI **상상도** 3장 |
| 언제 | 배치를 **저장**할 때 | 배치를 **업로드**할 때 |
| 어디에 | 내 작업실(`/craft`) 카드 | 데스크 피드 카드(`is_primary` 1장) + 상세 3장 |

**스크린샷은 상상도 생성의 입력이기도 하다.** image-to-image로 돌리면 기하가 보존되므로,
`docs/research/ai-image-provider.md`가 짚은 갈림길("품질 대 기하 보존")에서 보존 쪽 수단이 생긴다.

**따라서 불변식 하나**: **스크린샷이 없으면 업로드할 수 없다.** 워커에 보낼 입력이 없다.
`PUT /placements/{id}/feed-entry`가 이것을 422로 막는다.

### 8. 한도는 "장" 단위, 설정 프로퍼티, 3장 전부 성공했을 때만 기록

- **단위는 장이다.** `generated_image`를 삭제하지 않는 것이 한도 카운트의 근거이고(`erd.md`),
  회차를 묶는 컬럼이 없다. 상한은 **3의 배수**로 표현한다 — 아니면 "1장 남았는데 업로드가 안 된다"는
  설명 불가능한 잔량이 생긴다. 사용자에게는 "오늘 7번 올릴 수 있어요"로 번역해 보여준다.
- **값은 설정 프로퍼티** `app.image.daily-quota`. 초기값 **21**(=7회, 테스트 기준).
  코드 상수는 재배포가 필요하고, 사용자별 DB 테이블은 지금 전원이 같은 값이라 행이 전부 똑같아진다.
- **3장이 전부 성공했을 때만 3행을 한 트랜잭션으로 쓴다.** 부분 실패가 사용자 한도를 깎으면
  **우리 잘못으로 사용자가 손해를 본다.** 이 테이블은 삭제 금지라 사후 정리로 풀 수 없다.
- 초과 응답은 **429** + `ErrorCode` `IMAGE_QUOTA_EXCEEDED`.

**결제 확장을 지금 만들지 않는다.** 대신 나중에 싸게 붙도록 셋만 갖춘다: ⑴ "이 사용자의 오늘 상한"을
답하는 **판단 지점을 코드에 하나만** 둔다(결제가 오면 그 한 곳만 바뀐다) ⑵ `GET /users/me/image-quota`를
지금 판다(REQ-IMG-03의 "초과 시 안내"가 어차피 필요하고, 그 화면이 "충전하기"가 붙을 자리다)
⑶ 429 + 코드 문자열을 고정한다(결제가 붙어도 프론트 분기가 산다). **결제 모델(구독형 vs 크레딧형)은
미정**이다 — 둘은 데이터 모델이 다르지만 위 셋은 어느 쪽이 와도 재사용된다.

### 9. 판정 게이트는 업로드를 누른 순간에 쏜다

ADR-0009 결정 5의 공개 게이트를 **`PRIVATE → PENDING` 전이**에 건다. 위반이면 즉시
`422 PLACEMENT_JUDGMENT_FAILED`이고 **큐에 넣지 않는다.**

- 생성 후에 판정하면 **GPU 3장과 한도를 쓰고 나서 버린다.**
- 기획의 "즉시 업로드됐다는 피드백"을 준 몇 분 뒤에 뒤집게 된다 — "올라갔다더니 안 올라갔네".
- 피드가 서비스의 얼굴이 되면서 ADR-0009의 논거(*"남에게 보이는 배치는 실제로 되는 배치"*)가 더 세졌다.

판정은 현재 `NoOpPlacementJudge` 스텁이라 **당장은 아무도 막지 않는다.** 배선만 지금 만들어 두고,
REQ-CMP 구현이 끝나면 구현체만 갈아끼운다.

ADR-0009 결정 5의 *"이미 공개된 배치에 위반 스냅샷을 보내도 422"*는 그대로 산다.

### 10. API 표면은 단수 하위 리소스 토글 하나다

```
PUT    /placements/{id}/feed-entry   → 202 Accepted
DELETE /placements/{id}/feed-entry   → 204   (publish_status = PRIVATE)
```

- **`{status}`를 본문으로 받지 않는다.** `PUBLIC`·`FAILED`는 서버 전용이라, 받는 값의 부분집합만
  유효한 `PUT`이 되어 계약이 스스로 모순된다.
- **`202`인 이유**: 이 호출이 끝난 시점에 배치는 아직 피드에 없다. 200·204는 "다 됐다"는 뜻이다.
  ADR-0008이 202를 다루지 않으므로 이 ADR이 그 자리를 채운다.
- **재시도가 같은 호출이다.** `PUT`은 멱등이라 `FAILED`에서 다시 부르면 재투입된다.
  별도 재시도 엔드포인트를 만들지 않는다.
- 진행 상태는 `GET /placements/{id}`의 `publishStatus`로 확인한다. 별도 진행 조회 엔드포인트도 없다.

### 11. 이미 `PUBLIC`인 배치를 수정해도 재생성하지 않는다

자동 재생성은 제목 하나만 고쳐도 **한도 3장과 GPU를 태운다** — 사용자가 통제할 수 없는 소모다.
`PUBLIC` 배치의 수정을 금지하는 안도 부결했다(ADR-0009가 저장 게이트를 버린 정신과 정면으로 어긋난다).

**대가**: 피드 카드가 낡을 수 있다. 완화 근거 둘 — ⑴ 리믹스·상세는 **실제 배치 데이터**를 읽으므로
정확하다. 낡는 건 포스터 한 장이다. ⑵ 프론트가 "피드 이미지가 현재 배치와 다릅니다 — 다시
업로드할까요?"를 띄운다.

### 12. 업로드와 무관한 "상상도 미리 보기"는 보류한다

생성 입구를 **업로드 하나로 유지**한다. `POST /placements/{id}/generated-images`를 만들지 않는다.

- 입구가 둘이면 같은 큐에 두 경로가 들어오고, **판정 게이트·상태 전이가 한쪽에만 걸린다**
  (미리 보기는 상태를 안 바꾸므로). 상태 기계가 두 갈래가 된다.
- 21장 한도를 미리 보기로 태우면 정작 업로드를 못 한다.
- 미리 보기의 원래 목적("완성된 모습 확인")은 **실측 스케일 3D 씬이 이미 정확히 한다.** 상상도의
  고유 가치는 남에게 보여줄 실사 포스터이고, 그건 정확히 업로드 시점의 용도다.

**대가**: `docs/REQUIREMENTS.md` 페르소나 시나리오가 바뀐다. *"미리 보고 → 저장 → 구매 결정"*이
*"저장 → 업로드 → 상상도"*가 되고, 상상도가 **구매 결정의 입력에서 공유의 산출물로** 성격이 바뀐다.
REQ-IMG-01도 "1장 생성"에서 "업로드 시 3장 생성"으로 개정된다.

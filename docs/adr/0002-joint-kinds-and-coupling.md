# ADR-0002. 관절 종류 유니온과 커플링 — 회전·직선 관절, 종속 관절, 조작 UX

## 상태

**확정** — 2026-07-25, 승인 박동규.
결정 티켓 DERO-153 관절 리그 확장 설계.

## 맥락

D16(관절 가동)은 리지드 노드 계층 + 한계각 클램프까지 확정하고 구현도 끝냈다. 그런데 그 리그가 **회전 힌지 전용**이다. 타입 이름부터 `RigHinge`였고 매니페스트 필드는 `RigManifest.hinges`, 한계는 `minDeg`/`maxDeg` 한 쌍뿐, 배치 인스턴스가 값을 담는 컬럼은 `placed_item.joint_angles`였다.

D16이 확정한 **관절 제품군 4종**을 실제 제품 기준으로 세어 보면 회전만으로는 안 되는 것이 둘이다.

| 제품군 | 회전으로 안 되는 운동 |
|---|---|
| 폴(pole)형 모니터암 | 기둥을 타고 오르내리는 **높이 슬라이드** |
| 리프트형 노트북 거치대 | 상판이 수직으로 뜨는 **승강** |

직선 운동의 가동값은 **mm**다. 이것을 각도 필드에 담으면 `joint_angles`라는 이름과 "revolute는 도"라는 전제가 동시에 거짓이 되고, 한계 클램프가 무슨 단위를 자르는지 코드에서 알 수 없게 된다.

두 번째 구멍은 **종속 관절**이다. 마이크암 붐의 평행사변형 링크는 붐이 꺾이면 헤드가 반대로 같은 각만큼 돌아 수평을 유지한다. 사용자가 만지는 관절은 하나인데 움직여야 하는 피벗은 둘이다. 지금 모델에는 "이 관절은 저 관절을 따라간다"를 적을 자리가 없다.

세 번째는 **조작 수단**이다. 관절 조작이 하단 패널 슬라이더뿐이라, 화면 속 어느 부위가 어느 슬라이더인지 이름으로 추측해야 했다. 그 이름조차 내부 조인트 id(`elbow-pitch`)가 그대로 노출됐다.

마지막으로 **매니페스트는 손저작 JSON**이다. 등록자가 파트 이름·축·피벗점·한계를 손으로 적어 넣는다. 종류가 둘이 되면 "prismatic인데 `minDeg`를 적었다" 같은 실수가 생기는데, JSON에는 타입이 없어 TypeScript 유니온이 잡아 주지 못한다.

## 결정

### 1. 관절 종류를 판별 유니온으로 확장한다

`RigJoint`는 `revolute`(회전, **도**) / `prismatic`(직선, **mm**) 두 갈래의 판별 유니온이다. 한계 필드는 **종류가 소유한다** — revolute는 `minDeg`/`maxDeg`, prismatic은 `minMm`/`maxMm`이고 서로의 필드를 갖지 않는다.

- **`kind` 생략 = `revolute`.** 다수 쪽을 기본값으로 둬서 기존 매니페스트가 그대로 통과한다. prismatic만 `kind: 'prismatic'`을 명시한다.
- **`label`(한글 표시명)은 필수다.** 조작 UI·gizmo 툴팁이 쓴다. 옵셔널로 두면 안 채운 매니페스트가 반드시 생기고, 그때 화면에 뜨는 것은 내부 id다.
- 한계를 읽는 곳은 `jointLimits()` 한 군데다(`frontend/src/three/core/rig.ts`). 종류 분기를 호출부마다 복사하면 한 곳만 고치는 날 클램프가 갈린다.

### 2. 종속 관절은 커플링으로 표현하고, 값을 저장하지 않는다

`coupledTo: { joint, ratio, offset? }` — "나는 `joint`를 따라간다".

- **종속값 = `driver × ratio + offset`, 계산 후 자기 한계로 재클램프.** 재클램프는 ratio 오입력이 파트를 뒤집는 것을 막는 안전장치다(driver 30 × ratio -10 = -300이 자기 한계 -45로 잘린다).
- **저장하는 것은 driver 값뿐이다.** 종속값은 로드 시 재계산한다 — 저장하면 ratio를 고친 날 두 값이 어긋나고, 어긋난 쪽이 렌더를 지배한다.
- **커플링 체인 금지.** driver가 스스로 종속이면 매니페스트 검증에서 반려한다. 재계산이 "driver 전부 → 종속 전부" 2패스라 체인은 조용히 한 단계 뒤처진 값을 만든다. 위상 정렬을 도입할 만큼 실제 제품에 체인이 흔하지 않다.
- **사용자가 만지는 것은 driver뿐이다.** 종속 관절은 슬라이더에도 gizmo에도 뜨지 않고, 엔진의 `articulate`에 종속 관절 id를 주면 `null`을 돌려준다.
- 로드 경로(`resolveJointValues`)와 조작 경로(`scene.articulate`)가 **같은 산술 함수**(`coupledValue`)를 공유한다. 두 곳에 복사하면 한쪽만 고치는 날 저장된 포즈와 조작 중 포즈가 갈린다.

### 3. `placed_item.joint_angles` → `joint_values` 개명

prismatic 값이 mm라 `_angles`는 거짓 이름이다. 컬럼 하나에 두 단위가 섞이되, **어느 단위인지는 매니페스트의 `kind`가 정한다** — 값 옆에 단위를 적지 않는다(정본이 둘이 된다).

키는 매니페스트의 관절 키, 값은 JSON number. 스키마 정본은 `docs/context/erd.md` `placed_item` 절이다.

### 4. 사람이 쓰는 단위는 도·mm, 미터 환산은 런타임이 한다

- 매니페스트·DB·UI에 적히는 prismatic 값은 **mm**다. 전역 규격 단위가 mm이므로 저작자가 mm로 적고, 런타임이 `/1000`으로 GLB 미터 좌표계에 맞춘다.
- **prismatic 이동은 정지 포즈 위치(`restPos`) 기준 절대 이동이다.** 현재 위치에 더하는 누적 가산으로 만들면 슬라이더를 왕복할 때마다 파트가 흘러간다.
- 슬라이더는 내부 id가 아니라 `label`을 보여주고 값 뒤에 **종류별 단위**(`°` / `mm`)를 붙인다. 관절 종류가 둘인데 표기가 하나면 사용자가 120이 각도인지 mm인지 알 수 없다.

### 5. 조작은 gizmo + 슬라이더 병존, 값의 정본은 엔진 하나

**3D 드래그 gizmo**를 얹되 슬라이더를 없애지 않는다. gizmo는 "어느 관절이 화면 어디인가"를, 슬라이더는 정밀 입력과 가동 범위 표시를 맡는다.

- **상호작용 우선순위** — 선택 상태에서 마우스다운이 gizmo를 먼저 맞히면 관절 드래그, 아니면 배치 이동. gizmo 히트 판정은 **선택된 아이템에만** 적용한다.
- **드래그 중에는 카메라 오빗과 배치 이동을 잠근다.** 관절을 끄는 동안 카메라가 같이 돌면 드래그 기준 벡터가 매 프레임 달라진다.
- 제스처는 라이브러리 드래그 / 아이템 이동 / 오빗 / 관절 드래그를 **한 상태머신**으로 다룬다. 리스너를 쌍쌍이 늘리면 서로의 이벤트를 훔친다.
- **값의 정본은 엔진이고 UI는 파생이다.** 입력 경로가 둘(gizmo·슬라이더)이므로 어느 쪽으로 바꾸든 다른 쪽이 같은 값을 봐야 한다 — 슬라이더에 로컬 표시 상태를 두면 gizmo 드래그가 슬라이더에 반영되지 않는다. 선택·복제·이동·정지 포즈 복귀도 전부 하나의 선택 경로를 태워 gizmo 핸들과 실제 선택이 어긋나지 않게 한다.

### 6. 관절 구성은 실물 제품 기준으로 잡는다 — 관절을 가짜로 만들지 않는다

매니페스트의 관절 목록은 **그 제품이 실제로 움직이는 곳**과 일치해야 한다. 형상이 그럴듯하다고 관절을 넣지 않고, 카탈로그가 표기했다고 없는 관절을 만들지도 않는다. D16의 "파트 식별·관절 도출이 불가한 제품은 관절 없는 정적 에셋으로 등록한다"의 연장이다.

양방향으로 한 번씩 어긋났고 둘 다 실물 기준으로 맞췄다:

| 사례 | 어긋난 방향 | 조치 |
|---|---|---|
| 모니터암 head-pivot | 카탈로그가 `arm.pivot_range_deg`로 피벗을 표기하는데 매니페스트에 세로 회전 관절이 없어 화면에서 돌지 않았다 | 관절 추가 |
| 모니터암 shoulder-pitch | 실제 제품에 맨 아래 각도 조절이 없는데 매니페스트에만 있었다 | 관절 제거 |

카탈로그 표기 컬럼(`arm`의 각도 컬럼들)은 **표기·필터 전용**이고 가동 범위의 런타임 정본은 언제나 `asset.rig_manifest`다. 둘이 어긋나면 고칠 쪽은 실물을 보고 정한다.

### 7. gizmo는 축별 저채도 색으로 그리고, 판정 시맨틱 색과 겹치지 않게 한다

- 축은 매니페스트 로컬 축의 지배 성분(`dominantAxis`)으로 판정해 **X=코랄 · Y=민트 · Z=라벤더**로 칠한다.
- **채도를 낮춘다.** 3D 캔버스는 뉴트럴 그레이 유지가 원칙이고(DESIGN-SYSTEM §1.5), 충돌 빨강·경계 주황 같은 **판정 시맨틱 색과 색이 겹치면 조작 핸들이 경고로 읽힌다**. 코랄을 특히 낮게 잡은 이유다.
- 호버 시 굵기·불투명도·발광을 올리고, 드래그 중에는 가동 범위 호(회전)와 현재값 라벨을 띄운다.
- **prismatic 핸들은 고정 트랙 + 트랙 위를 이동하는 화살촉이다.** 핸들 전체가 파트와 함께 미끄러지면 어디까지 갈 수 있는지가 화면에서 사라진다.
- gizmo는 상수색 오버레이라 postfx 노출 역보상(`CAMERA_EXPOSURE` 1/20)이 필수다 — 없으면 물리 단위 수백의 씬에 묻혀 보이지 않는다(`frontend/src/three/CLAUDE.md` 지속 이슈).

### 8. 매니페스트는 기계 검증을 통과해야 등록한다

손저작 JSON은 타입이 오지 않으므로 `validateManifest()`(`frontend/src/three/core/rig.ts`)가 등록 검수 게이트다. 반환값이 빈 배열이면 통과, 위반은 한 줄씩 돌려준다(관절 검사는 관절 id를, 세그먼트 검사는 노드 이름을 박는다).

#### 8-1. 관절 종류별 필수·금지 필드 (검증 게이트의 정본)

| 종류 | `kind` 표기 | 필수 필드 | **금지** 필드 | 값 단위 |
|---|---|---|---|---|
| **revolute** | 생략 또는 `'revolute'` | `minDeg`·`maxDeg` (둘 다 number) | `minMm`·`maxMm` (undefined여야 함) | 도 |
| **prismatic** | `'prismatic'` **명시 필수** | `minMm`·`maxMm` (둘 다 number) | `minDeg`·`maxDeg` (undefined여야 함) | mm |

금지 필드는 타입이 아니라 **값의 존재 여부로 실제로 들여다본다** — 손저작 JSON에는 여분 필드가 그냥 실려 오기 때문이다.

종류와 무관한 공통 검사:

| 검사 | 규칙 |
|---|---|
| 관절 id | 매니페스트 안에서 유일 |
| `label` | 비어 있지 않을 것(공백만도 불가) |
| `parent`·`child` | `segments`에 정의된 세그먼트 키일 것 |
| `axis` | 단위 벡터(길이 허용 오차 1e-3) |
| `segments` | 같은 GLB 노드 이름이 두 세그먼트에 속하지 않을 것 |
| 한계 범위 | `min < max` |
| 정지 포즈 | `0`이 `[min, max]` 안에 있을 것 |
| `coupledTo.joint` | 자기 자신이 아닐 것 · 존재하는 관절일 것 · **그 관절이 스스로 종속이 아닐 것**(체인 금지) |
| `coupledTo.ratio` | 유한수 |

#### 8-2. 제품군별 전형 관절 구성 (저작 참조표)

저작자가 "이 제품엔 관절을 뭘 넣지?"에 답하는 표다. **전형이지 필수가 아니다** — 실물에 없는 관절은 뺀다(결정 6).

| 제품 | `spec_type` | 전형 관절 구성 | 종류 | 가동값 정본 | 카탈로그 표기 컬럼 |
|---|---|---|---|---|---|
| 모니터암 | `ARM` | base-yaw · shoulder-pitch · elbow-pitch · head-tilt · head-swivel · head-pivot | 전부 revolute | `rig_manifest` | `arm.tilt_*`·`swivel_range_deg`·`pivot_range_deg`·`segment_count` |
| 마이크암 | `ARM` | base-yaw · boom-pitch · boom-parallel | revolute, boom-parallel은 **커플링** | `rig_manifest` | `arm.tilt_*` 등(피벗 없음) |
| 노트북 거치대 | `PROP` | lift · tilt | lift = **prismatic**, tilt = revolute | `rig_manifest` | 없음(`prop`에 각도 컬럼 미추가, D19) |
| 휴대폰 거치대 | `PROP` | ball(yaw + pitch 스택) | 전부 revolute | `rig_manifest` | 없음 |

- 폴형 모니터암의 기둥 높이 슬라이드도 **prismatic**이다.
- 한 피벗에 관절 둘을 쌓을 수 있다(볼조인트의 yaw+pitch, 모니터암의 head-swivel+head-pivot). 부모 판정은 "같은 자식 세그먼트를 구동하는 직전 관절"이 받는다.

## 대안과 버린 이유

**관절을 각도 단일 타입으로 유지하고 직선 운동을 각도로 흉내낸다.** 높이 슬라이드를 각도로 적으면 저장값의 단위가 거짓이 되고(컬럼 이름이 `joint_angles`), 클램프가 자르는 것이 무엇인지 코드에서 사라진다. mm는 규격 DB의 전역 단위라 흉내낼 대상도 아니다.

**한계를 종류 무관한 `min`/`max` 한 쌍으로 둔다.** 필드 이름이 단위를 말하지 않으면 손저작 JSON의 단위 혼동을 **기계가 잡을 수 없다**. `minDeg`/`minMm`로 갈라 두었기에 "prismatic인데 minDeg를 적었다"가 검증 게이트에서 한 줄 오류로 떨어진다(결정 8-1).

**종속 관절 값도 함께 저장한다.** ratio를 고친 날 저장된 종속값과 재계산값이 어긋나고, 어긋난 쪽이 렌더를 지배한다. 저장하지 않으면 정본이 하나다.

**커플링 체인을 허용한다.** 재계산이 driver 전부 → 종속 전부의 2패스라 체인은 조용히 한 단계 뒤처진 포즈를 만든다. 제대로 하려면 위상 정렬 + 순환 검출이 붙는데, 실제 제품에서 체인이 필요한 사례를 못 찾았다. 필요해지면 검증 게이트의 금지 한 줄을 푸는 것부터 시작한다.

**`label`을 옵셔널로 둔다.** 옵셔널이면 안 채운 매니페스트가 반드시 생기고, 그때 화면에 뜨는 것은 내부 조인트 id다. 필수로 두면 검증 게이트가 등록 시점에 잡는다.

**gizmo 없이 슬라이더만 둔다.** 슬라이더는 관절을 이름으로만 지목해, 화면 속 어느 부위가 움직일지 눌러 보기 전에는 알 수 없다. 반대로 **gizmo만 두고 슬라이더를 걷는 안**도 버렸다 — 정밀 값 입력과 가동 범위 표시를 gizmo가 대신하지 못한다.

**슬라이더에 로컬 표시 상태를 둔다.** 실제로 그렇게 짰다가 코드리뷰에서 지적돼 걷어냈다 — 마운트 후 gizmo 드래그·`articulate` 갱신이 슬라이더에 반영되지 않았다. 입력 경로가 둘이면 표시 상태를 복제하는 순간 둘이 갈린다.

**gizmo를 판정 시맨틱 색(충돌 빨강·경계 주황)과 같은 팔레트로 칠한다.** 조작 핸들이 경고로 읽힌다. 축 색은 저채도 코랄·민트·라벤더로 분리했다.

**감수하는 것:**
- `RigManifest.hinges` → `joints` 개명과 `label` 필수화는 **파괴적 변경**이다. 기존 매니페스트 JSON은 그대로 통과하지 않는다. 현재 리그 에셋이 모니터암 하나뿐이라 지금이 비용이 가장 싼 시점이었다.
- gizmo 핸들은 선택 아이템에 대해 매 프레임 재동기화한다. 프레임당 할당이 0이 되도록 스크래치 버퍼를 쓰고 있으나, 관절 수가 크게 늘면 다시 측정해야 한다.

**후속 과제:**
- **prismatic·커플링을 쓰는 제품이 아직 하나도 없다.** 두 기능은 유닛 테스트로만 고정돼 있고, 실 에셋 검증은 폴형 암·리프트형 거치대·마이크암을 등록하는 날 처음 이뤄진다.
- 매니페스트 저작 도구(`/dev/rig`) — `gizmoMath`는 조작과 저작이 공유하도록 three 비의존 순수 모듈로 떼어 뒀지만 저작 화면은 아직 없다. 지금은 축·피벗점을 손으로 적는다.
- `validateManifest()`는 프론트 함수다. 등록 API가 생기면 같은 규칙을 서버가 강제해야 한다(erd.md는 키 유효성·클램프를 WAS 소관으로 적어 두었다).

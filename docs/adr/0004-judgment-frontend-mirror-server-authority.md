# ADR-0004. 호환성 판정의 위치 — 프론트는 미러, 서버가 정본

## 상태

**확정** — 2026-07-26, 승인 박동규.
결정 티켓 DERO-152 호환성 판정 위치 결정.

## 맥락

REQ-CMP 판정을 서버가 맡는지 클라이언트가 맡는지가 정해지지 않은 채로, **두 정본 문서가 서로 다른 답을 적어 두고 있었다.**

| 문서 | 적힌 것 | 읽히는 답 |
|---|---|---|
| `docs/context/3d-scene.md` 배치·충돌 항 | "호환성 판정(규격 DB 전용, `collision.ts`, D7/D8)과 배치 시 공간 겹침 피드백(`collider.ts`)을 분리" | 판정은 프론트 모듈 소관 |
| `docs/context/compatibility.md` 확정 규칙 | 클램프 물림 두께는 "저장 컬럼이 아니라 **WAS 파생값**" | 판정 산술은 서버 소관 |

둘 다 자기 자리에서는 맞는 말이라 어느 쪽도 틀렸다고 지울 수 없었다. 요구가 실제로 둘이기 때문이다.

**실시간 0ms.** 드래그 근접 판정은 포인터가 움직이는 동안 후보를 갈아 치우며 돈다 — FIT이면 자석이 발동하고, INCOMPATIBLE이면 근접 **즉시** 수치 사유 배너가 뜬다(자석 결합 UX). 판정 한 번에 네트워크 왕복이 끼면 자석이 손보다 늦게 붙고, 배너는 이미 지나간 위치를 설명한다.

**저장 무결성.** 반대로 저장·공유·템플릿 복사는 클라이언트가 보낸 판정 결과를 믿을 수 없다. 브라우저에서 도는 판정은 조작 가능하고, 조작된 배치가 통과하면 "구매 전 검증"이라는 서비스 전제 자체가 무너진다. 남이 만든 배치를 복사해 오는 경로에서는 애초에 그 배치를 판정한 프론트가 어떤 버전이었는지도 알 수 없다.

한쪽만 고르면 반드시 다른 하나를 잃는다.

## 결정

### 1. 역할을 넷으로 쪼갠다 — 프론트=미러, 서버=정본

| 역할 | 누가 | 언제 |
|---|---|---|
| 즉답 판정 (드래그 근접·아이템 추가) | 프론트 TS (`collision.ts` 계열 **순수 함수**) | 실시간 0ms |
| **확정 판정 (정본)** | WAS — 저장 시점 배치 **전체 재판정**, 위반 시 **저장 거부** | 저장·공유·템플릿 복사 |
| 대안 제시 (REQ-CMP-06) | **서버 전용** (카탈로그 SQL) | "불가" 배너의 "대안 보기" 클릭 시 |
| 판정 결과 저장 | **안 함** — 매번 재계산 | — |

프론트 판정은 **서버 판정의 미러**다. 화면을 즉시 되받아치기 위해 같은 규칙을 클라이언트에도 한 벌 두는 것이지, 그 결과가 무엇을 확정하지는 않는다. 저장 버튼을 누른 순간 WAS가 배치 전체를 규격 DB로 다시 판정하고, 위반이 있으면 거부한다 — **프론트가 뭐라고 보냈든 읽지 않는다.**

- 저장 시점 재판정은 **배치 전체**다. 마지막에 만진 아이템만 보면, 책상 규격을 나중에 바꿔 놓은 배치가 통과한다.
- 대안 제시는 미러를 두지 않는다. "같은 카테고리에서 조건을 만족하는 제품"은 카탈로그 전량을 훑는 질의라 클라이언트에 규격 DB를 통째로 내려야 성립한다. 서버 한 곳에 둔다.

### 2. 판정 결과는 저장하지 않는다

`judgment_result`는 화면에 내는 값이고, 어느 테이블의 컬럼도 아니다. ERD에 판정 결과 컬럼이 없는 현 상태를 **그대로 유지한다.**

규격 원본(`arm.clamp_min_mm`, `desk.edge_thickness_mm` 등)이 정본이고 판정은 그 파생값이다. 파생값을 굳혀 두면 원본을 고친 날 저장값이 조용히 어긋나고, 어긋난 쪽이 화면을 지배한다 — `compatibility.md`가 클램프 물림 두께를 컬럼으로 만들지 않은 것과 같은 논리다.

### 3. 드리프트는 공유 fixture 계약 테스트로 막는다

같은 규칙이 두 언어에 있으면 언젠가 갈린다. 한쪽이 조건부 경계를 고치고 다른 쪽이 안 고치면, 화면은 "적합"인데 저장은 거부되는 상태가 된다.

**입력 규격 → 기대 판정 JSON 한 벌**을 두고 TS(vitest)와 Java(JUnit) **양쪽이 같은 파일을 소비한다.** 한쪽만 고치면 다른 쪽 테스트가 그날 깨진다.

- fixture에는 판정 3종(암↔책상·모니터↔암·소품↔책상)의 정상 케이스와 **경계·결측 케이스**를 함께 담는다 — 물림 규격 NULL의 조건부 처리, `is_clamp_mountable = false`의 "판정 행 없음" 같은 것이 정확히 갈리기 쉬운 자리다.
- **판정 규칙 문서의 정본은 여전히 `docs/context/compatibility.md`다.** fixture는 그 문서를 기계가 읽을 수 있게 옮겨 적은 것이고, 규칙이 바뀌면 문서 → fixture → 양쪽 구현 순으로 내려간다.
- Java 쪽은 백엔드 착수 후(Phase 3)에 붙는다. 그때까지 fixture는 TS 단독으로 돌지만, **처음부터 언어 중립 JSON으로 둔다** — 나중에 옮기려면 프론트 테스트 코드에서 규칙을 다시 발굴해야 한다.

### 4. 선례 — 같은 패턴을 이미 한 번 적었다

ADR-0002 파급 절의 "`validateManifest()`는 프론트 함수다. 등록 API가 생기면 같은 규칙을 서버가 강제해야 한다"와 같은 구도다. 프론트 함수가 먼저 서고 서버가 나중에 같은 규칙을 강제하는 것은 이 프로젝트에서 두 번째다.

## 대안과 버린 이유

**서버 단독 판정.** 정본이 하나뿐이라 드리프트 걱정이 없고 fixture 계약 테스트도 필요 없다. 버린 이유는 드래그 중 근접 판정이다 — 포인터가 움직이는 동안 매번 왕복하면 자석이 손을 따라오지 못하고, INCOMPATIBLE 배너가 이미 지나간 위치를 설명한다. 실시간 0ms를 왕복으로는 만들 수 없다.

**프론트 단독 정본.** 즉답은 완벽하고 서버 판정 코드가 아예 필요 없다. 버린 이유는 무결성이다 — 브라우저에서 도는 판정은 조작 가능하고, 저장·공유·템플릿 복사 어느 경로에도 걸러 낼 지점이 남지 않는다. "구매 전 검증"을 파는 서비스에서 검증을 클라이언트에만 두면 검증이 아니다.

**판정 결과를 DB에 저장한다.** 재판정 비용이 사라지고 목록 화면에서 판정 배지를 질의 한 번에 그릴 수 있다. 버린 이유는 규격 원본을 고친 날 저장값이 **조용히** 어긋나기 때문이다 — 틀린 값이 오류를 내지 않고 그냥 화면에 뜬다. ERD에도 컬럼이 없고, `compatibility.md`가 클램프 물림 두께를 "파생값을 DB에 굳히면 원본을 고친 날 조용히 어긋난다"며 컬럼화를 거부한 것과 같은 판단이다.

**이 ADR이 정본 노릇을 하는 인용 지점** — 아래 문서들이 이 파일을 가리킨다.

| 문서 | 인용 지점 | 가리키는 결정 |
|---|---|---|
| `docs/context/compatibility.md` | "판정 위치" 절 | 1·2·3 |
| `docs/context/3d-scene.md` | 배치·충돌 "2계층 분리" 항 | 1 (`collision.ts`는 미러) |
| `docs/context/architecture-map.md` | 결정 기록 -152 행 | 전체 |

**바뀌지 않는 것:** D7 메쉬-규격 분리(판정 입력은 규격 DB mm뿐, 3D 메쉬 치수 참조 금지) · D8 판정 스코프 · `compatibility.md`의 판정 규칙 전량(3종·3단계·클램프 물림 두께 D21·결측 방어) · ERD(판정 결과 컬럼 없음 그대로, 동결 유지) · 공간 겹침 피드백은 `collider.ts` 소관이고 호환성 판정이 아니라는 경계.

**후속 과제:**
- **프론트 `ProductSpec` 판정 필드 확장** — 현 카탈로그(`frontend/src/three/scene/product.ts`)에 판정 입력이 거의 없다. `edgeThicknessMm`, `isClampMountable`·`clampMinMm`·`clampMaxMm`, 암 허용 하중을 채운다. Phase 1.
- **`vesa` 단일 문자열 → 배열.** 현행 `vesa: '100x100'`은 한 제품이 규격 하나만 지원한다는 뜻이 되는데, ERD는 `product_vesa` 정션으로 다대다를 전제한다. 지금 모양은 스키마가 금지한 거짓말이다. Phase 1.
- **fixture 계약 테스트 TS 쪽** — Phase 1에서 판정 ①·② 순수 함수와 한 세트로 선다.
- **서버 정본 재판정(저장 게이트)·대안 제시 API·Java 쪽 계약 테스트** — Phase 3(백엔드 착수 후). 그때까지 저장 게이트는 프론트 `trySave()`의 충돌·경계 검사만 있고 규격 판정 게이트는 없다.

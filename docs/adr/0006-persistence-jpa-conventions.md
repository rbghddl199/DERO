## 상태

**확정** — 2026-07-27, 승인 박동규.
결정 티켓 DERO-133 (에픽 DERO-125). 설계 맵: `docs/context/architecture-map.md`.
**부분 개정**: 결정 6의 Java 시각 타입은 `Instant` → `OffsetDateTime`으로 [ADR-0008](0008-api-response-contract.md)이 개정했다. 나머지 결정은 그대로 유효하다.

- soft delete 11테이블 + 부분 유니크 인덱스(`WHERE deleted_at IS NULL`).
- `CHECK` 제약을 쓰지 않는다 — 값 검증과 서브타입 정합성은 전부 WAS 소관.
- 시각은 전부 `TIMESTAMPTZ` UTC 저장. PK는 `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- `user`는 SQL 예약어.

## 결정

### 1. 정본 영속성은 JPA(Hibernate) 단독

MyBatis·jOOQ를 쓰지 않는다. 이 둘을 정본으로 두면 엔티티가 매핑 결과물이 되어 ADR-0001의 깊은 엔티티가 무너진다. jOOQ의 장점인 "스키마에서 타입 생성"은 스키마가 자주 바뀔 때 값이 나오는데, 여기 스키마는 **동결**이라 그 값이 안 난다.

### 2. QueryDSL은 지금 넣지 않는다

> **이 결정은 2026-08-01 [ADR-0018](0018-query-convention-entity-first-querydsl.md)로 대체됐다.**
> **QueryDSL을 채택한다** — 동적 조건 조합·타입 안전이 필요하면 바로 쓰고, 조건 개수를 세지 않는다. 아래 도입 트리거의 **"남은 개발 기간이 1주 미만이면 `Specification`" 조건은 삭제됐다** (그 조건의 전제였던 기간 제약이 무효가 됐다). 계단도 개정됐다 — 파생 쿼리 → 정적이면 `@Query` + `join fetch` → **동적 조건이면 QueryDSL**이고, 조회 기본은 프로젝션이 아니라 **엔티티 + 명시적 `join fetch`**다. **이 결정을 읽고 QueryDSL을 미루지 마라.** 아래 본문은 그때의 근거로 남긴다.

조회는 **계단**으로 오른다.

| 단 | 쓰는 자리 | 다음 단으로 가는 순간 |
|---|---|---|
| 파생 쿼리 (`findByXAndY`) | 조건 2개 이하, 연관 안 건드림 | **메서드 이름에 조건이 3개 이상 들어가는 순간** |
| `@EntityGraph` | 연관을 함께 로드해야 할 때 | 프로젝션·집계가 필요할 때 |
| `@Query` (JPQL) | 조인·프로젝션·집계 | 아래 도입 트리거 |

이름 길이로 자르는 이유: `findByCategoryIdAndStatusAndSourceAndDeletedAtIsNullOrderByCreatedAtDesc`는 읽는 비용이 JPQL보다 크다. 세는 기준이 눈에 보여 리뷰에서 논쟁이 안 난다.

**도입 트리거** — 같은 리소스 조회의 `@Query`가 조건 조합 때문에 **3개 이상으로 갈라지는 순간**. 단 그 시점에 **남은 개발 기간이 1주 미만이면 QueryDSL 대신 `Specification`**을 쓴다. QueryDSL 도입은 의존성 추가로 끝나지 않는다 — Q클래스 생성 태스크·gitignore·IDE 인식·그리고 **Hibernate 7.4 호환 스파이크**까지가 한 묶음이라, 막판에 시작하면 실패했을 때 되돌릴 시간이 없다.

### 3. JSONB는 도메인 레코드로 매핑한다

`@JdbcTypeCode(SqlTypes.JSON)` + 레코드. **hypersistence-utils를 쓰지 않는다** — Hibernate 7.4.1이 `Jackson3JsonFormatMapper`를 내장하고 `JacksonIntegration`·`StrategySelectorBuilder`가 자동 감지하므로 Jackson 3에서 그대로 돈다. (2025-12에 보고된 "Jackson 3에 FormatMapper 없음" 문제는 7.4.1에서 해결됐다.)

- **`spring.jackson.use-jackson2-defaults`를 켜지 않는다.** Jackson 3은 `FAIL_ON_UNKNOWN_PROPERTIES` 기본값이 `false`다 — 프론트가 매니페스트에 필드를 추가해도 백엔드가 안 깨진다. 저 스위치를 켜면 그 방어가 사라진다.
- **매니페스트는 부분 갱신하지 않고 통째 교체만 한다.** 레코드에 없는 필드는 역직렬화에서 사라지므로, 읽어서 일부만 고쳐 다시 쓰면 프론트 데이터가 조용히 유실된다.
- `Jackson3JsonFormatMapper`는 **자체 `JsonMapper`를 만든다.** Spring이 구성한 `ObjectMapper`가 JSONB 컬럼에 적용되지 않는다 — 맞춰야 하면 `hibernate.type.json_format_mapper`로 우리 구현을 꽂는다.

### 4. 규격 서브타입 5종은 JOINED 상속, `spec_type` 변경 금지

`@Inheritance(strategy = JOINED)` + `@DiscriminatorColumn(name = "spec_type")`, `Desk extends Product`.

**`spec_type`은 변경할 수 없다.** JPA는 엔티티 타입 변경을 지원하지 않아, 규격 종류를 바꾸려면 `Product` 행을 지우고 새로 만들어야 하고 그 순간 `placed_item`·`cart_item`·`product_like`·`product_vibe`가 전부 끊어진다. 그래서 **REQ-COM-10 자작 제품 수정에서 규격 종류 변경을 막고, 바꾸려면 삭제 후 재등록하도록 사용자에게 명시한다.**

### 5. 감사 정보의 정본은 `product` — 서브타입 감사 컬럼은 매핑하지 않는다

`@MappedSuperclass` 2단으로 쌓는다.

```
BaseEntity                 (created_at, created_by, updated_at, updated_by)   ← 감사 2종 테이블
  └ BaseSoftDeleteEntity   (+ deleted_at)                                     ← 감사 3종 11테이블
       └ Product         @Inheritance(JOINED)
            └ Desk       ← 감사 필드는 product 테이블에 매핑된다
```

Java는 단일 상속이라 `Desk`가 별도 `@MappedSuperclass`를 또 상속할 수 없고, JOINED에서 필드는 선언한 클래스의 테이블로 간다. 따라서 **`desk.created_at`·`desk.updated_at`은 매핑되지 않는다** — `created_at`은 DB 기본값 `now()`가 채우고, `updated_at`은 영원히 NULL로 남는다.

**이 컬럼들은 의도적으로 죽어 있다.** `erd.md` 전역 규칙이 "영원히 NULL인 컬럼이 읽는 사람을 속인다"며 금지한 상태를 알고도 감수한 것이다 — 서브타입 행은 `product`와 생명주기를 공유하므로(`ON DELETE CASCADE`, `deleted_at`도 `product`가 정본) 감사도 `product`가 정본인 게 일관되고, 동결 스키마를 여는 비용보다 싸다.

### 6. 시각 값은 앱이 넣는다 (JPA Auditing)

`@CreatedDate`·`@LastModifiedDate`가 항상 값을 채운다. DB `DEFAULT now()`는 DDL에 남지만 발동하지 않는 안전망이다.

- **Java 타입은 `Instant`. `LocalDateTime` 금지** — `TIMESTAMPTZ` UTC 저장 규칙과 어긋나 타임존이 날아간다.
- **개정(2026-07-27, [ADR-0008](0008-api-response-contract.md) 결정 7): Java 타입은 `OffsetDateTime`이다.** `Instant`도 `TIMESTAMPTZ` 정합은 똑같지만 항상 UTC라 로그·디버깅에서 KST를 암산해야 한다. `OffsetDateTime`은 그 정합을 지키면서 KST 벽시계를 그대로 보여준다. **`LocalDateTime` 금지는 그대로 유효하다** — 바뀐 것은 `Instant` → `OffsetDateTime`뿐이다.
- **`@EnableJpaAuditing`은 메인 애플리케이션 클래스가 아니라 별도 `@Configuration`에 단다** — 메인에 달면 `@WebMvcTest` 슬라이스가 JPA 컨텍스트를 요구하며 깨진다.
- `@CreatedBy`·`@LastModifiedBy`는 쓰지 않는다 — `erd.md`에 대응 컬럼이 없다.

DB를 정본으로 두는 안은 버렸다. `updated_at`은 트리거가 있어야 하는데 이 스키마는 트리거를 안 써서, 결국 `created_at`만 DB·`updated_at`은 앱이 되어 절반만 일관해진다.

### 7. soft delete는 `@SoftDelete`, 단 참조가 살아 있으면 삭제하지 않는다

`@SoftDelete(strategy = SoftDeleteType.TIMESTAMP, columnName = "deleted_at")` — Hibernate 7.4.1 네이티브. `deleted_at IS NULL = 살아있음`이 그대로 맞는다.

자동 필터는 **삭제된 행을 참조하는 연관을 끊는다.** 이 스키마에 그 자리가 실재한다 — `placed_item.product_id` → `product`, `comment.user_id`·`placement.user_id` → `"user"`. 제품을 지우면 그 제품을 쓴 기존 배치가 로드되지 않는다.

그래서 규칙 둘로 막는다:

1. **`product`·`"user"`는 참조가 살아 있는 한 삭제하지 않는다.** 카탈로그에서 내리는 건 `product.status = HIDDEN`이 담당한다(컬럼이 이미 있다). `deleted_at`은 참조가 없는 데이터 정리에만 쓴다.
2. 삭제된 행을 의도적으로 조회해야 하는 화면은 **네이티브 쿼리로 우회**한다 — `@SoftDelete` 필터는 네이티브 SQL에 붙지 않는다.

명시적 방식(리포지토리마다 `...AndDeletedAtIsNull`)을 버린 이유: 11테이블 × 모든 조회에서 한 번이라도 빠뜨리면 삭제된 행이 새는데, 2명 4주에 그건 실제로 일어난다.

> **개정(2026-07-30, [ADR-0012](0012-backend-code-conventions.md) 결정 2): 코드는 `@SoftDelete`를 쓰지 않는다 — 여기서 기각한 명시적 방식으로 구현돼 있다.**
> 실측(2026-07-30): `@SoftDelete` 0건, `global/entity/BaseSoftDeleteEntity`의 수동 `deletedAt` 필드 + 손으로 건 필터 9곳. 그리고 **위 문단이 경고한 일이 실제로 일어났다** — `placement/repository/PlacementRepository.java:32`의 `findForUpdateById`만 필터가 빠져 삭제된 배치에 `PUT`이 200으로 먹는다(같은 서비스의 `get`·`delete`는 404).
> ADR-0012은 이 어긋난 상태를 되돌리지 않고, **필터 위치를 "리포지토리 쿼리에 always" 한 곳으로 모으는 것**만 정했다. `@SoftDelete`로의 복귀는 엔티티 11개 + 기존 쿼리 9곳 동시 마이그레이션이고 위 "삭제된 행을 참조하는 연관이 끊긴다" 문제를 같이 처리해야 해서, **별도 판단·별도 ADR로 남긴다.**
> **이 결정을 읽고 `@SoftDelete`를 새로 붙이지 마라** — 지금 코드베이스와 어긋난다.

### 8. PK 생성은 SEQUENCE 전략 — 테이블별 명시 시퀀스

`@GeneratedValue(strategy = SEQUENCE)` + 엔티티마다 `@SequenceGenerator(sequenceName = "<테이블>_id_seq", allocationSize = 50)`.

DDL은 **명시적 시퀀스**다 — `CREATE SEQUENCE <테이블>_id_seq INCREMENT BY 50;` + `id BIGINT NOT NULL DEFAULT nextval('<테이블>_id_seq')`. `ALTER SEQUENCE ... OWNED BY`로 테이블에 묶어 함께 사라지게 한다(`SERIAL`이 암묵적으로 하는 것과 같다). SEQUENCE 전략을 쓰는 이유는 IDENTITY 전략에서 꺼지는 **JDBC 배치 삽입**이다 — ADR-0009의 배치 저장이 `placed_item` N행을 한 번에 쓴다.

- **`allocationSize`와 시퀀스 `INCREMENT BY`가 정확히 같아야 한다.** 다르면 Hibernate의 풀이 겹쳐 **PK 충돌이 조용히 난다.** 둘 다 50으로 고정한다.
- 시퀀스는 **테이블별**이다. 전역 공유 시퀀스는 `@MappedSuperclass`에 선언 한 번으로 끝나 보일러플레이트가 줄지만, 테이블 간 id 공간이 섞여 디버깅이 나빠진다 — 엔티티당 한 줄이 그보다 싸다.

**2026-07-28 정정 (DERO-201, 승인 박동규)** — 이 결정은 원래 "`erd.md`가 정한 `GENERATED BY DEFAULT AS IDENTITY`를 그대로 쓰면 **`erd.md` 변경 없이** SEQUENCE 전략이 성립한다"였다. **틀렸다.**

Postgres 의미론 설명 자체는 맞다(`BY DEFAULT`는 앱이 명시한 id를 받고, `sequence_options`로 `INCREMENT BY 50`도 준다). 놓친 것은 **identity가 자동 생성한 시퀀스가 `information_schema.sequences`에 나타나지 않는다**는 점이다. Hibernate `PostgreSQLDialect.getQuerySequencesString()`이 시퀀스 검증에 바로 그 뷰를 조회하므로, **아래 9번이 못박은 `ddl-auto: validate`가 `Schema-validation: missing sequence [brand_id_seq]`로 부팅을 죽인다.** 시퀀스는 `pg_class`에 이름·증분까지 정확히 실재하는데도 그렇다(2026-07-28 `postgres:18-alpine` 실측. 명시 `CREATE SEQUENCE`와 `BIGSERIAL`은 정상적으로 보인다).

같은 ADR 안에서 8번과 9번이 충돌하고 있었고, 엔티티 매핑(DERO-201)이 그 충돌을 드러냈다. 해소하며 검토한 대안 2개와 버린 이유:

- **엔티티를 `GenerationType.IDENTITY`로** — 스키마 무변경으로 즉시 통과하지만 이 결정의 유일한 실익인 배치 삽입을 잃는다. DDL의 `INCREMENT BY 50`도 의미를 잃어 행마다 id가 50씩 뛴다.
- **커스텀 `Dialect`로 `getQuerySequencesString()`을 `pg_sequence` 조회로 오버라이드** — 문서·스키마를 안 건드리지만 프레임워크 해킹이 영구히 남고 Hibernate 업그레이드마다 재검증이 필요하다.

`erd.md` 전역 규칙은 승인 후 언락하여 `BIGINT seq`로 개정했다(erd.md "확정 후 개정" 참조).

### 9. Flyway 운용

- **첫 운영 배포 전까지 `V1__baseline.sql` 하나를 고쳐 쓴다**(2026-07-27 실제 파일명으로 정정. 종전 표기 `V1__init.sql`). checksum 불일치가 나면 고민 없이 로컬 DB를 날린다. 운영 DB가 생기는 순간부터 누적(V2+)으로 전환한다. 아직 데이터가 없는데 마이그레이션을 쌓으면 절반이 되돌리기가 되어 읽을 수 없는 이력만 남는다.
- **`spring.jpa.hibernate.ddl-auto = validate`.** Flyway가 만든 스키마와 엔티티 매핑이 어긋나면 부팅이 실패한다 — 28테이블을 손으로 매핑하는데 이 그물이 없으면 어긋남이 런타임까지 간다. `create-drop`·`update`는 **금지**(Flyway와 주인이 둘이 된다).
- **시딩 데이터는 Flyway 밖에 둔다.** 카탈로그 제품은 운영 중에도 계속 늘어나 마이그레이션에 넣으면 제품 하나마다 파일이 생기고, 통합 테스트는 빈 스키마에서 시작해야 격리된다. 8번 결정으로 배치 삽입이 살아났지만 대량 시딩은 여전히 SQL이 빠르다.

### 10. 테스트 하네스

`spring-boot-testcontainers` + `@ServiceConnection`. 공유 `@TestConfiguration`에 `static` 컨테이너(postgres·redis)를 두고 `@Import`로 끌어 쓴다. redis는 ADR-0005의 리프레시 토큰 저장소라 인증 통합 테스트에 필요하다.

- ADR-0001이 정한 `reuse=true`는 **개발자 각자의 `~/.testcontainers.properties`에 `testcontainers.reuse.enable=true`가 있어야** 실제로 재사용된다. 코드가 아니라 로컬 설정이라 온보딩 문서에 넣는다.
- 격리는 층별로 가른다:

  | 층 | 격리 |
  |---|---|
  | 영속성·CRUD 통합 | `@Transactional` 롤백 |
  | **e2e (`RANDOM_PORT`)** | **truncate** |

  e2e에 롤백을 쓸 수 없다 — 진짜 HTTP 요청은 별도 스레드에서 돌아 테스트 트랜잭션 밖이고, 데이터가 남는다. ADR-0001이 **outside-in TDD**를 정했으니 이 경로를 반드시 지난다.
- **검증 전에 `flush()`를 부른다.** 롤백 테스트는 1차 캐시 때문에 실제 SQL이 안 나간 것을 감춘다 — 제약 위반이 테스트에서 안 터지고 운영에서 터진다.

### 11. 조회 기본값

- **모든 `@ManyToOne`·`@OneToOne`에 `fetch = LAZY`를 명시한다.** JPA 기본값이 `EAGER`라 빠뜨리면 조용히 EAGER가 되고, `PlacedItem` → `Product` → `Brand`·`Category`가 목록 조회에서 N+1로 폭발한다.
- **`spring.jpa.open-in-view = false`.** Boot 기본값 `true`는 영속성 컨텍스트를 응답 렌더링까지 열어둬 쿼리가 어디서 나가는지 알 수 없게 만든다. `false`로 두면 서비스 밖 지연 로딩이 예외로 터지는데, 그게 **대가가 아니라 목적**이다.
- **`hibernate.default_batch_fetch_size = 100`.** 지연 로딩 N+1의 대부분이 `IN (...)` 2회 쿼리가 된다.
- **컬렉션 페치와 `Pageable`을 같이 쓰지 않는다.** `@OneToMany`를 페치하면서 페이징하면 Hibernate가 행 전체를 메모리로 읽고 거기서 자른다(`HHH90003004` 경고만 남기고 동작은 한다). 페이징이 필요한 목록은 ID 페이징 후 2차 조회로 채운다.

## 대안과 버린 이유

**① QueryDSL을 지금 도입**
Hibernate 7.4 GA에서 검증된 빌드가 없다(맥락 표). 그 리스크를 감수해서 사는 값이 Should·Could 요구사항(REQ-REC-02·REQ-REC-05)에 몰려 있는데, 이들은 4주 2명에서 잘릴 1순위다. 나중에 넣는 비용도 싸다 — 리포지토리 커스텀 구현체 하나를 더하는 국소 변경이라 구조를 갈아엎지 않는다.

**② `Specification`(JPA Criteria)을 기본 도구로**
의존성 0에 버전 리스크도 0이지만, 선택 조건 2~3개짜리 화면에 쓰기엔 장황하다. **최후 퇴로로만 남긴다**(결정 2의 트리거 참조).

**③ 규격 서브타입을 `@MapsId` 별도 엔티티로**
`spec_type` 변경 시 `product.id`가 살아남고 `Product` 조회에 서브타입이 새어들지 않는다. 다형 호출이 거의 없어(호환성 판정은 `Desk`·`Arm` 구체 타입을 받는다) 실익도 있었다. **`spec_type` 변경을 금지하기로 하면서 JOINED의 유일한 치명타가 사라져** 표준적인 상속 매핑을 골랐다.

**④ JSONB를 `String`으로 통과시키기**
역직렬화가 깨질 일이 없고 4주엔 제일 싸다. 하지만 엔티티가 벙어리가 되어 ADR-0001의 깊은 엔티티와 어긋나고, REQ-COM-09 업로드 검증을 엔티티 메서드로 쓸 길이 막힌다.

**⑤ 서브타입 감사 컬럼을 `erd.md`에서 제거**
죽은 컬럼이 없어져 가장 정직하다. 동결 해제 + 승인 절차를 이 결정 하나 때문에 밟는 값이 안 났다.

**⑥ 전역 공유 시퀀스**
`@MappedSuperclass` 선언 한 번으로 28엔티티가 물려받고 id가 전역 유일해 디버깅이 쉬워진다. PK DDL이 `DEFAULT nextval(...)`이 되어 **동결된 `erd.md` 전역 규칙 변경**이 필요해 버렸다.

## 파급

- `backend/CLAUDE.md` 필수 규칙에 이 ADR의 코드 규칙(LAZY 명시·`Instant`·`spec_type` 불변·계단·`@SequenceGenerator`)을 반영했다.
- **`build.gradle` 변경은 Testcontainers 의존성뿐이다** — QueryDSL 미도입이라 Q클래스 생성 파이프라인이 없다.
- **`application.yml` 값 셋이 확정됐다** — `spring.jpa.hibernate.ddl-auto: validate` · `spring.jpa.open-in-view: false` · `spring.jpa.properties.hibernate.default_batch_fetch_size: 100`. 파일 작성은 환경 분리 결정이 티켓으로 졸업할 때 함께 한다.
- **V1 DDL에 `(INCREMENT BY 50)`이 들어간다** — `erd.md` 본문 변경은 아니지만 파생 규칙이라 마이그레이션 작성 시 빠뜨리면 PK가 충돌한다.
- **`@Table(name = "\"user\"")`** — `user`는 SQL 예약어라 인용이 필수다.
- 명명 전략은 **Boot 기본값을 유지**한다 — `CamelCaseToUnderscoresNamingStrategy`가 `erd.md`의 snake_case와 이미 일치한다.
- REQ-COM-10 자작 제품 수정 화면은 **규격 종류(`spec_type`) 변경 UI를 두지 않는다**(결정 4). 프론트·기획에 전달이 필요하다.
- [DERO-134 패키지 구조 결정](DERO-134)은 이 ADR과 독립이다 — 애그리거트 루트는 거기서 잡는다.
- **곁가지 발견**: `backend/dero-api/compose.yaml`의 postgres healthcheck가 `pg_isready -U myuser -d mydatabase`인데 실제 계정은 `dero`/`dero_be`다. 헬스체크가 영영 실패한다. 구현 착수 시 고친다.

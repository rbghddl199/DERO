# ADR-0027. 배치·게시글·작성자 검색 — 인덱스 셋, 작성자는 필터로 조립

## 상태

**확정** — 2026-08-07, 승인 박동규.
[ADR-0019](0019-search-elasticsearch-nori.md)가 파급 절 "범위 밖"으로 미뤄 둔
*"데스크피드 배치 검색과 게시글 본문 검색"*의 후속이다. ADR-0019가 세운 것들
(ES 클러스터·Nori 사용자 사전·별칭 재색인 절차·`AFTER_COMMIT` 색인·503 폴백 규약)은
**그대로 재사용한다** — 늘어나는 것은 인덱스와 매핑이지 그 결정들이 아니다.

## 맥락

**제품 검색만 서버로 갔고 나머지는 그대로다.** ADR-0019가 `GET /products?q=`를 ES로 옮기면서
같은 병을 앓던 두 화면을 명시적으로 범위 밖에 뒀다 — *"데스크피드가 찾는 것은 제품이 아니라
배치(placement)라 이 ADR이 고치지 못한다. 같은 병이되 다른 인덱스다."* 2026-08-07 실측으로
그 둘이 아직 클라이언트 필터임을 확인했다.

| 화면 | 코드 | 검색 대상 | 범위 |
|---|---|---|---|
| 데스크피드 | `DeskFeedGallery.tsx:108` | 제목·작성자·태그 | **받아 온 페이지 안** |
| 커뮤니티 | `CommunityGallery.tsx:112` | 제목·작성자·#태그 | **받아 온 페이지 안** |

둘 다 커서 페이징이라 **"불러온 목록 안에서만 검색"이 최적화가 아니라 실제 결함이다** —
ADR-0019가 제품에서 고친 바로 그 상태다. `docs/SPEC.md` REQ-COM-13이 그것을 결함으로 적고 있다.

**스키마 실측**

| | 제목 | 본문 | 태그 |
|---|---|---|---|
| `placement` | `title` VARCHAR(100) | `description` TEXT | **컬럼 없음** |
| `post` | `title` VARCHAR(100) | `content` TEXT (`[[placement:ID]]` 토큰 포함) | `post_hashtag` ↔ `hashtag` |

배치에 태그 컬럼이 없어 **데스크피드의 태그 칩은 값이 항상 비어 뜨지 않는다.**

## 결정

### 1. 인덱스는 셋이다 — `placements` · `posts` · `users`

하나로 합치고 `type` 필드로 가르는 안을 부결했다. **매핑이 갈리기 때문이다** — 배치는 짧은
`title` + 자유로운 `description`이고 게시글은 `content` 전문이라 분석기·부스트 배분이 다르다.
ES 매핑은 한번 만들면 필드 타입·analyzer를 못 바꾸므로(ADR-0019 결정 5) 성격이 다른 문서를
한 인덱스에 넣으면 **한쪽을 튜닝할 때마다 다른 쪽이 같이 재색인된다.**

통합 검색 화면(한 칸으로 제품·배치·글을 모두 찾는) 요구는 없다. 생기면 그때 멀티 인덱스
질의로 조립한다 — 인덱스를 나눠 뒀다고 못 하는 일이 아니다.

### 2. 작성자 검색은 유지하되, 결과를 사람과 글로 나누지 않는다

**`users`에서 닉네임이 맞은 userId를 찾아 `posts`/`placements` 질의의 필터로 넘긴다.**
지금 클라이언트 필터의 동작이 정확히 그것이다 — 작성자 이름이 맞으면 **그 사람의 글이 결과에
뜬다.** 서버로 옮기면서 동작을 바꾸지 않는다.

결과를 "글" / "사람" 두 섹션으로 나누거나 탭을 두는 안은 부결했다. **요청받지 않은 화면
신설이고**, 이 작업의 목적은 지금 보이는 것을 페이징 너머까지 넓히는 것이다.

대가는 ES 왕복 2회다. 첫 왕복은 대개 0히트라(사용자 닉네임을 검색어로 치는 일이 드물다) 싸다.

**작성자 이름을 `posts` 문서에 직접 싣는 안도 부결했다.** ADR-0019 결정 4가 정한 것과 정면으로
걸린다 — 표시값을 ES에 실으면 닉네임을 바꾼 순간 그 사람의 글 전부를 재색인해야 하고, 밀리면
화면이 조용히 옛 닉네임을 보여준다. 색인 트리거가 엔티티 3개(`post`·`placement`·`user`)로 늘어난다.

### 3. `users`에 싣는 것은 닉네임 하나

자기소개는 그것을 쓰는 화면이 없다. **이메일 로컬파트는 부결이다** — 검색 결과로 이메일을
역추적할 수 있게 된다.

### 4. 전량 색인, 노출 판정은 Postgres

ADR-0019 결정 4 그대로다. `PRIVATE` 배치도 색인하고 `publish_status = PUBLIC` 필터는 id로
다시 읽는 Postgres 쿼리가 건다.

**`PUBLIC`만 색인하는 안을 부결한 이유**는 인덱스 크기가 아니라 판정 위치다. 공개 전환 때 색인,
비공개 전환 때 삭제로 가면 **노출 규칙이 두 벌**이 되고, 갈렸을 때 어느 쪽이 맞는지 판정할
수단이 없다. 규모는 문제가 되지 않는다 — 배치·게시글은 수천 건 규모다.

### 5. 배치 태그는 `hashtag` 마스터 재사용 + `placement_hashtag` 정션, 입력은 공개 전환 시점

`placement`에 태그 문자열 컬럼(배열/CSV)을 두는 안을 부결했다. **태그 마스터가 두 벌이면
`#원목데스크`가 피드와 커뮤니티에서 다른 태그가 된다** — "같은 해시태그를 눌렀는데 피드에선
되고 커뮤니티에선 안 된다"가 나온다.

**입력 시점이 공개 전환인 이유**: `PRIVATE` 배치의 태그는 아무도 못 본다. 공개 전환 화면
(`PUT /placements/{id}/feed-entry`)이 이미 사용자에게 "남에게 보일 것"을 묻는 자리다.

ERD 프리즈를 열어 정션 1개를 추가한다(2026-08-07 승인). `placement`·`hashtag` 테이블은 무변경이고
테이블 추가라 [ADR-0026](0026-blue-green-deploy-and-expand-contract-migration.md)의 확장/축소
규칙에서 **확장 쪽**이다 — 배포 1회로 나간다.

### 6. 검색어 이벤트에 `search.index` 필드를 더하고, 로거는 공용 패키지로 옮긴다

값은 `products` · `placements` · `posts`. 없으면 대시보드가 세 검색의 검색어를 한 덩어리로
집계해 **"카탈로그 구멍 목록"이라는 0건 패널의 의미가 무너진다**(ADR-0020 결정 7) — 게시글에
없는 단어가 제품 구멍으로 읽힌다.

**로거는 도메인마다 두지 않고 하나를 공용으로 옮긴다.** ES ingest pipeline이 `log.logger`가
`...search.SearchEventLogger`로 끝나는지로 라우팅을 판정하므로 **패키지 끝을 `.search`로
유지하면 라우팅은 그대로 산다.** 도메인별 로거 클래스를 두면 라우팅 조건이 늘 때마다
`observability/elasticsearch/bootstrap-log-indices.sh`를 고쳐야 하는데, **그 스크립트는 배포
파이프라인 밖이라 EC2에서 조용히 낡는다**(2026-08-07 387 배포에서 실측 — `docs/context/observability.md`
"EC2의 `~/dero/observability/`는 배포와 무관하게 낡는다").

### 7. 색인 실패 복구는 전량 재색인 그대로 — 실측 규모가 그것을 성립시킨다

**ADR-0019 결정 3이 스스로 남긴 경고를 여기서 닫는다.** 그 ADR은 *"쓰기 빈도가 자릿수로 다르다.
제품은 관리자만 바꾸지만 배치는 사용자가 수시로 저장·공개한다. '수백 건 전량 재색인이 몇 초'라는
결정 3의 전제가 배치에는 성립하지 않는다 — 색인 실패 복구 전략부터 다시 정해야 한다"*고 적었다.

**실측(prod, 2026-08-07): `placement` 188행 · `post` 19행 · `user` 91행.** 제품 카탈로그(167)와
같은 자릿수다. 전제는 **아직** 성립한다 — `AFTER_COMMIT` 이벤트 색인 + 수동 전량 재색인 한 벌을
그대로 쓰고, 유실 추적 인프라를 만들지 않는다.

**다시 볼 지점을 여기 적어 둔다**: 배치가 **수만 건**이 되면 전량 재색인이 초 단위를 벗어나고,
그때는 실패한 문서만 다시 넣을 수단(아웃박스·CDC)이 필요하다. 그 판단의 근거는 쓰기 빈도가
아니라 **전량 재색인에 걸리는 실제 시간**이다 — 재색인 로그의 소요 시간이 신호다.

## 대안과 버린 이유

**통합 인덱스 하나(`type` 필드)** — 매핑 충돌(결정 1). 통합 검색 요구가 없는데 지금 그 모양을
만드는 것은 요청하지 않은 flexibility다.

**서버 `ILIKE`로만 검색(ES 없이)** — 배치·게시글은 제품보다 오타·부분어 요구가 약하니 싸게
가자는 안. **검색 로직이 두 벌이 되는 것**이 부결 이유다(ADR-0019 결정 6이 폴백을 부결한 것과
같은 논리) — 같은 서비스 안에서 화면마다 관련도 규칙이 다르면 "왜 여기선 되고 저기선 안 되지"를
아무도 풀 수 없다.

**`users` 인덱스 대신 Postgres에서 닉네임 조회** — 왕복 하나를 아끼는 안. 닉네임도 부분어·오타
관용이 필요한 검색어인데 그 자리에 `ILIKE`를 쓰면 위와 같은 두 벌 문제가 생긴다. 인덱스 하나가
싸다.

**데스크피드 태그 UI 제거(태그 없이 제목·설명만)** — ERD를 안 여는 안. 지금 화면에 있는 기능을
없애는 것이라 사용자가 잃는 것이 실재하고, 태그는 데스크피드 탐색의 주된 축이다.

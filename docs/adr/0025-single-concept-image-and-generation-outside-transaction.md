# ADR-0025. 상상도는 1장, 생성기는 GMS 고정, 생성 호출은 트랜잭션 밖

## 상태

**확정** — 2026-08-06, 승인 박동규.
[ADR-0015](0015-placement-upload-async-pipeline.md)의 **결정 3·4·5·6·8을 개정**한다(나머지는 유효).
기획 근거는 `docs/CONTEXT.md` D29. API 표면은 `docs/context/api-spec.md` §4. `erd.md`는 안 건드린다.

## 맥락

ADR-0015는 세 가지를 전제로 서 있었고, 셋 다 사실이 아니게 됐다.

1. **"상상도를 만드는 모델은 우리 로컬 노트북의 python 프로세스다."** 그 모델은 끝내 오지 않았다.
   그동안 실제로 상상도를 만들어 온 것은 `GmsImageGeneration`(GMS 프록시 → `gpt-image-2`)이고,
   2026-08-02 콘테스트부터 운영이 그것으로 돌았다. 즉 ADR-0015가 "잠정"이라 부른 쪽이 6주째
   유일한 구현이고, "본안"이라 부른 쪽은 코드가 한 줄도 없다.
2. **"상상도는 3장이다."** 3장은 각도가 다른 3장을 전제로 한 수인데, 실제 구현은 각도를 지정하려고
   `n=1` 요청을 **3번** 부른다(2026-08-05). 그래서 3장은 곧 **생성 시간 3배·비용 3배**다.
   프론트 폴링 상한이 2분인데 장당 최악 5분이므로, 3장은 사용자가 "실패했나" 싶은 시간을 3배로 늘린다.
3. **"3행을 한 트랜잭션으로 쓴다."** 그 트랜잭션 안에 **외부 호출까지 들어가 있었다.**
   `GeneratedImageService.publish`가 `@Transactional` 하나로 재료 읽기 → GMS 호출 → 행 쓰기를 감싸,
   `read-timeout` 300초 × 3장 동안 커넥션 하나와 `demotePrimaries`의 행 락을 붙잡았다.

세 번째는 문장으로만 보면 결정 8을 지킨 것처럼 읽힌다 — **"한 트랜잭션"이 원자성을 뜻하는지 경계의
크기를 뜻하는지 그 문장이 갈라 놓지 않았기 때문이다.** 이 ADR이 그것을 가른다.

## 결정

### 1. 상상도는 1장이다 (ADR-0015 결정 6 개정)

한 업로드가 `generated_image`에 **1행**을 만들고, 그 행이 곧 `is_primary`다.

- **각도 컬럼을 안 만든다는 원 결정은 그대로 유효하다** — 오히려 각도가 하나뿐이라 더 확실해졌다.
- **`is_primary`와 부분 유니크도 그대로 둔다.** 지금은 항상 참이라 잉여로 보이지만, 지우면 재업로드
  이력(옛 행이 남는다)에서 "현재 대표가 어느 행인가"를 답할 수단이 사라진다. `demotePrimaries` →
  새 대표 INSERT 순서도 그래서 그대로다.
- **장수의 정본은 `FeedEntryService.IMAGES_PER_UPLOAD` 상수 하나다.** 포트 요청의 `count`, 계약 검증,
  상세 조회 개수, 한도 선차감이 전부 거기서 읽는다. 되돌리거나 2장으로 바꾸는 비용을 그 한 줄로
  묶어 두는 것이 이 결정의 절반이다 — 그래서 포트의 `count` 필드도, `GmsImageGeneration`의 루프도,
  프론트의 2열 그리드도 **지우지 않고 남긴다**(지금은 1회만 돌고 안 그려진다).
- 도달할 수 없게 된 좌·우 사선 프롬프트는 지운다. 여러 장으로 돌아가면 그때 각도 문구를 되살린다.

부결: `generate()`가 `String` 하나를 돌려주도록 포트를 아예 1장짜리로 줄이는 안 — 상수 한 줄이던
되돌리기 비용이 포트·구현·계약 테스트 전면 수정으로 커진다.

### 2. 일일 한도 기본값은 7 (ADR-0015 결정 8 개정)

- **단위는 여전히 "장"이다.** `generated_image` 행 수가 근거이고 회차를 묶는 컬럼은 없다.
- 상한이 `IMAGES_PER_UPLOAD`의 배수여야 한다는 제약은 유지하되, 1장이 되면서 **모든 정수가 배수**라
  사실상 풀렸다. "1장 남았는데 업로드가 안 된다"는 잔량은 이제 생기지 않는다.
- 기본값 **21 → 7**. 3장×7회였으므로 **회차 수를 그대로 옮긴 값**이다. 장수만 줄이고 21을 두면
  하루 21회가 되어 GMS 비용이 3배로 뛴다 — 줄이려던 것이 늘어난다.

### 3. "전부 성공했을 때만 기록"은 원자성이지 경계 크기가 아니다 (ADR-0015 결정 8 개정)

`publish`를 **세 구간**으로 가른다.

```
① 짧은 트랜잭션   PENDING 확인 · 프롬프트 재료 읽기 · 스크린샷/주인 게이트
② 트랜잭션 없음   ImageGenerationPort.generate(...)      ← 유일하게 오래 걸리는 구간
③ 짧은 트랜잭션   PENDING 재확인 · demotePrimaries · 행 INSERT · PUBLIC 전이
```

- **쓰기는 전부 ③ 하나에 모여 있으므로 "부분 실패가 한도를 깎는" 사고는 막힌 채다.** 원 결정이
  지키려던 것은 이것이고, 그 보장에 외부 호출을 같은 트랜잭션에 넣을 이유는 없었다.
- **가드를 두 번 본다.** ①이 통과시킨 뒤 ②가 도는 몇 분 사이에 사용자가 `DELETE .../feed-entry`로
  내릴 수 있다. 그때는 **만든 그림을 버린다** — 명시적 취소를 뒤집는 것보다 낫고, 행이 안 들어가니
  한도도 안 깎인다.
- 구현은 `TransactionTemplate` 두 번 + `publish`에 `@Transactional(NEVER)`. **이 애노테이션이
  없으면 클래스의 `readOnly = true`가 살아나** 두 구간이 기본 전파(REQUIRED)로 거기 합류해 ⑴다시 한
  덩어리가 되고 ⑵Hibernate가 읽기 전용에서 `FlushMode.MANUAL`을 써 **INSERT가 조용히 사라진다.**
- **전파는 `NOT_SUPPORTED`가 아니라 `NEVER`다**(2026-08-06 보정). 둘 다 클래스 `readOnly`를 무력화하는
  것은 같다 — 메서드 레벨 `@Transactional`은 클래스 레벨과 병합되지 않고 대체한다. 갈리는 건 바깥에
  트랜잭션이 생긴 날이고, `NOT_SUPPORTED`는 그것을 **중단(suspend)** 시키는데 **중단된 트랜잭션은 자기
  커넥션을 계속 쥔다** — 이 결정이 막으려던 300초 점거가 아무 흔적 없이 부활한다. `NEVER`는 같은
  상황을 `IllegalTransactionStateException`으로 세운다. 호출부는 `ImagePublishWorker` 하나뿐이라
  트랜잭션이 생길 일이 없고, 그래서 생기면 사고다.
- **회귀는 기능 테스트로 안 잡힌다** — 다시 합쳐도 상태 전이도 행 수도 그대로 통과한다. 그래서
  `GeneratedImagePublishTransactionTest`가 포트를 가로채 호출 순간의 `isActualTransactionActive()`를
  직접 보고, 같은 테스트가 쓰기 커밋까지 확인한다.

부결: 워커(`ImagePublishWorker`)가 세 구간을 조립하는 안 — 상태 기계 계약이 두 클래스로 흩어지고,
`publish` 하나를 읽으면 되던 것이 두 곳을 대조해야 하는 일이 된다.

### 4. 생성기는 GMS로 확정한다 — 로컬 AI 머신은 폐기 (ADR-0015 결정 3·4·5 개정)

**로컬 노트북 python 워커 + SSH 터널 기획을 파기한다.** 상상도는 `app.image.generation.mode=gms`가
정본이고, `stub`은 키 없이 부팅하기 위한 테스트·로컬 기본값으로만 남는다.

- **큐 소비 루프는 WAS 안 스레드가 최종형이다**(`ImagePublishWorker`). "진짜 워커가 오면
  `app.image.worker.enabled`를 꺼서 이 루프를 내린다"는 전제가 사라졌다.
- **결정 5(presigned URL을 메시지에 담는다)는 실현된 적이 없고, 이제 실현하지 않는다.** 메시지는
  `{placementId, requestedAt}`뿐이고 생성기가 WAS 안에 있어 `StoragePort`로 직접 바이트를 만진다.
  자격증명을 남의 기기에 두지 않으려던 결정이었는데, 둘 기기가 없어졌다.
- **결정 3의 터널 부결 논거는 유효한 채로 남는다** — Redis 포트를 열지 않고 `127.0.0.1` 바인딩을
  유지한다(리프레시 토큰 동거). 그 문제 자체가 사라졌을 뿐이다.
- **결정 4의 유실 방지(`BLMOVE` + 처리중 리스트 + 스위퍼)는 그대로 유지한다.** 원인이 "노트북이
  잠들었다"에서 "WAS가 재시작했다 / GMS가 늦다"로 바뀌었을 뿐 유실은 여전히 난다.
- **포트 추상화는 유지한다**(ADR-0001의 3포트 중 하나). 갈아탈 대상이 생기면 `ImageGenerationPort`
  구현이 바뀌지, 워커나 큐가 바뀌지 않는다 — 그게 이 포트를 둔 이유고, 이번 파기로 실제로 증명됐다.

부결: 포트를 걷어내고 `GmsImageGeneration`을 직접 부르는 안. 구현이 하나뿐이라는 이유로 지우면
스텁이 같이 사라져 키 없는 로컬·CI 부팅이 깨진다.

## 파급

- **`erd.md` 무변경.** `generated_image`도 `is_primary` 부분 유니크도 그대로다. 이미 쌓인 3장짜리
  묶음은 마이그레이션하지 않는다 — 삭제 금지 테이블이고, 상세 조회가 최신 `IMAGES_PER_UPLOAD`장만
  끊어 읽으므로 옛 행은 화면에 안 나온다.
- **API 무변경.** `GET /placements/{id}/generated-images`는 배열 그대로고 길이만 줄었다.
  프론트는 `isPrimary` 1장을 크게 그리고 나머지를 2열로 그리는 코드를 그대로 둔 채 상수만 맞춘다.
- **생성 시간이 1/3로 준다.** 프론트 폴링 상한(`PUBLISH_POLL_TIMEOUT_MS` 2분)이 처음으로 현실적인
  값이 됐다. `read-timeout: 300s`는 **요청 1건당** 상한이므로 그대로 두고, 워커
  `processing-timeout: 10m`과 비교할 값은 `read-timeout × IMAGES_PER_UPLOAD`다.
- **커넥션 점유가 사라진다.** 워커가 한 스레드인 지금은 낭비 한 건이지만, 워커를 늘리는 순간
  풀 고갈이었다 — 늘리기 전에 막았다.
- ADR-0015는 **대체됨이 아니라 부분 개정**이다. 상태·큐·`feed-entry` API·게이트 순서·스크린샷 전제는
  전부 그 문서가 정본으로 남는다.

# 백엔드 런타임 함정 근거 — 로컬 개발 · 포트 · 이미지 파이프라인

각 폴더 `CLAUDE.md`는 "무엇을 하면 깨지는가" 한 문장만 들고 있다. 이 문서는 그 문장들의 **근거**
정본이다 — 실측치, 티켓 번호, 실패 서사, 버린 대안. 티켓 DERO-544에서 옮겨 왔다.

읽는 순서: 증상을 만났을 때만 연다. 규칙 자체는 `CLAUDE.md`와 `.claude/rules/backend/*`에 있다.

## 1. 로컬 개발 환경

### 1-1. 스키마 검증 · 시퀀스

- **`TRUNCATE ... RESTART IDENTITY` makes the next test class see negative ids** — 규칙은 `.claude/rules/backend/testing-runtime.md` §2. `allocationSize = 50` + a sequence reset to 1 = Hibernate's pooled optimizer hands out `nextval - 49 … nextval`, i.e. **negative primary keys** (measured 2026-08-11: `-47`, `-46` for the first two users created after `DeskFeedControllerTest`'s teardown). Rows insert fine and every `findById` works, so **nothing fails — until an id has to survive as text**. `DeskFeedMentionControllerTest` was the first such test (`[[user:ID]]` in a post body, parsed with `\d{1,18}`): it passed alone and failed only in the full suite, and the assertion error (`mentions` empty) pointed at the parser, not the fixture. 18 test classes truncate this way today; `PostSearchPersistenceTest` documents the related ordering symptom.
- **`GENERATED BY DEFAULT AS IDENTITY`가 소유한 시퀀스는 `ddl-auto: validate`에 안 보인다.** Hibernate `PostgreSQLDialect.getQuerySequencesString()`은 `information_schema.sequences`를 읽는데, **identity 소유 시퀀스는 그 뷰에서 제외된다**. 그래서 `@SequenceGenerator(sequenceName = "<table>_id_seq")`는 부팅을 `Schema-validation: missing sequence [brand_id_seq]`로 죽인다 — 시퀀스가 `pg_class`에 정확한 이름과 `INCREMENT BY`로 존재하는데도 그렇다(2026-07-28 실측, postgres:18-alpine, DERO-201). 명시적 `CREATE SEQUENCE`와 `BIGSERIAL`은 보인다. **증상이 "시퀀스 없음"이라 DDL을 의심하게 되지만, 원인은 조회하는 뷰다.** ADR-0006 결정 8의 전제("erd.md 변경 없이 SEQUENCE 전략 유지")를 깬다 — 같은 ADR의 결정 9 `validate`와 충돌.

### 1-2. actuator health 200/503 — 규칙은 `.claude/rules/backend/testing-runtime.md` §3

- **테스트에서 `/api/actuator/health`는 개발자 로컬 Docker 상태에 따라 200 또는 503이다 — 어느 쪽도 assert 금지.** `application-test.yaml`은 Redis를 설정하지 않아 `RedisHealthIndicator`가 `localhost:6379`로 폴백해 **Testcontainers 밖, 호스트의 redis 컨테이너**에 닿는다: 컨테이너가 떠 있으면 200, 죽어 있으면 db·diskSpace·ssl은 UP인 채 `redis`만 DOWN(`RedisConnectionFailureException`)으로 503. 둘 다 2026-08-05 실측, DERO-464 — 같은 테스트가 컨테이너를 켜자 뒤집혔다. Postgres만 띄우는 `AbstractPostgresIntegrationTest`는 원인이 **아니고**, `unless-stopped`는 손으로 끈 redis를 되살리지 않으므로 한 머신이 며칠씩 503 상태로 앉아 있을 수 있다. **바디에는 컴포넌트 상세가 없다**(`{"groups":[...],"status":"DOWN"}`) — `show-details` 기본값이 `never`라서다. 어느 것이 죽었는지 보려면 `@TestPropertySource(properties = "management.endpoint.health.show-details=always")`를 임시로 단다. 이 엔드포인트를 만지는 흔한 이유는 스크레이프 assert 전 워밍업 요청이다 — 요청은 보내되 상태는 무시한다.

### 1-3. Boot 4.1 스타터 이름 — 규칙은 `.claude/rules/backend/gradle-build.md` §1

- **Spring Boot 4.1 스타터 이름은 Boot 3과 다르다.** `spring-boot-starter-web`이 아니라 `-webmvc`; `-oauth2-client`가 아니라 `-security-oauth2-client`; `spring-boot-starter-test` 하나가 아니라 슬라이스별 `-test` 스타터(`...-webmvc-test`, `...-data-jpa-test`). 의존성은 기억이나 튜토리얼이 아니라 `build.gradle`에 이미 있는 표기를 복사해 추가한다 — Boot 3 이름은 의존성 해석에서 깨진다.

### 1-4. 툴체인·JAVA_HOME·DOCKER_HOST·Gradle 데몬

- **툴체인은 21이지만 기본 `java`는 더 낮을 수 있다** — Gradle은 툴체인을 별도로 감지한다. macOS: `java -version`이 17(jenv shim)을 보여줘도 `./gradlew compileJava`는 성공한다(2026-07-23, `~/Library/Java/JavaVirtualMachines`에서 21 자동 감지). `JAVA_HOME is not set and no 'java' command could be found`가 뜨면 **JDK가 없다고 단정하지 말고 `~/.jdks/`부터 본다**: WSL에 IntelliJ의 `~/.jdks/corretto-21.0.12`는 있는데 PATH에 `java`가 없었다(2026-07-28, DERO-205). 있으면 `JAVA_HOME=$HOME/.jdks/corretto-21.0.12 ./gradlew ...`로 넘기고, 정말 없을 때만 openjdk-21을 설치한다.
- **WSL에서 Testcontainers가 Docker를 못 찾는다 — `DOCKER_HOST`를 명시하라.** 증상: `Could not find a valid Docker environment` + `DOCKER_HOST unix:///var/run/docker.sock is not listening`, 그런데 **소켓은 멀쩡하다**(`curl --unix-socket /var/run/docker.sock http://localhost/_ping` → 200). 진짜 원인: Testcontainers 2.0.5가 `DockerDesktopClientProviderStrategy`를 먼저 고르고, WSL에서 그 `getSocketPath()`가 null을 반환해 NPE — unix 소켓 전략은 **시도조차 안 된다**. 실패는 `NoClassDefFoundError`/`ExceptionInInitializerError`로 떠서 코드 버그처럼 보인다(2026-07-28, DERO-205). 해법: `DOCKER_HOST=unix:///var/run/docker.sock ./gradlew test`.
  - **두 세션이 동시에 `./gradlew test`를 돌리면 실패가 조작된다 — 코드보다 데몬 경합부터 의심.** 병렬 워커가 `--stop`을 치면 반대쪽 테스트 JVM이 실행 도중 죽는데, Gradle은 이를 **평범한 테스트 실패로 보고한다** — 실제 테스트 줄번호가 붙은 `ServletException`/`IllegalArgumentException`이라 방금 고친 것의 회귀로 읽힌다(2026-08-02 실측: `ProductImageControllerTest` 포함 7건 빨강, 단독 재실행에서 전부 초록). 신호: 로그 끝의 `Gradle build daemon has been stopped: stop command received`, 다음 실행의 `java.io.EOFException`. `build/test-results/`는 경쟁 실행이 지워 버려 부검이 안 된다. **판정은 모든 워커가 끝난 뒤 단독 실행으로만.**
  - **환경변수만으로 안 되면 Gradle 데몬을 죽인다.** 데몬은 처음 뜰 때의 환경을 재사용하므로, `DOCKER_HOST` 없이 뜬 데몬은 새 env를 테스트 JVM에 영영 안 넘긴다. `./gradlew --stop` 먼저. **`--stop`에도 `JAVA_HOME`을 붙인다** — 래퍼는 데몬을 멈추는 데조차 JVM을 찾다가 거기서 죽는다(2026-07-28, 두 번 발생).

### 1-5. ArchUnit freeze 베이스라인 — 규칙은 `.claude/rules/backend/testing-runtime.md` §4

- **ArchUnit freeze 베이스라인은 스스로 줄어들어, 테스트의 "현재 위반 N건" javadoc이 조용히 썩는다.** `freeze.store.default.allowStoreUpdate=true`라 위반 하나를 고치면 `src/test/resources/archunit_store/<uuid>`에서 그 줄이 지워지는데, 규칙 옆 javadoc은 원래 개수를 그대로 들고 있다 — 2026-08-06 `ControllerConventionTest`는 여전히 "위반 7건 — AuthController.refresh / UserController.me / …"라고 말했지만 store에는 **1건**(refresh; 나머지 6건은 진작 해소)이었다. **남은 작업은 주석이 아니라 store 파일로 센다**(`stored.rules`가 규칙 이름 → uuid 매핑). 마지막 하나를 해소하면 규칙을 unfreeze하고 베이스라인 파일과 `stored.rules` 줄을 둘 다 지운다 — 빈 베이스라인은 미래 회귀가 흡수될 자리다(`archunit.properties` 원칙).

### 1-6. 데이터 컨테이너 · docker-compose 제거

- **이 폴더의 dev `compose.yaml`은 삭제됐다**(2026-07-29, 박동규 — 루트 compose 단일화). 로컬 postgres/redis는 이제 리포 루트 **`compose.data.yaml`**(프로젝트 `dero-data`)에서 온다: 리포 루트에서 `docker compose -f compose.data.yaml up -d`. 호스트 포트는 `127.0.0.1:5432` / `127.0.0.1:6379`로 퍼블리시(루프백 바인딩, EC2에서 안전). 로컬 더미 자격증명 `dero`/`derobe`/`dero_be`는 루트 `.env` `POSTGRES_*`가 정본 — 배포 설정에 재사용 금지(ADR-0010).
- **`spring-boot-docker-compose`는 제거됐다**(2026-07-29, 박동규 승인 — 명시적 설정 선호). 컨테이너 자동 기동도 연결 정보 자동 주입도 없으므로: ① 부팅 전 위 명령으로 데이터 컨테이너를 손으로 띄운다 ② 로컬 연결 정보 정본은 `application-local.yaml` datasource/redis 블록 — **루트 `.env` `POSTGRES_*` 더미와 짝이니 한쪽을 바꾸면 다른 쪽도 바꾼다** ③ `local` 프로파일 없이는 datasource가 없어 부팅이 죽는다 — `bootRun`은 하드코딩돼 있지만 IntelliJ는 Run Configuration의 Active profiles에 `local`이 필요하다.

### 1-7. POSTGRES_* 볼륨 · Dialect 메시지

- **`POSTGRES_*`는 빈 볼륨에만 적용된다.** `.env` 자격증명을 바꿔도 기존 `dero-data_postgres-data` 볼륨 안의 role은 그대로다 — 2026-07-27 부팅이 `password authentication failed for user "dero"`로 죽었는데, 볼륨에는 Initializr 기본 `myuser` role만 있었다. 증상이 "비밀번호 틀림"이라 설정을 의심하게 되지만 원인은 **role 자체가 없는 것**(PG는 없는 role에도 동일하게 응답한다). 해법 둘: 비밀번호만 불일치 — 소켓은 trust라 `docker exec dero-data-postgres-1 psql -U dero -d dero_be -c "ALTER USER dero WITH PASSWORD '...'"`(2026-07-29 사용); role이 정말 없음 — `docker compose -f compose.data.yaml down -v` 후 다시 올린다. 스키마는 Flyway가 재구축한다.
- **`Unable to determine Dialect without JDBC metadata`는 `local` 프로파일이 꺼졌다는 증거가 아니다.** datasource 프로퍼티가 없을 때와, 있는데 연결이 실패할 때 같은 메시지가 뜬다 — 로그가 SQLException 체인 없이 그 한 줄로 끝나서 비활성 프로파일로 오진하기 쉽다(2026-08-01 실측). 그때 원인은 위 항목의 역방향: `application-local.yaml`의 datasource 블록(`dero_db`/`deroroot`/`derodero`)이 루트 `.env`(`dero`/`dero_be`)로 이미 초기화된 컨테이너의 실제 role/DB와 어긋나 있었다 — 두 파일이 따로 드리프트했다. `docker exec dero-data-postgres-1 psql -U <실제 role> -d <실제 db> -c '\du'`로 컨테이너의 실제 값을 확인하고 `application-local.yaml`을 거기에 맞춘다.

### 1-8. Flyway V1 동결 — 규칙은 `.claude/rules/backend/flyway-migration.md` §1

- **`V1__baseline.sql`을 직접 고치면 다음 부팅에서 로컬 dev DB가 죽는다.** **2026-07-31부터 V2를 만든다(박동규 지시); V1은 동결** — 아래 함정은 그날까지의 워크플로였고, 지금 V1을 고치면 곧장 되밟는다. 첫 사례: `V2__placement_publish_status_and_generated_image_primary.sql`(`visibility` → `publish_status` 개명 + `generated_image.is_primary`); V2부터 마이그레이션은 **로컬 볼륨 리셋 없이** 다음 부팅에 적용된다. 역사 기록: 동결 전 워크플로는 V1을 고쳤는데, 돌고 있는 로컬 postgres의 `flyway_schema_history`는 **옛 체크섬**을 들고 있어 `local` 프로파일 부팅이 `Migration checksum mismatch for migration version 1`로 막힌다(2026-07-29 `image_url`→`image_key` 개명 중 실측 — 낡은 체크섬 `1088911785`). **`./gradlew test` 초록은 안심이 아니다** — Testcontainers는 새 컨테이너를 띄워 마이그레이션을 처음부터 재생하므로 부팅에서야 발견한다. 해법: 리포 루트에서 `docker compose -f compose.data.yaml down -v` → `up -d`(볼륨을 버리면 Flyway가 재구축).
  - **정정(2026-07-30, DERO-279): "Testcontainers는 무관하다"는 `reuse=true`에서 거짓.** 재사용 컨테이너는 옛 체크섬을 들고 살아남아, V1을 고친 뒤 전체 테스트가 `Migration checksum mismatch for migration version 1`로 컨텍스트 기동에 실패한다. 다음 실행에서 저절로 풀렸다(그 사이 재사용 컨테이너가 정리됨) — **재현 불가가 더 나쁘다**, 코드를 뒤지러 가게 되니까. 막히면 `docker ps`, 남은 `testcontainers` 컨테이너 삭제, 재실행.

### 1-9. 원격 DB + app.storage.mode

- **원격 DB에 터널로 붙으면 `app.storage.mode`도 맞춰야 한다 — 아니면 API는 200인데 이미지/GLB가 전부 404다.** 공유 `application.yaml` 기본값은 `mode: local`(`LocalPresignService`가 이 머신의 `./data/uploads`를 뒤진다); prod는 `application-prod.yaml`에서 `mode: s3`로 덮는다. 원격(운영) DB의 `asset_key`/`image_key`는 실제 S3 객체를 가리키므로, `mode: local`인 로컬 백엔드는 프리사인은 멀쩡히 되는데(서명·라우팅 성공) 모든 `GET`이 `404 STORAGE_FILE_NOT_FOUND` — 프론트의 "미리보기 이미지 없음"으로만 드러나 프론트나 API 배선을 의심하게 된다(2026-08-01 실측, `/simulator` 제품 썸네일 전멸). 해법: `application-local.yaml`의 `app.storage.mode`는 `${APP_STORAGE_MODE:local}`로 유지하고(팀 공유 파일, 기본값은 `local` 그대로), 원격 DB에 붙는 사람이 자기 `.env.local`에 `APP_STORAGE_MODE=s3`를 넣는다(기존 `AWS_*` 4개 재사용).

### 1-10. Docker 부재 · 컨테이너 스펙 · PG18 볼륨 경로 · PG LTS

- **Docker가 없으면 postgres도 없어 SQL/마이그레이션 검증이 불가능하다.** 증상은 환경마다 다르다(둘 다 2026-07-23 확인): WSL은 `The command 'docker' could not be found in this WSL 2 distro`(Docker Desktop > Settings > Resources > WSL Integration에서 배포판 활성화); macOS는 CLI는 있는데 `docker info`가 소켓에 못 닿는다(Docker Desktop 자체를 켠다).
- 데이터 컨테이너 스펙 정본은 루트 `compose.data.yaml` — postgres `postgres:18-alpine`, redis `redis:8-alpine`, 둘 다 네임드 볼륨 영속 + `127.0.0.1` 호스트 포트.
- **PG 18은 이미지의 볼륨 경로를 바꿨다** — `/var/lib/postgresql/data`가 아니라 **`/var/lib/postgresql`**(`PGDATA=/var/lib/postgresql/18/docker`). 튜토리얼대로 `/var/lib/postgresql/data`를 마운트하면 데이터가 볼륨 밖에 남아 컨테이너 삭제와 함께 사라진다.
- PostgreSQL에 LTS는 없다. 메이저당 5년, 18은 2030-11까지 — 메이저 업그레이드는 볼륨 교체를 뜻하므로 스키마 동결 전에 결정한다.

### 1-11. 마이그레이션 테스트 target — 규칙은 `.claude/rules/backend/flyway-migration.md` §2

- **`target` 없이 `migrate()`를 부르는 마이그레이션 테스트는 나중에 쓰인 모든 버전을 조용히 적용한다.** `PlacementWallBackfillMigrationTest`는 `target("7")`에서 옛 모양 데이터를 깔고 나머지를 돌리므로 V8 **그리고** 이후 추가된 모든 마이그레이션을 탄다 — V9의 잔여 백필이 지금 V8 테스트 안에서도 돌고, V10의 DROP도 돌 것이다. 대개는 그게 원하는 바지만(체인이 여전히 착지함을 증명), **미래 마이그레이션이 옛 버전 이름만 단 옛 테스트를 깨뜨릴 수 있다**는 뜻이고, 나중 마이그레이션이 지우는 컬럼을 만지는 assert는 헷갈리는 "column does not exist"로 실패한다. assert는 테스트 대상 마이그레이션이 *만드는* 컬럼에 걸고, 한 단계를 격리해서 볼 테스트라면 양끝에 `target(...)`을 못 박는다.

### 1-12. 설정 파일 — 규칙은 `.claude/rules/backend/spring-config.md`

- `src/main/resources/application.yaml`은 공유 JPA 값을 이미 들고 있다 — `ddl-auto: validate`(Hibernate의 스키마 생성 차단; 스키마 정본은 `docs/context/erd.md`) · `open-in-view: false` · `default_batch_fetch_size: 100`. ADR-0006에서 확정; 완화 금지.
- **Boot 4.1에서 메트릭 export는 opt-in — 레지스트리 의존성만으로는 조용한 404다.** 클래스패스의 `micrometer-registry-prometheus`에 `management.endpoints.web.exposure.include`의 `prometheus`를 더해도 **부족하다**: `management.prometheus.metrics.export.enabled: true`가 없으면 `PrometheusMetricsExportAutoConfiguration`이 `management.defaults.metrics.export.enabled is considered false`로 물러나 `PrometheusMeterRegistry` 빈이 안 만들어지고 `/api/actuator/prometheus`는 **예외도 경고도 없이 404**(2026-08-04 실측, Boot 4.1.0 + Micrometer 1.17.0, DERO-383). **Boot 3 튜토리얼에는 그 줄이 없고**, 하류 증상은 배포 후 Prometheus 타깃이 `DOWN`으로 앉아 있는 것뿐이다. `PrometheusEndpointTest`가 셋(의존성 · 노출 · export)을 함께 못 박는다 — 진단은 조건 리포트: `ConditionEvaluationReport.get(beanFactory).getConditionAndOutcomesBySource()`.
- **Actuator는 기본 `/actuator`가 아니라 `/api/actuator`다**(2026-07-31, `application.yaml`의 `management.endpoints.web.base-path`). nginx는 `/api` 접두사만 전달하고, 이는 컨트롤러가 `@RequestMapping("/api/v1/...")`를 직접 드는 것과 짝이다(`server.servlet.context-path`였다면 `/api/api/v1/...`로 겹친다). **경로를 바꾸면 `Jenkinsfile`의 `wait_for`도 같이 바꾼다** — Verify는 nginx를 우회해 `127.0.0.1:8081`을 직접 치므로, 아니면 다음 배포가 404를 30번 재시도하다 타임아웃된다.
- **QueryDSL Q 클래스는 `build/generated/sources/annotationProcessor/java/main`에 떨어진다**(2026-08-01 배선, DERO-332). Gradle이 그 경로를 소스셋에 자동 추가하므로 **`build.gradle`에 `sourceSets`/`querydslDir`/`clean.doLast`를 손으로 넣지 마라** — 온라인 QueryDSL 가이드 대부분이 Gradle 4 시절 것이고 지금은 불필요한 복잡성이다. `build/`는 이미 gitignore 대상이고 `clean`이 지운다(그 뒤 IDE가 Q 클래스를 보려면 `./gradlew compileJava` 재실행). apt는 **3줄 세트**: `querydsl-apt:7.0:jakarta` + `jakarta.annotation-api` + `jakarta.persistence-api`. 규칙: `backend/CLAUDE.md`의 쿼리 계단 절.
- **datasource/redis 블록은 `application.yaml`에 의도적으로 없다** — 3개 프로파일 파일(`application-local.yaml`, `application-prod.yaml`, 테스트의 `application-test.yaml`)과 루트 `.env.local` → compose 보간이 주입한다(ADR-0010). 공유 파일에 URL/자격증명을 쓰면 프로파일별 주입을 조용히 덮는다.
- **테스트 컨텍스트가 하나 늘면 Postgres 커넥션이 터진다 — Hikari 풀은 테스트에서 4다.** 스프링 테스트 컨텍스트마다 Hikari 풀이 하나씩 뜨고 기본값이 10이라, 컨텍스트가 늘어나는 순간 컨테이너 Postgres의 `max_connections`(100)를 넘겨 **뒤에 뜨는 컨텍스트가 통째로 죽는다** — `Failed to load ApplicationContext` 안쪽에 `FATAL: sorry, too many clients already`가 숨어 있다(2026-08-06 실측, ES 통합 테스트가 `@DynamicPropertySource`로 새 컨텍스트를 만들면서 넘겼다). **증상이 "새로 추가한 테스트가 컨텍스트 로딩부터 실패"라 새 코드 문제로 오진하기 쉽다** — 같은 실행의 다른 테스트도 같이 죽었는지부터 본다. 못은 `application-test.yaml`의 `spring.datasource.hikari.maximum-pool-size: 4`이고, 테스트는 단일 스레드라 더 필요 없다.

### 1-13. OAuth 등록 항목·프록시 스킴 — 규칙은 `.claude/rules/backend/spring-config.md` §5

- **`.env.local` 등록 항목은 전부 채우거나 전부 비운다** — 일부만 채운 프로바이더는 부팅을 `Client id of registration 'kakao' must not be empty.`로 죽인다. 파일이 아예 없으면 잘 뜬다(2026-07-27 실측). 항목 목록: `.env.local.example`; 근거 ADR-0010.
  - **Prod에는 "비워 두기" 선택지가 없다 — OAuth 4개 프로바이더 전부 실값이 필요하다.** `application-prod.yaml`이 등록 키를 무조건 `client-id: ${OAUTH_KAKAO_CLIENT_ID}`로 선언하므로(2026-07-30 개정 — 그전에는 compose가 `SPRING_SECURITY_OAUTH2_...` 완화 바인딩으로 몰래 주입했다) prod는 소셜 로그인을 뺀 채 못 돈다. 키 자체가 없으면 시끄럽게 실패한다 — compose `:?`가 `docker compose up`에서 멈추고, compose를 우회해 env 없이 띄우면 부팅이 `Could not resolve placeholder 'OAUTH_KAKAO_CLIENT_ID'`로 죽는다. **빈 문자열이 여전히 조용한 경로다** — 플레이스홀더가 `""`로 풀려 `Client id of registration 'kakao' must not be empty.`에서야 드러난다(2026-07-29 Jenkins Verify가 이렇게 막혔다, DERO-242). 값을 채워라, 지우지 마라.
- **프록시 뒤에서 `{baseUrl}`은 http로 풀린다 — https가 필요하면 `server.forward-headers-strategy`를 켠다.** nginx가 TLS를 종단하고 평문 HTTP를 전달하는데 Boot 기본값이 `NONE`이라 Spring은 **`X-Forwarded-Proto`를 받고도 무시한다**. OAuth `redirect-uri: "{baseUrl}/api/login/oauth2/code/{registrationId}"`가 `http://www.dero.life/...`로 조립되고 Kakao/Google이 **"unregistered redirect URI"**로 인가를 거부한다(2026-08-01 실측, DERO-317, 두 프로바이더 모두). **증상이 프로바이더 콘솔 화면에 떠서 콘솔 등록 실수로 오진하기 쉽지만**, 뭘 등록했든 http 스킴은 항상 틀렸다. nginx는 원인이 아니다 — 헤더는 이미 보내지고 있었다. `redirect_uri=` 스킴을 직접 진단: `curl -sD - -o /dev/null https://www.dero.life/api/oauth2/authorization/kakao | grep -i location`. **`prod` 프로파일 전용이라 로컬/CI/테스트는 전부 통과한다**(로컬은 프록시 없이 `localhost:8080` 직행, 스킴이 맞다).
- **`.env.local`이 안 읽히면 작업 디렉토리부터 본다.** `spring.config.import: optional:file:./.env.local[.properties]`는 `./`를 JVM 작업 디렉토리 기준으로 풀고 파일은 `backend/dero-api/`에 있다 — `bootRun`은 모듈 폴더가 기본(정상)이지만, 리포 루트를 가리키는 IDE Run Configuration은 아니다. `optional:`이라 **경고도 에러도 없이** 건너뛰고, 소셜 로그인만 조용히 깨진다.

### 1-14. spotless 실측 — 규칙은 `.claude/rules/backend/gradle-build.md` §4

- **spotless는 git이 있어야 돈다.** `ratchetFrom 'origin/develop'`이라 spotless 태스크는 git 저장소를 요구한다. 실측(2026-08-11, `.git` 없는 사본): `spotlessCheck` → `Cannot find git repository in any parent directory`로 실패, `bootJar` → 성공. 배포 Dockerfile은 소스만 COPY하고 `.git`을 넣지 않으므로 **`bootJar`만 부르는 지금은 안전하고, `build`나 `check`로 바꾸는 순간 CI는 통과하고 배포에서만 죽는다.**
- 위반 고치기: `./gradlew spotlessApply`. 판정 확인: `./gradlew spotlessCheck`. 대상은 develop과 다른 파일뿐이다. develop에서는 판정 대상이 0개라 항상 통과한다 — 통과가 곧 "전체가 규칙에 맞다"는 뜻이 아니다. 실측 2026-08-11: 509개 중 419개가 탭 들여쓰기(규정은 스페이스 2).
- **들여쓰기 규정이 두 개다** (2026-08-11 실측, DERO-613). 위 줄의 "규정은 스페이스 2"와 `.claude/rules/java/architecture.md` §3의 "들여쓰기는 탭"(정본)이 정면으로 어긋난다. 그래서 탭 파일을 한 줄만 고쳐도 `spotlessCheck`가 **전체 탭→스페이스 재포맷**을 요구하고(`CommunityErrorCode` 114줄→102줄), `spotlessApply`는 "편집한 파일 전체를 재포맷하지 마라"(architecture.md 규칙 3)를 깨는 리뷰 불가능한 diff를 만든다. 어느 쪽으로 통일할지는 **DERO-619**가 결정한다.
- 함정: 스테일 캐시 상태에서 돌리면 위반이 파일마다 `google-java-format(InvocationTargetException)`으로 위장해 도구가 깨진 것처럼 보인다. `--rerun-tasks`로 다시 돌리면 실제 diff가 나온다.
- 포매터 값은 `docs/GoogleStyle_custom.xml`(INDENT 2 · CONTINUATION 4 · RIGHT_MARGIN 100)과 일치하는 google-java-format 기본값이다. 스킴을 바꾸면 `googleJavaFormat` 버전·설정도 같이 바꾼다 — IntelliJ Reformat과 spotless가 다른 답을 내면 저장할 때마다 서로 되돌린다.

## 2. 스토리지·프리사인·AI 이미지 포트

<!-- moved from CLAUDE.md 2026-08-10 (DERO-546, H-21); staged in .claude/rules/backend/storage-and-ai-ports.md until 2026-08-14. Verbatim — not summarised. -->
원본: `backend/dero-api/src/main/java/com/brunchies/dero/infra/CLAUDE.md` 전문 (머리말 3단락 + 함정 전체). 규칙은 `.claude/rules/backend/storage-and-ai-ports.md`.

### infra — external boundary ports

Of the 3 ports named in `package-info.java` (object storage · AI concept image · recommendation engine), **storage and AI concept image are implemented** (recommendation engine is not yet). Living here: the 2 `StoragePort` implementations (`LocalFileStoragePort`/`S3StoragePort`) and the 2 implementations of the presign-issuing port `PresignPort` (`S3Config`/`S3PresignService`, `LocalFileSigner`/`LocalPresignService`/`LocalFileController`). Config is unified in one `StorageProperties` (`@ConfigurationProperties(prefix = "app.storage")`) — a new `app.storage.*` key means a new field there.

**`app.storage.mode` selects all four implementations** (presign fixed 2026-07-31, approved 박동규 — two-step upload must work both locally without S3 credentials and in prod before S3 is deployed; `StoragePort` 2026-08-02, DERO-357). `s3` → `S3PresignService`+`S3StoragePort`; `local` (default, `matchIfMissing=true`) → `LocalPresignService` issues a URL the WAS itself HMAC-signs and `LocalFileController` (`PUT`/`GET /api/v1/local-files/{*key}`) receives it and puts/gets bytes on the local volume through `LocalFileStoragePort`. Domain services know only `PresignPort` — never inject a concrete type. **Exactly one implementation per mode** — one unconditional implementation extra and both beans come up and injection dies at startup; conditioning only one side causes the "presign and StoragePort must see the same mode" accident below. `StorageModeTest`·`ImageGenerationModeTest` enforce this mechanically.

**The AI concept-image port is selected by `app.image.generation.mode`** (2026-08-02, DERO-354 — same idiom as presign's `app.storage.mode`). `stub` (default, `matchIfMissing=true`) → `StubImageGeneration` echoes the screenshot key back; `gms` → `GmsImageGeneration` calls `gpt-image-2` through the GMS proxy, decodes base64 and puts it in `StoragePort`. **The call path is selected once more by `app.image.generation.request-type`** (2026-08-02, DERO-358) — `edits` (default) posts the screenshot PNG as multipart to `POST /v1/images/edits`, `generations` is the old text-prompt-only path; both share response parsing and storage. Config is `ImageGenerationProperties` (`@ConfigurationProperties(prefix = "app.image.generation")`) — **it cannot live on the `image` package's `ImageProperties` because `infra` may not import a domain** (`LayerDependencyTest`). Only the prefix sits under `app.image`; `ImageProperties` ignores unknown keys so there is no clash.

### Traps

- **Spring 7's `SimpleClientHttpRequestFactory` sends chunked when `Content-Length` is absent — the cloudflare in front of GMS rejects that with a 400 HTML page and concept images fail 100% in prod.** Symptom is the worker log line `GMS 이미지 생성 실패: status=400 BAD_REQUEST, body={"message":"[OpenAI 에러] ...","error":"<html> ... <center>cloudflare</center> ..."}`; because the body wears an OpenAI error message and **local and CI both pass** (`MockRestServiceServer` replaces the request factory wholesale so the transport layer never runs), you end up suspecting the model name, API key, Korean prompt text, image size in turn. All innocent — `curl` from the prod server with the real screenshot and prompt returns 200, and **adding only `-H "Transfer-Encoding: chunked"` to the same request reproduces that 400 HTML** (measured 2026-08-02). Proximate cause: `SimpleClientHttpRequest` (Spring Framework 7.0.8) uses fixed-length if `headers.getContentLength() >= 0` and otherwise calls `setChunkedStreamingMode`, and `FormHttpMessageConverter` does not set `Content-Length` on multipart. Spring 7 removed `setBufferRequestBody`, so **wrapping in `BufferingClientHttpRequestFactory` is the only fix** (`GmsImageGenerationConfig`). **Downgrading to `request-type=generations` does not save you** — the JSON path 400s the same way when chunked. Regression: `GmsRestClientTransferEncodingTest` starts the JDK's `com.sun.net.httpserver.HttpServer` and checks over a real socket.
- **presign and `StoragePort` must see the same mode — mismatched, rows insert fine and every image 404s.** Before 2026-08-02 the only `StoragePort` implementation was `LocalFileStoragePort`, so turning on `mode=gms` in prod (`app.storage.mode=s3`) wrote GMS's PNGs to **container-local disk** while presign pointed at **S3** (the same shape of accident is already recorded in `dero-api/CLAUDE.md`). `S3StoragePort` (DERO-357) closed that hole, and the whole guarantee is that both are conditioned on the same `app.storage.mode` — **add new implementations with the condition in pairs.**
- **`S3StoragePort.store` infers `Content-Type` from the key extension.** The port signature has no contentType; without it S3 stores `application/octet-stream` and **a presigned GET downloads the PNG instead of rendering it** — the API is 200 and the file is intact, so it gets misdiagnosed as a frontend bug. Paired with `LocalFileController.download` inferring the same way (`S3StoragePortTest` pins it).
  - **That inference runs on `store` only — it is absent from the read path, which is why a `.png` key holding webp bytes does not break.** A presigned GET makes S3 return **the stored `Content-Type` verbatim**; `S3StoragePort` is not involved. The 2026-08-05 one-off backfill (`scripts/webp-backfill.mjs`) stands on that fact — it overwrote existing images **at the same key** declaring only `Content-Type: image/webp`, taking 508.6 MB of served images down to 44.5 MB with **zero DB, backend or frontend change** (originals kept under `originals/`). The one price is a key extension that no longer matches its content; new uploads avoid it because the frontend now sends a `.webp` filename (`frontend/src/components/admin/CLAUDE.md`). **Read the item above as "the extension decides the served type" and you will judge that backfill unsafe** — it only governs the `store` path (AI concept images).
- **A multipart file part without a filename goes out as a value part — upstream answers "you sent no image".** `ByteArrayResource.getFilename()` is `null` by default, so the `image` part becomes a plain value, not a file. It compiles and the request comes back 4xx rather than 200, so you suspect the prompt or the key. That is why `GmsImageGeneration.screenshotPart()` pins a filename with an anonymous subclass.
- **A fixed output resolution defeats the whole point of `edits` — hence `size: auto` as the default** (re-verified 2026-08-02). The screenshot is the frontend's raw 3D canvas dump, so its aspect ratio varies by viewport and dpr; send a fixed `1024x1024` and upstream reframes to that ratio — no matter how firmly the prompt says "preserve the layout", a different ratio forces cropping and recomposition. **The symptom looks like "the AI ignores instructions" so you go edit the prompt, but the cause is `size`.** Computed by `OutputImageSize` (long edge 1536, both edges multiples of 16, aspect ratio 1:3~3:1 — `gpt-image-2` constraints). If the PNG cannot be read, send `auto` and keep generating — failing to derive a size is no reason to mark the placement `FAILED`.
- **`read-timeout` × `IMAGES_PER_UPLOAD` must be smaller than `worker.processing-timeout`.** 120s was too short and was raised to 300s — OpenAI's docs cite up to 2 minutes for complex prompts. `read-timeout` bounds **one request**, so the comparison against the worker's 10 minutes is against the product, not the single value; exceed it and the sweeper treats the job as lost, then the reverted job answers late. **It is also paired with the frontend polling ceiling (`PUBLISH_POLL_TIMEOUT_MS`, currently 2 minutes)** — if polling is shorter, users get the "refresh to check" notice while generation is proceeding normally. Dropping to 1 image cut the worst case from 15 to 5 minutes, which is the first time that ceiling has been realistic.
- **An upload is one `n=1` call as of 2026-08-06** (D29, ADR-0025 — was three). The prompt preserves the captured camera exactly; the left/right three-quarter variants are gone with the images that needed them. **`n` itself still stays 1 and the loop stays** — one response holding several images cannot assign a stable role (angle) per image and produced repeated viewpoints (measured 2026-08-05), and the loop is what makes going back to N a one-line constant change. Total request time is `read-timeout × IMAGES_PER_UPLOAD` and must stay below `worker.processing-timeout`.
- **`request-type` is a downgrade switch — do not delete it.** Whether the GMS proxy accepts multipart is **unmeasured** (no key, so no live call). If it is rejected, `IMAGE_GENERATION_REQUEST_TYPE=generations` must be able to drop to the text-only path and revive concept images without a redeploy. That is also why both paths share response handling — if the downgrade touched storage or key assembly it would be that day's second bug.
- **`RestClient` assembly — 규칙은 `.claude/rules/backend/storage-and-ai-ports.md`.** 근거: `MockRestServiceServer.bindTo(builder).build()` plants a mock request factory in the builder, and a constructor that then attaches timeouts via `.requestFactory(...)` overwrites the mock. It compiles and (given a network) the test passes, so it stays invisible. Hence `GmsImageGenerationConfig` builds the finished `RestClient` bean and `GmsImageGeneration` receives it injected.
- **Do not use `IllegalStateException` for startup fail-fast — `ExceptionConventionTest` blocks it** (ADR-0012 decision 4's ban list; the rule is frozen so **only new violations** go red). Bean creation failure is not request handling and not a place to attach `BusinessException` + an HTTP status — Spring's `BeanInitializationException` is the right one.
- **When switching binding style (`@Value` → `@ConfigurationProperties`), search the class javadoc too.** After `S3Config` moved to `StorageProperties`, its class javadoc kept saying "bound explicitly with Spring `@Value`" for a while (caught in review 2026-07-29). Grep the old annotation name in javadoc and fix it in the same change.
- **`@Lazy` on a `@Bean` is nullified when the injection point is non-lazy.** `S3Config.s3Presigner` had `@Lazy`, yet `S3PresignService` (`@Component`) took `S3Presigner` through its constructor without `@Lazy` at the injection point, so the real bean was created the instant that service was — no proxy in between. `@Lazy` on `@Bean` only marks the bean as a lazy-init candidate; inserting the lazy proxy is the injection point's `@Lazy` (`public S3PresignService(@Lazy S3Presigner s3Presigner, ...)`). What it looked like: **47 backend tests failing to boot the context**, innermost cause `region must not be blank or empty.` (`authController → userService → s3PresignService → s3Presigner`) — the symptom "no test comes up at all" points you at test config and profiles, but the cause is the injection point. **It never showed in prod** — `compose.yaml` injects `AWS_REGION: ${AWS_REGION}` from `.env`, so region is filled; only tests and credential-less local `bootRun` are empty. Do not work around it with a dummy `AWS_REGION` in the test profile — that leaves `@Lazy`'s intent a lie and local boot still dies. (measured 2026-07-30, DERO-279)
  - **Resolved — all 4 `@Lazy` were deleted 2026-08-02 and `S3Config` became conditional on `mode=s3`** (approved 박동규). What `@Lazy` was trying to say is "do not create this bean in environments that do not use S3", and that is a condition, not laziness — both consumers (`S3PresignService`·`S3StoragePort`) already carried `@ConditionalOnProperty(mode=s3)` from DERO-357, so the issuing side got the same condition. The mechanism above is still valid knowledge, but that shape no longer exists in this codebase. **If you find yourself wanting `@Lazy` to defer a startup failure, read it as a missing condition.** The price is that failure moves from the first request to startup, and that is the point — prod-only config omissions have surfaced only at deploy three times (`dero-api/CLAUDE.md`).
- **`LocalFileStoragePort` is back, but its only caller is `LocalFileController`, not a domain** (2026-07-31). Until that morning it was dead code: its only user, `PlacementService.saveThumbnail/loadThumbnail`, moved to two-step presign in the API redesign (DERO-304), removing the path that put and got bytes on local disk; it was kept rather than deleted as one of ADR-0001's 3 ports. The `mode=local` decision realized that revival candidate. **Never call `StoragePort` from a domain** — a domain knows only `PresignPort`, and only `LocalFileController` touches bytes. (`StoragePort.delete(key)` still has no caller — added ahead of one, 2026-07-29.)
- **The controller taking `{*key}` is the only defense against path traversal.** `LocalFileStoragePort` resolves the key straight through `baseDir.resolve(key)` — the justification for not validating was "the key is assembled by a domain service", which no longer holds now that keys arrive in the URL. Remove the `..` rejection in `LocalFileController.verified()` and files outside `app.storage.local-dir` become readable. **Signature verification does not cover this** — the signature only answers "did we issue this URL" and never inspects the key's content. The day some issuing path mixes user input (a filename, say) into a key, `../` passes with the signature intact.
- **`mode=local` signing rules are written in exactly one place, `LocalFileSigner`.** If issuing (`LocalPresignService`) and verification (`LocalFileController`) each hold their own copy, fixing one side **still compiles** and every URL becomes 403. The signed payload is `method + "\n" + key + "\n" + exp` and **the separators are required** — plain concatenation makes `key="a1", exp=234` and `key="a12", exp=34` the same string, which lets expiry be stretched (`LocalFileSignerTest.서명_경계_모호성` pins it).
- **The port name in `package-info.java` does not match the real interface name.** The doc calls this port `ObjectStorage`; the actual interface is `StoragePort` (confirmed 2026-07-29) — you can search and fail to find it. Not renamed; get 박동규's confirmation first if needed.

## 3. 업로드·이미지 생성 파이프라인

<!-- moved from CLAUDE.md 2026-08-10 (DERO-546, H-21); staged in .claude/rules/backend/upload-image-pipeline.md until 2026-08-14. Verbatim — not summarised. -->
원본: `backend/dero-api/src/main/java/com/brunchies/dero/image/CLAUDE.md` 전문. 규칙은 `.claude/rules/backend/upload-image-pipeline.md`; 엔드포인트 계약 정본은 `docs/context/api-spec.md` §4.

### image — AI imagery + upload pipeline

Root is `GeneratedImage`. Feed-entry gate, Redis queue, stub worker live here.
Design: `docs/adr/0015-placement-upload-async-pipeline.md` · stub decision `docs/CONTEXT.md` D27-보 · API surface `docs/context/api-spec.md` §4.

### Traps

- **`PUT`/`DELETE /placements/{id}/feed-entry` lives here, not in `placement`.** Gate ③ is the daily image quota, counted from `generated_image`; dependency is one-way `image → placement` (`LayerDependencyTest.placement는_위를_모른다`), so `placement` cannot see that table. URL = resource layer, package = dependency layer. The `docs/context/backend-api SPEC` module table ("feed-entry gate is placement") is a sketch; the machine rule wins.
- **Editing tags after publishing is `PUT .../feed-entry/tags`, never a second `PUT .../feed-entry`.** That endpoint is the retry button, so re-calling it sends a `PUBLIC` placement back to `PENDING`, regenerates the image and charges daily quota — for a one-word tag edit. `FeedEntryService.replaceTags` skips every gate and only swaps the junction rows, then republishes `PlacementChangedEvent` so the search document follows. **Its request body inverts `FeedEntryRequest`'s `null` rule** (`@NotNull`, empty = clear all): there is no retry call here, so "unchanged" has no meaning to express.
- **Gate order is the contract: ①judge ②screenshot ③quota ④transition+enqueue.** Judging late burns generation cost plus quota, then reverses an "uploaded" message minutes later. **`CONDITIONAL` does not block** — it means catalog spec is unregistered, not that the placement is wrong; blocking lets our missing data block a user's publish. Only `INCOMPATIBLE` blocks.
- **Read the placement under judgment via `PlacementRepository.findForJudgmentById`.** `PlacementJudge` branches on `PlacedItem.product` with `instanceof`; **a LAZY proxy makes every branch silently false and judgment rows vanish**. Symptom is not an exception but **"zero violations"**, misread as a pass. The save path is safe only because merge just set concrete types, not because `instanceof` is safe.
- **Enqueue in `afterCommit`.** Inside the transaction the worker picks up a still-`PRIVATE` placement and drops it — job lost, user waits forever. Inverted in tests: a `@Transactional` MockMvc test never commits, so nothing enters the queue and happy-path assertions go false (use `Propagation.NOT_SUPPORTED` + truncate isolation).
- **Idempotency belongs on the consume side, not the request side.** The guard in `publish()` (no-op unless `PENDING`) blocks three accidents: ①a late job re-publishing a placement the user took down via `DELETE .../feed-entry` ②duplicate publish writing more image rows and charging quota twice ③two overlapping publishes where the primary-row partial unique kills the later one, leaving good rows but a `FAILED` placement. **Do not guard in `requestFeedEntry`** ("skip if already `PENDING`") — enqueue is `afterCommit`, so a Redis drop in that window leaves DB `PENDING` with an empty queue, and blocking re-enqueue makes that placement unrecoverable by any user action.
  - **Since 2026-08-06 the guard runs twice, and both are load-bearing.** `publish` splits into `prepare` (short tx) → generation **outside any transaction** → `attach` (short tx), so the user has minutes to withdraw while the image is being made; only `attach`'s re-check closes that window, and when it fires the finished image is thrown away on purpose (an explicit cancel must win, and unwritten rows charge no quota).
- **The external generation call must stay outside the transaction, and `@Transactional(propagation = NEVER)` on `publish` is what keeps it there.** Delete it and the class-level `readOnly = true` revives: both `TransactionTemplate` blocks join it under REQUIRED, so ①it is one long transaction again (GMS `read-timeout` is 300s — a pooled connection and `demotePrimaries`' row locks held that whole time) and ②Hibernate's read-only `FlushMode.MANUAL` makes the **INSERTs silently vanish**. **No functional test catches the first half** — status transition and row count pass either way — so `GeneratedImagePublishTransactionTest` asserts `isActualTransactionActive()` at the port call and the committed write together. Rationale: ADR-0025 decision 3.
  - **`NEVER`, not `NOT_SUPPORTED`** (2026-08-06). Both neutralize the class-level `readOnly` — a method-level `@Transactional` replaces the class-level one rather than merging with it — so they are identical while the only caller (`ImagePublishWorker`) has no transaction. They diverge the day one appears: `NOT_SUPPORTED` **suspends** it, and a suspended transaction still owns its connection, so the 300s hold this whole design exists to prevent comes back with nothing to see. `NEVER` throws `IllegalTransactionStateException` instead. Locked by the second case in `GeneratedImagePublishTransactionTest` — the first two assertions pass under either propagation.
- **Make queue ops fail toward duplication, never loss.** `requeueStale` pushes back to the waiting list **first**, removes from processing after; the reverse order loses the job entirely if it dies between the two commands and the placement stays `PENDING` forever. Same reason `complete` clears the claim timestamp first (leftovers pile up in a hash field nobody reads, with no TTL). **Duplicates are absorbed by the consume-side guard above; loss is absorbed by nobody.**
- **`complete`/`requeueStale` need the original payload string** — Redis `LREM` deletes by value, so `claim` returns `ClaimedJob(payload, job)` rather than just the deserialized result. Re-serializing to delete leaves a ghost in the processing list on any one-character drift (field order, time format), and the sweeper resurrects that ghost forever.
- **`GeneratedImage.createPrimary` allows one row per placement** — partial unique `uq_generated_image_placement_id ... WHERE is_primary` enforces it in DB. Re-upload = **one transaction: `demotePrimaries` first, then the new primary**; that bulk UPDATE clears the persistence context, so **re-read the placement afterwards** or the following `markPublished()` misses dirty checking.
- **`IMAGES_PER_UPLOAD` is the one source of truth for how many images an upload makes — 1 since 2026-08-06** (was 3; D29, ADR-0025). The port request's `count`, the contract check in `publish`, the detail-list `Limit`, and the quota pre-charge all read it. **Never write the number anywhere else**, and don't "simplify away" the port's `count`, `GmsImageGeneration`'s loop, or the frontend's 2-column grid just because they now run once/render nothing — keeping them is what makes going back to N a one-line change. The left/right three-quarter prompts in `DeskScenePrompt` **were** deleted (unreachable, and a stale angle instruction would corrupt the single image); restore those if N ever returns.
- **Daily quota counts `generated_image` rows, so stub consumption really charges.** D27-보 ("stub does not charge quota") is **not literally implementable** — no column distinguishes stub rows from real ones and the schema doc is frozen. Single decision point is `FeedEntryService.requireWithinDailyQuota`, so a billing or marker column would change only that. Tuning: `app.image.daily-quota` (default 7 = 7 runs at 1 image each; it was 21 = 7 runs at 3). **Awaiting 박동규 decision.**
- **"How images are made" sits behind `infra/ImageGenerationPort`** (2026-08-02, DERO-354). `GeneratedImageService.publish` only **receives** keys and writes rows; the stub↔GMS switch is `app.image.generation.mode` alone. The contracts this service keeps (state machine, `IMAGES_PER_UPLOAD` rows, 1 primary, queue, API) hold under any implementation — **changing mode must never require editing this package.**
  - `publish` reads via `findForJudgmentById` for prompt material (desk texture/frame + placed product names); `findByIdAndDeletedAtIsNull` does not fetch items, costing one query per product. Same fetch join as the judgment path, same soft-delete filter.
  - Domain values are passed **flattened to strings** (`ImageGenerationRequest`) — `infra` cannot import `Placement`/`DeskTexture`/`FrameType` (`LayerDependencyTest.infra는_도메인을_모른다`).
- **The stub writes the screenshot key straight into the row** — no file copy in storage. The domain knows only `PresignPort` and only `LocalFileController` touches bytes (`infra/CLAUDE.md`), and S3 mode has no copy op on the port. So in stub mode the concept image *is* the screenshot file.
- **Worker flag off = the bean does not exist** (`@ConditionalOnProperty`) — "no loop", not "thread up doing nothing", so tests and local are visibly not bound to the Redis queue. **`application-prod.yaml` turns it on; off means every upload stalls in `PENDING`.**
- **Redis also holds refresh tokens** (ADR-0005). `ImagePublishQueue` touches only its own 3 keys — no global commands like `FLUSHDB` here. Blocking `BLMOVE` uses a dedicated Lettuce connection (`LettuceListCommands.bLMove` → `getAsyncDedicatedConnection`), so it does not pin the shared connection and stall token lookups.
- **No presigned URL in queue messages** — presign has a TTL, queue wait has no upper bound, so a late worker gets an expired URL. ADR-0015 decision 5 shaped the message as `sourceImageUrl` + `uploadTargets[3]`; **this implementation carries only `{placementId, requestedAt}`** (presign issued when the worker claims). **That message shape will never be built** — the local-notebook python worker was scrapped 2026-08-06 (D29, ADR-0025) and the generator now lives inside the WAS, writing bytes through `StoragePort` directly.
- **Redis integration tests extend `AbstractRedisIntegrationTest`** — Redis is not stacked onto the Postgres base because dozens of queue-less integration tests should not pay the container cost. `@ServiceConnection` is unusable: Boot 4.1 `spring-boot-testcontainers` has no Redis `ConnectionDetailsFactory` (verified in the jar). Wire it with `@DynamicPropertySource`.

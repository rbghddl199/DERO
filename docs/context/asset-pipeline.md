> 읽는 시점: 에셋 등록·검수·규격 DB(REQ-ADM-*) 작업 시 (루트 CLAUDE.md 라우팅 표에서 진입).
> 관련 결정: `docs/CONTEXT.md` D6(운영 정책)·D7(기술 원칙)·D5(조명 광학 규격)·D16(관절 가동)·D18(책상·모니터는 파이프라인 대상 아님 — 전량 절차 생성)·D19(소품 전량 GLB화, 파라메트릭 폴백 폐지).

## 확정 규칙

### 제품 중심 에셋 모델 (2026-07-17 확정, 승인 박동규)
- **모든 배치 아이템은 제품 단위 선택이다.** 책상·선반 등 단순 형상도 규격만으로 존재하지 않는다 — 같은 1400×700 상판이라도 제품의 재질(원목·메탈·플라스틱 등)·텍스처에 따라 무드가 달라진다
- **제품 데이터 = 규격 + 비주얼 변형**
  - 규격: mm·하중·관절 한계각(D16)·광학(D5) — 판정의 정본
  - 비주얼 변형: 전용 GLB 참조(재질 포함) 또는 `asset.finish` 프리셋·텍스처 세트·코드 상수 — 무드의 정본. 어느 쪽인지는 아래 "재질 정본은 네 갈래다" 참조
- **절차 생성 지오메트리는 치수 가변 파트에만 남는다 (2026-07-23 개정, 승인 박동규. D19)** — 파라메트릭 **제품**은 폐지됐고, 책상 상판·모니터 전체(D18, 모니터는 2026-08-02 재개정)만 런타임 절차 생성으로 남는다. 따라서 "제품마다 머티리얼 스킨 1세트 필수"도 폐기다
- **재질 정본은 네 갈래다.** 판별식은 export 모드 단독이 아니라 **제품 종류를 먼저 보고, `asset` 행이 있는 제품만 export 모드로 가르는** 2단 판별이다 — 위에서부터 순서대로 따져 먼저 걸리는 갈래가 정답이다
  - **① 책상이면 → `desk_texture`가 정본** (재질 4종: 월넛·오크·블랙·화이트). 책상은 `asset` 행 자체가 없어(D18) export 모드가 존재하지 않는다
  - **② 모니터면 → 코드 상수가 정본** (2026-07-23 확정, 승인 박동규). 절차 생성 파트지만 등록 모니터 2종의 값이 완전히 같고 이를 읽는 요구사항·UI가 없어 DB 컬럼으로 올리지 않는다. 모니터도 책상처럼 `asset` 행이 없어(D18 2026-08-02 재개정 — 하이브리드 폐기) export 모드가 존재하지 않는다
  - **③ 그 외 `asset` 행이 있고 `glb_export_mode = 'TEXTURE'`면 → GLB 자신이 정본.** 별도 재질 입력이 없다. 등록 제품 대부분이 여기 속한다
  - **④ 그 외 `asset` 행이 있고 `glb_export_mode = 'PART_SEGMENTATION'`이면 → `asset.finish`가 고른 코드 프리셋이 정본** (2026-07-23 개정, 승인 박동규). part-seg export는 텍스처를 받을 수 없어 재질을 따로 정해야 하는 유일한 집합이다. DB가 받는 것은 **어느 프리셋인지 하나뿐**이고 PBR 수치는 코드가 갖는다:

| `asset.finish` | 뜻 | 대응 재질 분류(코드) |
|---|---|---|
| `CLEAR_ACRYLIC` | 투명 아크릴 | `glass` — transmission·ior |
| `METALLIC` | 메탈릭 | `metal` |
| `WHITE` | 화이트 | `plastic` 밝은 값 |
| `BLACK` | 블랙 | `plastic` 어두운 값 |

  - **수치를 DB로 올리지 않는 이유**: `frontend/src/three/render/materials.ts`의 `materialForSkin()`이 이미 재질 분류별로 clearcoat·transmission·ior·거칠기를 코드에서 강제한다. 색·거칠기·금속성을 DB에서 또 받으면 정본이 둘이 되어 어긋나고, 등록자가 수치를 흔들면 D17 아트 디렉션 일관성이 깨진다. 등록 입력도 숫자 3개에서 드롭다운 1개로 준다. 정확한 수치는 이 문서에 박지 않는다 — 코드 소관이다
  - **한계: 에셋 하나에 마감 하나다.** 로더가 전 메쉬에 같은 재질을 입힌다. 몸통 블랙 + 관절 메탈 같은 투톤이 필요해지면 그때 `asset_part_material`(1:N) 신규 테이블이지, 컬럼을 늘리는 게 아니다
- 무드 시뮬레이션(D5)이 성립하려면 재질이 제품마다 실제로 달라야 한다 — 이 원칙은 D5의 전제. 재질이 GLB 안으로 들어갔을 뿐 전제 자체는 그대로다

### 기존 규칙
- MVP 파이프라인: 생성(Meshy·Tripo·Rodin — 운영진 전용) → 검수 → 보정 → 경량화
- glTF 2.0 = 미터 단위. 로드 후 Three.js Box3 실측 → 규격 DB 값으로 **균일** 스케일
- 비균일 스케일 금지. 내부 비율 오차 5% 초과 = 재생성. Meshy auto_size 신뢰 금지 — 규격 DB가 정본
- **관절 제품군은 4종이다 (2026-07-23 확정, 승인 박동규)** — 모니터암·마이크암(`spec_type = ARM`, `arm_kind`로 구분)·노트북 거치대·휴대폰 거치대(`spec_type = PROP`). 넷 다 **part-segmentation export + 리그 매니페스트**(아래 2026-07-18 절)로 만든다. **파트 식별·관절 도출이 불가한 제품은 관절 없는 정적 에셋으로 등록한다** — 파라메트릭 제네릭 폴백("제네릭 에셋 + 규격 스킨")은 폐지됐다(2026-07-23, D19). 관절을 가짜로 만들지 않는다
  - **이 4종은 텍스처를 입히지 않고 파트 분할 상태 그대로 받는다.** 재질은 등록자가 고른 `asset.finish` 프리셋을 로더가 입힌다(위 재질 정본 4갈래 중 ④). 텍스처를 넣으려고 `TEXTURE`로 재export하면 파트가 융합돼 관절을 잃는다
  - **리그 매니페스트의 저장 자리는 `asset.rig_manifest`다** (2026-07-23 개정 — 그전엔 `arm`). 매니페스트가 GLB 파트 이름에 묶여 있어 제품 규격이 아니라 에셋 파일에 종속이고, 거치대 2종은 `PROP`이라 `arm` 테이블에 자리가 없었다
- **관절 종류별 구성 참조표 (2026-07-25, ADR-0002 결정 8-2)** — 저작자가 "이 제품엔 관절을 뭘 넣지?"에 답할 표. 관절 종류가 `revolute`(회전)/`prismatic`(직선) 판별 유니온으로 확장됐다(결정 1) — `RigJoint`는 `kind`·`label`(표시명, 필수)을 갖고, 평행사변형 링크 등은 `coupledTo`(driver·ratio·offset)로 종속 관절을 표현한다(결정 2)

  | 제품 | `spec_type` | 전형 관절 구성 | 가동값 정본 | 카탈로그 표기 컬럼 |
  |---|---|---|---|---|
  | 모니터암 | `ARM` | base-yaw·shoulder-pitch·elbow-pitch·head-tilt·head-swivel·head-pivot | `rig_manifest` | `arm.tilt_*`·`swivel_range_deg`·`pivot_range_deg`·`segment_count` |
  | 마이크암 | `ARM` | base-yaw·boom-pitch·boom-parallel(커플링) | `rig_manifest` | `arm.tilt_*` 등(피벗 없음) |
  | 노트북 거치대 | `PROP` | lift(`prismatic`)·tilt | `rig_manifest` | 없음(`prop`에 각도 컬럼 미추가, D19·erd.md) |
  | 휴대폰 거치대 | `PROP` | ball(yaw+pitch 스택) | `rig_manifest` | 없음 |

  **이 표는 전형이지 필수가 아니다 — 실물에 없는 관절은 뺀다**(ADR-0002 결정 6). 등록된 `monitor-arm`은 실제로 shoulder-pitch가 없어 관절이 5개다.

  **저작은 `/dev/rig`에서 한다 (2026-07-25, DERO-155).** 운영진 전용 데브 라우트다 — 제품을 고르면 GLB 파트 목록이 뜨고, 파트를 논리 세그먼트로 묶고 관절의 축(정축 6버튼)·피벗·한계를 정한 뒤 `product.ts`에 붙여넣을 TS 블록을 복사한다. 편집할 때마다 `validateManifest()`가 돌고 **통과할 때만 미리보기 슬라이더가 활성**이라, 반쯤 조립된 계층을 "됐다"고 오독할 수 없다. 피벗 기본값은 **부모∩자식 bbox 교집합의 중심**을 제안하는데 `monitor-arm` 5관절 실측 대조 오차가 2.1~11.5mm였다 — **기본값은 출발점이고 저작자가 Y·Z를 손보는 것이 정상 절차다.** 손으로 좌표를 적던 이전 방식은 폐기다.
  > **한계**: 이 화면의 로더는 KTX2를 붙이지 않는다. 리그 대상이 텍스처 없는 part-seg GLB라 지금은 맞지만, 텍스처가 박힌 GLB는 이 화면에서 열리지 않는다.

  > **등록 검수 게이트**: 매니페스트는 `validateManifest()`(`frontend/src/three/core/rig.ts`)를 통과해야 등록한다. 종류별 필수/금지 필드는 ADR-0002 결정 8-1 표가 정본이다. **가동 범위의 런타임 정본은 항상 `asset.rig_manifest`이고 `arm`의 각도 컬럼은 카탈로그 표기·필터 전용** — 같은 값을 두 곳에 넣지 마라.
- **사용자 업로드는 MVP 범위다 (2026-07-23 개정, 승인 박동규. D20)** — 이전 "정식 서비스 비전 — MVP 범위 아님" 서술을 거둔다. 사용자가 GLB + 카테고리별 규격을 직접 올리고(REQ-COM-09), 운영진이 승인·반려한다(REQ-ADM-04).
  - **운영진 파이프라인(위 4단계)과 갈리는 지점**: 생성·보정·경량화가 업로더 몫이라 운영진은 **검수만** 한다. 스케일 정합·비율 오차 5% 같은 위 규칙은 그대로 검수 기준이 된다 — 규칙이 느슨해지는 게 아니라 강제 시점이 등록에서 검수로 옮겨간다.
  - **검수 상태는 `asset.review_status` 3값**(`PENDING`/`APPROVED`/`REJECTED`, 기본값 `PENDING`). 대기·반려여도 업로더 본인 배치에는 쓸 수 있고, 남에게 보이는 건 `APPROVED`부터다. 반려 사유는 `asset.review_note`
  - **미인증 경고 문구는 승인 후에도 뜬다** — 승인은 "봤다"지 "실측을 보증한다"가 아니다. 규격이 자기신고라 `product.source = USER`인 제품에 D6 문구를 붙인다: "인증되지 않은 사용자가 올린 자료로, 실제 규격과 다를 수 있습니다"
  - **책상(`spec_type = DESK`)과 모니터(`MONITOR`)는 업로드 대상이 아니다** — 둘 다 절차 생성이라 GLB 자체가 없다(아래 D18 항목). 대상은 암·조명·소품 3종(2026-08-02 개정 — 그전엔 모니터를 포함한 4종)
- **등록 대상 = 책상·모니터를 뺀 모든 제품 (2026-07-23 개정, 승인 박동규. D19 / 2026-08-02 모니터 제외)** — 이전 파라메트릭 프리미티브로 그리던 소품 전량(키보드·스피커·병·머그·화분·매트·램프 2종)이 GLB 등록 대상이 됐다.
  - **책상과 모니터가 파이프라인 대상이 아니다 (D18)** — GLB를 만들지 않고 규격 DB 값(또는 사용자 입력값)으로 런타임 절차 생성한다. 등록 대상은 규격 메타데이터와 책상 재질용 텍스처 세트뿐이다.
  - **모니터가 여기 들어온 것은 2026-08-02 재개정이다** — 2026-07-23의 "화면 패널만 절차 생성 + 스탠드·베젤 파츠 GLB" 하이브리드는 폐기됐다. 결합이 구현된 적이 없고, GLB를 등록하는 순간 프론트 인스턴스화 분기(`spec.glbUrl ? … : buildProp`)가 절차 생성을 건너뛰어 비균일 스케일이 발생한다. 근거 전문은 `docs/CONTEXT.md` D18.
  - **조명은 여전히 AI 생성 금지** — 광학 규격을 못 만든다(D5, 아래 절). 등록 대상이라는 것과 생성 수단은 별개다.

## 구현 세부 (2026-07-17 확정)

### 포맷·압축
- **GLB 전용**. 지오메트리 압축 meshopt(`EXT_meshopt_compression`), 텍스처 압축 KTX2

### 용량 예산 (2026-07-24 개정, 승인 박동규 — 실측 근거)

**예산은 물체 크기별로 갈린다.** 이전 "에셋당 100~500KB 일괄"은 폐기다 — 표면적이 123배 차이나는 에셋에 같은 상한을 요구했고, 소품은 통과하지만 대형은 물리적으로 도달 불가였다.

| 물체 최대변 | 텍스처 해상도 | 파일 상한 |
|---|---|---|
| ≤150mm 소품 | 1024² | 500KB |
| 150~400mm 중형 | 2048² | 1MB |
| ≥400mm 대형 | 2048² | 2.5MB |

- **초기 로드 ≤3MB / 전체 씬 ≤10MB는 그대로.** 대형 에셋은 씬에 1~2개뿐이라 lazy 로드로 방어한다(D19)
- **MetallicRoughness는 크기와 무관하게 512 고정** — 4096→512에서 PSNR 40.1dB로 손실이 안 보인다. metallic 채널이 사실상 전부 0(평균 0.4/255)이라 정보가 없다
- **Emit은 내용이 검정이면(최대 밝기 ≤16/255) 제거** — 파일보다 VRAM이 문제다. 4096² 검정 맵이 물체당 8.4MB를 먹는다

#### 해상도 판정 공식

**줌인 상한(화면 폭 25%, `3d-scene.md`)이 텍스처 해상도를 결정한다.** 텍셀 밀도가 화면 픽셀 밀도 이상이면 통과다.

```
화면px/mm      = 1920 × 0.25 ÷ 물체폭mm
필요 텍스처 변  = √( (화면px/mm)² × 표면적mm² ÷ UV점유율 )
                → 2의 거듭제곱 올림, 하한 512 · 상한 2048
```

실측 검증(렌더 스크린샷끼리 PSNR, 40dB 이상 = 육안 구분 불가):

| 에셋 | 폭 | 표면적 | UV점유율 | 공식 | 채택 | 실측 |
|---|---|---|---|---|---|---|
| 탁상 가젯 | 91mm | 24,962mm² | 73.7% | 970 | 1024² | 40.48dB 통과 (512²는 30.49dB 탈락) |
| PC 케이스 | 534mm | 3,083,700mm² | 49.6% | 2241 | 2048² | 1024²는 33.47dB 탈락 |

- **UV 점유율이 낮으면 해상도를 올리기 전에 UV를 다시 펴라.** 점유율 49.6%는 텍셀 절반을 버리는 것이고, 리팩만으로 파일 크기 증가 없이 선형 밀도 1.4배를 얻는다
- 자동화: `scripts/asset-pipeline.sh`가 해부·판정·경량화·검증을 한 번에 한다

> **위 표의 dB는 코덱 손실을 뺀 값이다 — 해상도 효과만 격리해서 잰 것이다.** 실제 배포본(KTX2/ETC1S)은 여기에 코덱 손실이 더해져 **렌더 PSNR 29.7~31.7dB**로 내려간다. 아래 "코덱 손실" 절을 반드시 같이 읽어라. 이 표만 보고 "우리 에셋은 40dB를 넘는다"고 말하면 틀린다.

#### 코덱 손실 — 해상도와 같은 급이다 (2026-07-24 실측)

**ETC1S는 공짜가 아니다. 텍스처를 절반 해상도로 줄이는 것과 맞먹는 값을 이미 지불하고 있다.**

| 무엇을 바꿨나 | 렌더 PSNR |
|---|---|
| 코덱만 ETC1S(`-tq 8`) | 29.7~31.7dB |
| 해상도만 1단계↓ (코덱 없음) | 28.5~33.6dB |

- **손실의 사실상 전부가 normal 맵에서 나온다.** 맵별로 하나씩만 코덱을 걸어 분해한 결과 — normal만 ETC1S = 29.9~32.2dB(**전체 ETC1S와 동일**), color만 = 42.2~43.6dB, attrib만 = 50.5~53.2dB. 텍스처 공간에서 0011 normal은 ETC1S 22.0dB인데 UASTC는 31.6dB다
- **`-tq 10`은 값어치 없다.** +0.14~0.45dB에 파일이 5~10% 커진다. ETC1S의 병목은 코드북 크기가 아니라 블록 구조라 품질 옵션으로 살 수 없다
- **`-tu normal`(normal만 UASTC)은 +7.4~8.9dB를 회복하지만 파일이 2.8~3.1배가 된다.** 같은 예산에서 겨루면 무승부이거나(0011) 해상도 쪽이 이긴다(0012) — 즉 지금 표의 해상도 선택은 예산 대비 최적이 맞다
- **PSNR이 두 손실의 성격 차이를 못 잡는다.** ETC1S는 디테일 밀도를 유지하고 값·위치를 틀린다(스페큘러가 블록 단위로 어긋남). 해상도 축소는 디테일을 아예 지운다. 같은 dB라도 "정밀해 보이는가"가 중요한 제품은 ETC1S@풀해상도가 낫게 보일 수 있다 — **최종 판정은 dB가 아니라 눈으로 한다**
- 측정 환경: 헤드리스 Chromium이 BC7(BPTC)로 트랜스코딩했고 GPU 포맷 단계의 추가 손실은 ≤0.05dB였다. **ETC2/ASTC만 지원하는 모바일은 미측정이다**

#### 배포 코덱 설정 (2026-07-24 확정, 승인 박동규 — 실측)

**normal 맵만 UASTC로 빼고 해상도를 절반으로 낮춘다. 나머지는 ETC1S 유지.**

```
gltfpack -i IN -o OUT -cc -tc -tq 8 -tu normal -tl normal <N/2> -tl color <N> -tl attrib 512
```

| 클래스 | 코덱 | 해상도 |
|---|---|---|
| color(baseColor·emissive) | ETC1S | 목표 N (위 판정 공식) |
| **normal** | **UASTC** | **N/2 (하한 512)** |
| attrib(MR·AO) | ETC1S | 512 고정 |

- **왜 normal만 UASTC인가** — 손실의 100%가 여기서 나온다(위 절). color·attrib은 ETC1S로 42~53dB라 손댈 이유가 없다
- **왜 normal 해상도를 절반으로 낮추나** — UASTC는 텍셀당 ETC1S의 5.4배다. 절반 해상도로 낮춰야 파일 예산에 들어온다. normal은 화면에서 소품 크기라 절반 해상도로도 렌더 차이가 파일 예산 대비 최적이다(RD 프론티어 실측)
- **왜 N/2로 통일하나** — 대형·소형 모두 "color 목표의 절반"이라 규칙이 한 줄이다. 소형(0012급)은 N/2 = 512가 하한과 만난다. 640으로 예산을 더 쥐어짜는 대안(+0.98dB)은 파일 여유가 2%로 얇아져 버렸다 — 512는 25% 여유를 남긴다
- **`-tu`에 `-tq`를 얹은 효과는 미측정이다.** `-tq 10`이 ETC1S에선 값어치 없었지만 UASTC 매핑은 확인 안 했다 — 기본값을 쓴다

실측 결과:

| 에셋 | 설정 | 파일 | 렌더 PSNR | 예산 |
|---|---|---|---|---|
| PC 케이스 | color 2048 / normal UASTC 1024 / attrib 512 | 2308KB | 31.86dB | 2.5MB 중 92% |
| 탁상 가젯 | color 1024 / normal UASTC 512 / attrib 512 | 375KB | 30.24dB | 500KB 중 75% |

- **40dB는 예산 안에서 도달 불가다.** 넘는 건 전체 UASTC(8798KB, 예산 3.5배)뿐 — 전체 ETC1S는 29.7~31.7dB에서 천장이라 예산 여유를 품질로 바꿀 방법이 없었다. normal-UASTC가 그 여유를 쓸 수 있는 유일한 계열이다
- 자동화: `scripts/asset-pipeline.sh`가 이 설정을 크기 구간에서 자동 산출한다

#### 화질 판정은 렌더 화면 기준이다

**텍스처 파일끼리 PSNR을 재면 안 된다.** 텍스처를 1:1 픽셀로 볼 때의 손실이라 실제 화면보다 훨씬 나쁘게 나오고, 필요 이상으로 큰 텍스처를 지불하게 된다. 같은 에셋이 파일 기준 26.9dB(탈락)에서 렌더 기준 40.5dB(통과)로 뒤집힌 사례가 있다. **동일 카메라·조명으로 렌더한 스크린샷끼리 비교한다.**

### 도구 함정 (2026-07-24 실측, 전부 직접 당한 것)

- **npm판 gltfpack(`npx gltfpack`)은 BasisU가 없다.** `-tc`·`-tw`·`-tl`이 전부 무동작이고 `gltfpack was built without BasisU support`만 뱉는다. [Releases](https://github.com/zeux/meshoptimizer/releases)의 네이티브 바이너리를 받아라. `scripts/asset-pipeline.sh`는 `$GLTFPACK` → PATH → `scripts/.bin/gltfpack` 순으로 찾고, npm판이면 "KTX2가 0개"라는 결과로 잡아낸다
- **텍스처 클래스 이름은 `color`·`normal`·`attrib`뿐이다.** `-tl c 2048`처럼 약자를 쓰면 `unrecognized texture class` 경고만 뜨고 **조용히 무시된다** — 출력 크기가 안 바뀌는데 명령은 성공한 것처럼 보인다
- **`npx gltf-validator`는 실행 파일이 없다.** 그 패키지는 `validateBytes` 라이브러리만 노출해 `could not determine executable to run`으로 죽는다. `npx -y @gltf-transform/cli validate --format csv`가 같은 Khronos 밸리데이터를 돌리고 severity 컬럼을 준다. **오류를 찾으면 종료 코드 1이라 "실행 실패"와 구분이 필요하다** — CSV 헤더 유무로 판별한다
- **gltfpack은 텍스처를 삭제하지 못한다.** 빈 Emit 제거는 GLB JSON을 직접 편집하는 사전 단계가 필요하다(`scripts/glb_strip_emit.py`)
- **gltfpack 출력의 KTX2 밉 체인은 정상이다**(`levelCount = log2(최대변)+1`). "밉이 없어 three.js가 `minFilter`를 강등한다"는 진단이 한 번 나왔는데 헤더를 뜯어 확인한 결과 거짓이었다 — 렌더가 이상하면 밉을 의심하기 전에 다른 곳을 봐라
- **Meshy의 emissive 맵은 신뢰할 수 없다** (2026-07-25 실측, `assets-raw/library` 12개 전수). Meshy는 emissive 슬롯을 **항상** 만들지만 12개 중 **9개가 완전 검정**(최대밝기 0~19, 발광픽셀 0.000%)이었다. 나머지 3종의 실패 방식이 각각 다르다: 흐릿한 노이즈(0007 — 최대 47이라 검정 판정을 통과하지만 64 넘는 픽셀이 0%), 정상 발광(0014 — 최대 144·발광 1.0%), **표면 전체 발광**(0017 — 최대 255·발광 **99.99%**, 조명이 emissive에 구워진 경우). **발광이 필요한 제품을 Meshy 산출물에 의존하지 마라** — 맵이 없는 것이 기본값이다
- **`EMIT_BLACK_MAX` 판정에 구멍이 둘 있다**(`scripts/glb_probe.py:28`). 판정이 `max_luma` 하나만 보기 때문에 ① **하한**: 뜨거운 픽셀 하나만 있으면 사실상 검정인 맵이 살아남는다(0004는 최대 19로 임계 16을 넘어 "유지"인데 발광픽셀은 0.001%다) ② **상한이 아예 없다**: 0017 같은 전면 발광 맵이 그대로 통과하고, 저작 규약대로 ×20을 곱하면 화면이 하얗게 탄다. **최대밝기가 아니라 발광픽셀 비율에 하한·상한을 둬야 한다**
- **컬러 베이크된 emissive를 흰 마스크로 바꿀 땐 `max(r,g,b)`를 써라.** 표준 luminance 가중치(`0.2126R+0.7152G+0.0722B`)를 쓰면 파란 발광이 죽는다 — 실측에서 luminance는 발광픽셀의 0.06%를 잃었고 `max`는 0.00%였다(2026-07-25). 마스크로 바꾸면 색이 `emissiveFactor`로 빠져 런타임 리컬러가 가능해지는 대신, 한 텍스처에 여러 색이 구워져 있던 구분(팬=파랑·스트립=마젠타)은 한 색으로 합쳐진다

### 발광 세그먼트 GLB 저작 규약 (2026-07-26 확정, 승인 박동규 — DERO-163)
가변 발광(리컬러) 제품의 "빛이 틈새로 새는" 룩 저작법. 첫 대상은 키보드 백라이트.
- **원리: 마스크가 아니라 지오메트리가 가린다.** 발광 파트를 별도 메쉬로 두고 비발광 파트가 물리적으로 덮으면 보이는 빛 = 틈새다. emissive 텍스처 페인팅 불필요 — ADR-0003이 예고한 "빌드타임 텍셀 마스크"는 세그먼트 분리가 불가능한 융합 메쉬의 폴백으로 격하한다.
- 키보드 기준 세그먼트 3개: `case` / `plate`(발광면) / `keycaps`(뭉치 1개 — 키 단위 분리 금지). 융합 금지, Apply Scale=1, 미터.
- **발광 지정 = 발광 메쉬 노드에 glTF extras `emitterSurface: true`** (Blender 커스텀 프로퍼티 1개). GLTFLoader가 extras를 `userData`로 옮겨 런타임 `selectEmitterMeshes`(frontend `emitters.ts`)가 그대로 읽는다. 표시 없는 GLB는 전 메쉬 발광 폴백(현행 유지).
- **가변 발광 파트는 emissive 맵을 굽지 않는다** — 색·세기는 런타임이 `placed_item.emitter_color`로 주입한다(리컬러 경로). Meshy emissive 신뢰 불가 문제(아래 도구 함정)도 같이 회피된다. 고정 발광(전구 유리 등)의 "emissive ×20 저작" 규칙은 별개로 유지.
- 압축: `asset-pipeline.sh`가 `-ke`(extras 보존)를 항상 준다 — gltfpack 기본은 extras 폐기라 이 플래그 없이는 발광 지정이 조용히 죽는다. 세그먼트 병합 방지는 **세그먼트별 재질 분리**로 담보한다(gltfpack은 동일 재질 메쉬만 병합) — 동일 재질 세그먼트가 필요해지면 관절 에셋처럼 `-kn -km`.
- 검수 추가 1줄: 발광 제품(`product_emitter` 행이 있는 제품)의 에셋은 `emitterSurface` 플래그 메쉬 ≥1 존재 확인.
- 온보딩 완료 시 절차형 `keyboard-tkl` 지오메트리는 제거한다(D19 정합 — 파라메트릭 폴백 폐지).

### 조명 GLB 저작 규약 (2026-07-30 확정, 승인 박동규 — DERO-228)
조명 GLB가 0장인 시점에 정했다. 대상은 차폐 기하(갓·격자·셰이드)를 가진 발광체. 기각 사유 전문은 228 티켓 코멘트, 맵은 `docs/context/lighting-map.md`.
- **광원 좌표 = `light_origin` 빈 노드.** 메쉬·자식 없는 glTF Empty, 이름은 정확히 `light_origin`, 제품 로컬 좌표(glTF 미터). **런타임 정본은 노드가 아니라 `product_emitter.point_x/y/z_mm`** — 등록 도구가 노드를 읽어 mm 정수로 변환해 넣고 런타임은 DB만 본다(정본 1개). 노드를 두는 값은 저작 정확도와 검수다: 갓을 옮기면 노드가 같이 옮겨져 아래 갓 조건이 깨진 것이 보인다. **이름 변경은 파괴적 변경**(관절 체크리스트와 같은 규칙).
  - **차폐 기하가 있으면 필수** — 없으면 bbox 중심 폴백이 걸리고 램프의 bbox 중심은 폴대 중간이라 조용히 틀린다. 반대로 모니터라이트·스크린바는 제품 전체가 곧 발광 바라 bbox 중심이 맞다. 그래서 **`shape`로 기계 강제하지 않는다** — `SPOT`이 곧 "갓이 있다"는 뜻이 아니고, 강제하면 바형 제품을 헛되게 묶는다. `erd.md`의 `point_*_mm` 규칙(nullable, 셋 다 or 셋 다 NULL)은 그대로다.
- **갓이 빛을 실제로 깎으려면 `atan(rBot / H) < 빔 반각`.** `rBot` = 갓 아랫테 반경, `H` = `light_origin`에서 갓 아랫테까지의 깊이. 빔 반각은 `distribution` 프리셋이 고르고 정본은 `frontend/src/three/scene/lighting.ts`다.
  - ~~현행 절차 생성 램프가 3배 위반한다(rBot 0.092 / H 0.05 = 차단 61.5°).~~ **264가 고쳤다** — `props.ts` 갓은 이제 rBot 0.075 / H 0.20(광원이 갓 윗구멍)이라 차단 시작 **20.6°**로 `lamp-task`(flood 40.1°) 빔 안에 든다. 265 실측 darkFraction 0.8287(빔 안 0.8018)로 기하 예측 0.8439/0.8013과 일치한다.
  - **`atan(rBot/H)` 하나는 갓이 안 기울었을 때의 근사다.** 절차 램프 갓은 `rotation.z = 0.12`(6.9°)만큼 기울어 차단각이 방위마다 **16.7° ~ 24.4°**로 갈린다. 그래서 `lamp-warm`(spot 18.3°)은 "무늬 0"이 아니라 웅덩이 **바깥 테두리(정규화 반경 0.907~1)에 초승달**이 생긴다(빔 안 어두운 비율 0.0427). 게이트 경고를 계산할 때 기운 갓은 이 범위를 봐야 한다 (2026-07-30 DERO-265).
  - **등록을 막지 않는다.** 얕은 접시형 갓·오픈 셰이드는 실물에 있고 그런 제품은 무늬가 없는 것이 사실이다. 등록 도구가 두 각을 계산해 "이 갓은 무늬를 내지 않는다"를 경고하고 저작자가 그대로 등록한다.
- **차폐 기하 = `lampShade` 이름이 붙은 메쉬.** 베이크가 굽는 것은 이 이름의 메쉬(복수 가능)뿐이다. `light_origin`과 같은 형태의 **이름 규약**이고 `-kn`이 이미 이름을 보존한다 — glTF extras 플래그는 여전히 0개다. **이름 변경은 파괴적 변경.** 이 이름이 없는 제품은 마스크가 흰색(= 쿠키 없음)으로 정상 렌더된다.
  - **받침·폴·바닥판을 이 이름에 넣지 말 것.** 쿠키는 그림자 맵과 달리 깊이가 없어 **광선 위 첫 히트 표면까지** 어둡게 만든다 — 광원 바로 아래의 받침을 차폐물로 구우면 받침 **자기 윗면**이 검게 죽는다(지금 그 자리는 웅덩이 핵으로 253/255다). 받침이 상판에 드리우는 진짜 그림자는 이미 그림자 캐스터 슬롯 2칸이 깊이로 처리한다. (2026-07-30 판정 박동규 — 228 ④의 "제품 전 메쉬"를 **차폐 기하 한정**으로 좁혔다. ④가 근거로 든 darkFraction 0.8402는 원래 갓만 구운 226 프로브 값이고 순수 고리 예측 0.843과 일치한다 = 중앙이 밝다.)
- **쿠키 마스크는 파일로 굽지 않는다 — 런타임 베이크다.** 제품별 첫 배치 때 격리 씬에서 **차폐 기하를 투과율 `SHADE_TRANSMITTANCE`(현재 0.5)의 회색 + 배경 흰색**으로 `spot.shadow.camera` 시점에서 1회 렌더해 128²로 리드백하고 `light.colorNode`에 싣는다(경로·해상도는 226 확정). **새 컬럼도 새 파일도 없다.**
  - ~~불투명 검정~~ **투과율로 바뀌었다** (2026-07-30 박동규 부결, 265 2차). 매끈한 원통 갓에서 불투명은 빔의 바깥 고리를 통째로 죽였고, 화면의 갓이 `emissiveIntensity = 18`로 빛나는 반투명 종이라 앞뒤도 안 맞았다. 마스크 값이 곧 통과율이라 이제 그 고리가 죽는 대신 `t`만큼만 깎인다. 근거·재판정 경위는 `lighting-map.md`의 226 ⑤. **투과율을 제품별로 저작할지는 미결이고 지금은 전역 상수 하나다 — 266(등록 도구)로 인계.**
  - **저장 128²는 그대로지만 렌더는 512²다** — 4×4 박스 평균으로 내려야 원형 경계에 계단이 안 생긴다(226 ⑥의 "해상도 무차별"은 격자 링 대비 기준이라 이 축을 안 덮는다). 등록 도구가 마스크를 미리 보여줄 일이 생기면 같은 규칙을 따라야 값이 일치한다.
  - 파일로 안 두는 이유: 마스크는 갓 기하 파생값이라 파일에 두면 재export마다 낡는다. 게다가 `lamp-warm`·`lamp-task`는 절차 생성이라 `asset` 행이 없어 `asset.cookie_key`에 **자리가 없고**, `product_emitter`에 두면 파일 종속 값을 제품에 매다는 것이다 — 222가 `asset.emitter_manifest`를 뜯어낸 논거의 거울상이다. 128² PNG는 3.3KB라 아껴서 얻는 것보다 스토리지·마이그레이션·낡음 검수를 사는 값이 비싸다.
  - **`asset-pipeline.sh`에 베이크 스테이지를 넣지 않는다.** 베이크가 브라우저를 요구한다(`spot.shadow.camera` 재사용·RenderTarget 렌더·리드백) — 이 스크립트는 bash + python + gltfpack이라 headless Chromium이 새 의존성이 된다. 넣을 것이 없어졌다. (~~톤매핑 토글~~ — 265가 불필요로 확인했다: `Renderer.currentToneMapping`이 출력 타깃이 아닐 때 항상 `NoToneMapping`이라 RenderTarget 렌더는 구조적으로 톤매핑을 안 거친다. 오히려 `renderer.toneMapping`을 만지면 본 씬의 출력 패스 구성이 흔들린다.)

- **조명의 emissive 맵은 굽지 않는다.** 사용자가 밝기 배율·색온도를 조절하므로(D5·REQ-SIM-08 개정) 위 "발광 세그먼트" 절의 가변 발광 규칙이 그대로 걸린다 — 색·세기는 런타임 주입이다. 고정 발광(전구 유리 등)의 "emissive ×20 저작"은 별개로 유지.
- **압축: `-kn` 필수 — `asset-pipeline.sh`가 항상 준다.** `light_origin`은 메쉬 없는 노드라 gltfpack이 기본으로 지운다: `-cc -ke`만 주면 출력 노드가 **이름 없는 하나로 뭉개진다**(실측). `-ke`가 없으면 `emitterSurface`가 조용히 죽던 것과 같은 계열이고, 대가는 실제 에셋 5.1MB에서 **+40 B(+0.001%)**다. **`-km`은 불필요** — 살(비발광)과 발광면은 재질이 필연적으로 달라 gltfpack이 병합하지 않는다.
- 검수 추가 1줄: **압축 후 `light_origin` 노드 생존 확인**(위 `-kn` 회귀 방어). 163의 "`product_emitter` 행이 있는 제품의 에셋은 `emitterSurface` 메쉬 ≥1" 줄은 조명에도 그대로 걸린다.

### 제품 비주얼 변형 제작
- **재질을 따로 정해야 하는 대상은 part-segmentation 관절 에셋뿐이다 (2026-07-23 개정, 승인 박동규)** — 등록자가 `asset.finish` 4종(`CLEAR_ACRYLIC`·`METALLIC`·`WHITE`·`BLACK`) 중 하나를 **드롭다운으로 고른다**(REQ-ADM-01). 색 코드·거칠기·금속성을 직접 입력하지 않는다. 이전 "제품마다 머티리얼 스킨 1세트 필수"는 폐기(D19 이후 TEXTURE GLB가 재질을 스스로 들고 온다)
- **입력 규칙**: `asset.glb_export_mode = 'PART_SEGMENTATION'`이면 `finish` 필수, `'TEXTURE'`면 NULL — WAS 검증(단일 조건이라 분기가 하나다)
- **텍스처 컬럼(`texture_url`)은 부활 없이 폐기했다.** part-seg export는 텍스처를 받을 수 없고, 텍스처가 필요해 TEXTURE로 재export하는 순간 관절을 잃는다 — 채울 값이 존재하지 않는 컬럼이었다
- **치수 가변 파라메트릭 지오메트리의 텍스처는 triplanar 또는 vertex-position 매핑을 쓴다.** 이유: 상판 크기가 규격 DB 값에 따라 달라지므로 고정 UV를 쓰면 나뭇결이 늘어나거나 눌린다(UV 스트레치)
- 전용 GLB로 만든 제품은 UV 고정이므로 일반 UV 매핑 가능
- 책상 재질 4종(월넛·오크·블랙·화이트)은 치수 가변이므로 **triplanar 필수**. 텍스처 미확보 상태에서는 `woodGrainNode`(TSL 절차 생성)가 폴백으로 동작해야 한다 — 텍스처 확보가 구현을 막지 않는다.

### Meshy part-segmentation 실측 + 관절 구현 (2026-07-18 확정, 승인 박동규)
- **part-segmentation export = 파트별 분리 메쉬**(모니터암 실측 10조각)가 flat 형제로 나온다. **텍스처·리그·부모자식 계층·관절축 정렬 원점은 없다.** 파트 이름 generic(`model_partN`).
- **texture export = 융합 단일 메쉬 + PBR 텍스처.** 한 파일에 관절+텍스처 동시 불가. (예: 스피커·머그 같은 정적 소품 = texture 모드 융합, 모니터암 = part-seg + 관절. 모니터는 GLB가 없어 어느 쪽도 아니다 — 전량 절차 생성, D18.)
- **관절 구현 = part-seg 지오메트리 + 저작 리그 매니페스트(규격 DB) + 런타임 FK.** 매니페스트 = 파트→논리 세그먼트 매핑 · 관절별 축/점 · 한계각(min/max, 종류별 단위). 런타임이 관절에 피벗 노드를 세워 리지드 노드 계층(부모-자식 FK) 구성, 한계각 클램프. 지오메트리=에셋 / 관절 정의=규격 DB → D7·D16 그대로.
- **로드·경량화**: GLTFLoader + KTX2Loader(KHR_texture_basisu) + MeshoptDecoder(EXT_meshopt_compression), WebGPURenderer 지원(renderer.init() 후 KTX2 detectSupport). 등록 전 `gltfpack -cc -tc`로 meshopt+KTX2 경량화(용량 예산 준수).

### AI 생성(Meshy 등) 사용 범위 (2026-07-18 개정, 승인 박동규)
- **정적 장식물·정적 제품**: texture(융합) export 그대로 사용.
- **관절 에셋**: **part-segmentation export + 저작 리그 매니페스트 동반 시 허용**(위 절). 이전 "관절 에셋 AI 생성 전면 금지"는 폐기 — 전제였던 "세그먼트 분리 불가"가 part-segmentation 실측으로 무너졌다. 매니페스트 없이 융합 단일 메쉬로는 여전히 관절 불가.
- **조명 에셋**: 여전히 AI 생성 금지 — 광학 규격을 못 만듦(D5).
- Meshy 리깅 API(스킨 출력)는 휴머노이드 전용 — 본 프로젝트 관절 에셋엔 쓰지 않는다.

### Turbopack dev 캐시 — 의존성이 바뀐 merge 뒤 (2026-07-30 실측, tiptap merge)
- `git merge`가 `package.json`/`package-lock.json`을 바꾸면, 이미 돌고 있던 `npm run dev`(Turbopack)가 `Cannot find module '@swc/helpers-<hash>/...'` 같은 unknown-module 오류를 던진다. node_modules는 실제로 최신이고(`npm install`은 "up to date"만 말한다) — `.next/dev`에 남은 옛 content-hash 청크가 새 의존성 그래프와 안 맞는 것이다.
- 복구: `npm install` 재실행으로는 안 낫는다. **dev 서버를 죽이고 `.next`를 통째로 지운 뒤 재시작**한다.

# 3D 씬·배치 컨텍스트

> 읽는 시점: 시뮬레이터 화면(REQ-SIM-*) 구현·수정 시 (루트 CLAUDE.md 라우팅 표에서 진입).
> 관련 결정: `docs/CONTEXT.md` D3(차별점 1·3)·D4(벽 3면)·D5(조명 무드 시뮬레이션)·D16(관절 가동)·D18(책상·모니터 절차형 생성)·D19(소품 전량 GLB화).

## 확정 규칙
- 표면 스냅 배치: 상판·타공판·벽 표면에 자동 부착. z축 수동 조정 없음 (아키스케치 대비 핵심 차별점)
- 카메라: **자유 시점 조작이 기본**이고, 고정 프리셋 5종(1인칭·전면·후면·측면·탑뷰)을 단축키로 즉시 전환해 조작 부담을 던다 — 프리셋이 자유 시점을 대체하지 않는다(2026-07-24 표현 명확화). **줌인 상한 = 물체가 화면 폭의 25%** (뷰포트 1920px에서 480px. 2026-07-24 확정, 승인 박동규). 줌아웃 하한은 씬 전체가 들어오는 거리 — 텍스처 예산과 무관하다(멀어지면 낮은 밉을 쓴다). **이 25%가 에셋 텍스처 해상도를 직접 결정하므로 임의로 풀지 마라** — 50%로 풀면 모든 에셋이 2048²를 요구해 예산이 무너진다. 판정 공식·실측 근거는 `asset-pipeline.md` 용량 예산. 제품 재질·마감을 크게 확인하려는 요구는 씬 줌이 아니라 **제품 상세 뷰**로 푼다(에셋 1개만 로드하므로 고해상도 감당 가능)
- 벽은 좌·전면·우 3면 개별 토글. 꺼진 면에는 타공판·선반 배치 불가 (조건 규칙) — 드래그 레이캐스트가 **켜진 벽만** 대상으로 삼아 이 규칙을 강제한다(`Raycaster`는 `visible=false`를 안 거른다). **반대로 아이템이 붙어 있는 벽은 끌 수 없다** — 토글이 거부되고 안내가 뜬다 (D4 2026-08-03 확정)
- 배치된 오브젝트 임의 리사이즈 금지 — 크기 조절 UI 미노출 (책상 규격 입력 폼은 대상 아님, D18)
- 조명은 무드 시뮬레이션 — 색온도·밝기 규격 + 배치 위치가 씬 무드·반사에 반영 (Must, D5 2026-07-17 개정). 조도(룩스) 수치 계산은 범위 밖
- 관절 에셋은 규격 DB 한계각 범위에서 가동. 스키닝 금지 (Must, D16). **한계각·축·피벗점의 정본은 `asset.rig_manifest`**(2026-07-23 — 그전엔 `arm.rig_manifest`). 관절 제품군은 4종이다 — 모니터암·마이크암(`spec_type = ARM`)·노트북 거치대·휴대폰 거치대(`spec_type = PROP`). 매니페스트를 `asset`에 둬서 `spec_type`과 무관하게 넷을 같은 코드 경로로 구동한다
- **관절 종류·커플링·조작 UX (2026-07-25, ADR-0002).** 관절은 회전(`revolute`, 도)뿐 아니라 직선(`prismatic`, mm — 폴형 암 높이 슬라이드, 리프트형 거치대 승강)도 있다. 평행사변형 링크 등 종속 관절은 `coupledTo`(driver·ratio·offset)로 표현하고 **저장하지 않는다** — 로드 시 driver 값에서 재계산. 종속 관절은 gizmo·슬라이더에 뜨지 않는다(사용자가 만지는 것은 driver뿐). 조작은 3D 드래그 gizmo + 슬라이더 병존 — 상호작용 우선순위는 **선택 상태에서 마우스다운이 gizmo를 먼저 맞히면 관절 드래그, 아니면 배치 이동**이고, 드래그 중에는 카메라 오빗·배치 이동을 잠근다
- **회전은 직접 조작이다 (REQ-SIM-18 개정, ADR-0022 결정 7 — 2026-08-03 확정).** 선택 아이템 **발밑 회전 링 기즈모**를 끌면 실시간으로 yaw가 돌고 **45° 배수에 6° 이내로 들어오면 자석이 문다**(격자 사이 값은 그대로 유지 — 연속 회전은 계속 가능하다). **R 키 = 45° 회전**이고 대상은 **드래그 중인 것이 먼저**다: 라이브러리에서 끌고 오는 고스트 → 끌고 있는 배치 아이템 → 선택 아이템. 링은 관절 기즈모와 같은 히트 우선순위 규칙(ADR-0002)에 후보로 들어간다 — **관절 기즈모 > 회전 링 > 아이템 > 빈 곳**. 벽 아이템(yaw가 벽 법선에 종속)과 결합된 모니터(포즈 주인이 암 FK)에는 링이 뜨지 않는다. ~~꾹 누르기 회전 버튼(초당 120°)은 `SelectionToolbar` 폐기와 함께 사라졌다~~ → **2026-08-04 재개정(ADR-0023 결정 6·7, DERO-409)**: 부동 툴바가 **복구되고 꾹 누르기 ±도 세 축 모두 돌아온다**(회전 120°/s, 기울기 30°/s, 높이 300mm/s — 높이 속도는 ADR이 정하지 않아 두 축과 같은 체감(전 구간 2.5~3초)에 맞춘 구현 선택이다). 링 기즈모·R 키와 **병존**한다 — 링은 큰 각을 휙 돌리는 도구, ±는 1~5° 미세 조정 도구다. 폐기 사유였던 "조작 중 패널·마우스 동반 상승"은 **조작 시작 시 화면 좌표 동결**로 원인만 도려낸다(선택·이동 중에는 계속 따라간다)
- **로더의 재질 적용은 `glb_export_mode`가 가른다.** `PART_SEGMENTATION`이면 GLB에 텍스처가 없으므로 `asset.finish`(`CLEAR_ACRYLIC`·`METALLIC`·`WHITE`·`BLACK`)에 대응하는 코드 프리셋을 **전 메쉬에** 입힌다. `TEXTURE`면 GLB 자체 머티리얼을 그대로 쓴다 — 덮으면 텍스처가 죽는다. 함정: **에셋 하나에 마감 하나라 파트별로 다른 재질을 입히지 않는다.** 투톤이 필요해 보이면 코드로 우회하지 말 것 — 스키마 확장 대상이다(`asset_part_material` 1:N)
- **책상은** GLB 없이 규격값으로 절차 생성 (Must, D18). 제품 선택/직접 입력 2모드가 `DeskConfig` 하나로 수렴 — 렌더 경로는 `buildDesk(config)` 한 개
- **모니터도 전량 절차 생성** (Must, D18 2026-08-02 재개정 — 2026-07-23 하이브리드 폐기) — 화면 패널·베젤·스탠드를 인치·화면비·곡률·베젤 폭·스탠드 깊이에서 만든다. **모니터에는 GLB를 붙이지 않는다** — 인스턴스화 분기가 `spec.glbUrl ? assets.instantiate(spec) : buildProp(spec)`(`scene.ts`)이라 `glbUrl`이 생기는 순간 절차 생성 분기가 통째로 건너뛰어지고 GLB 전체가 규격 치수로 스케일된다(비균일 스케일, NFR-02·D7). 따라서 `asset` 행이 없는 `spec_type`은 `DESK`·`MONITOR` 둘이다
- 책상과 모니터를 뺀 **모든 제품은 GLB** (Must, D19) — 파라메트릭 프리미티브 렌더 경로는 폐지다(폴백도 없음). 절차 생성은 **치수 가변 지오메트리**(책상 상판·모니터)에만 남는다. GLB 8종이 초기 로드 예산을 거의 다 쓰므로 **lazy 로드 필수**
- 책상 뒷변과 전면 벽 간격 기본 50mm(2026-08-06, 1mm에서 개정 — 벽이 책상에 딱 붙어 답답하다는 사용자 피드백) — **벽을 책상 뒷변으로 당긴다**(책상을 밀면 배치 좌표계 전체가 이동해 기존 좌표가 깨짐). 2026-08-05부터 간격은 사용자 조정 가능(`setFrontWallGap`, 1mm~3m 클램프 — 최소 1mm는 z-fighting 방지, 세션 한정 비영속) — 기준은 좌/우(책상 중심 거리)와 달리 **책상 뒷변**이다
- 모니터 조정은 포즈만. 인치·화면비·곡률은 규격 DB 소관 — 조절 UI 금지 (VESA·하중 판정 근거 보호)

## 구현 세부 (착수 시 채움)
_단축키 매핑은 아직 미정 — 정해지면 여기에 기록한다._

**배치·충돌 (2026-07-21 확정, 승인 박동규)**
- **2계층 분리.** 호환성 판정(규격 DB 전용, D7/D8 — 프론트 `collision.ts`는 실시간 즉답 **미러**이고 정본은 WAS의 저장 시점 전체 재판정이다, ADR-0004)과 배치 시 공간 겹침 피드백(`collider.ts`)을 분리. 공간 충돌만 시뮬레이터 지오메트리를 참조해도 됨.
- **파트별 OBB + SAT.** 메쉬당 방향성 바운딩 박스 1개(`mesh.matrixWorld`가 FK 피벗 회전 포함 → 관절 포즈 반영 공짜), 빨강 틴트는 관절 에셋이면 겹친 파트만, 정적 소품이면 아이템 전체. 접촉 허용 오차로 밀착·스태킹 접촉은 충돌 아님 — **판정용 OBB 반크기를 축마다 5mm 깎되 그 축 반크기의 40%를 상한으로 둔다**(상한이 없으면 두께 7mm 아이패드 같은 얇은 파트가 음수 반크기가 되어 판정에서 통째로 사라진다). 실효 문턱은 CONTACT_EPS 0.5mm를 더해 겹침 11mm다 (2026-08-03 확정, 승인 박동규 — 그전까지 관용치 0이라 약속만 있고 구현이 없었다).
- **얹기 = 규격 박스 스태킹 + 사용자 자세 (2026-08-04 재개정, ADR-0023 · DERO-408 — 아래 접촉 솔버 불릿 3개를 폐기한다).** 아이템은 아래 아이템의 **지지면**(`core/snap.ts` `supportSurfaces` → `supportTopY`)에 **평평하게** 얹혀 시작하고, 그 뒤 **자세는 사용자가 정한다** — 수동 3축(yaw 저장 · pitch ±75° 저장 · 높이 0~2600mm **절대 y** 저장 — 상한 2026-08-11 1000→2600 개정, DERO-588: 모니터 위 수동 배치(ADR-0024 결정 4의 탈출구)가 1000에 막혔다). 밑면 레이 격자·표본 수집·기울기 계산은 전부 사라진다(`core/contact.ts`·`scene/contactSample.ts` 삭제). **실메쉬 형상을 읽지 않는다** — 메쉬/스펙 분리 규칙과 재정렬한 것이 이 개정의 근거 중 하나다. 드롭 순간만 지지면 높이로 초기화하고 이후에는 사용자 값이 정본이라 **받침을 치우면 위 아이템은 그 자리에 남는다.** 자세가 저장값이라 **로드 시 재계산이 없다** — `position_y_mm`은 벽 아이템뿐 아니라 모든 아이템에서 되읽히는 값이 된다(아래 결정성 계약 불릿의 "상판·바닥 아이템의 y는 파생값"은 폐기).
- **지지면은 아이템당 하나가 아니다 — 모니터는 스탠드 발판만 내놓는다 (2026-08-04 개정, ADR-0024 · DERO-431).** `supportSurfaces(spec, center, yawRad)`가 아이템별 지지면 **목록**을 내고 `resolveSupportY`가 `flatMap`으로 펼친다. 대부분 제품은 종전대로 하나(규격 footprint × 규격 박스 상단)지만 **모니터는 발판 하나뿐**이다 — rect는 `MONITOR_STAND_WIDTH_MM`(200) × `standDepthMm`, topY는 규격 박스 밑면 + `MONITOR_STAND_FOOT_HEIGHT_MM`(14). **패널은 지지면을 안 내놓는다**(모니터 위에는 안 얹는다). 통짜 박스로 되돌리면 27"의 613.7×130mm 띠 전체가 지지면이 되어 ①모니터 밑 받침대가 +542mm로 튀고 ②목 옆 빈 자리에 소품을 못 놓는다. **충돌은 이 결함과 무관하다** — `collider.ts`는 이미 파트별 OBB라 패널·발판·목이 따로 잡힌다. 상수 정본은 `scene/monitor.ts`(`monitorStandFootMm`)이고 `props.ts` 발판 메쉬가 같은 값을 쓴다 — 한쪽만 만지면 얹힘 높이가 화면과 갈라진다. **연쇄 재안착은 여전히 없다**(결정 4): *받침대 먼저 → 모니터 얹기*는 되고 반대 순서는 사용자가 모니터를 올린다. **모니터 위에 얹는 길은 커서 레이로 열려 있다 (2026-08-11 개정, ADR-0024 결정 4 · DERO-591)** — 드래그 중 포인터가 모니터 패널을 맞히면 그때만 드롭 높이가 패널 상단이 된다(x는 커서 추종 + 패널 폭 클램프, z는 패널 중심, 축은 호스트 로컬 좌우축). 지지면 목록은 그대로라 목 옆·패널 아래는 종전대로 상판 높이다 — 자동 규칙으로 되돌리면 같은 XZ에 타깃이 둘이라 431 증상 ①②가 재발한다. 스탠드 높이 아래 히트는 버리고(발판·목은 이미 지지면이다), 얹힌 아이템에 **새 필드·새 상태는 없다**(높이가 이미 사용자 소유 저장값이라 모니터를 옮겨도 그 자리에 남는다). 정본은 `core/snap.ts` `resolveMonitorTopPose` + `scene.ts` `pickMonitorTop`·`moveItemOnMonitorTop`, 회귀 테스트는 `tests/snap.test.ts` "resolveMonitorTopPose".
- **모니터암도 지지면을 하나도 안 내놓는다 (2026-08-05 개정, ADR-0024 결정 8 · DERO-455).** `spec.arm`이면 `supportSurfaces`가 빈 목록이다. 같은 결함이 한 칸 옆에 있었다 — `monitor-arm-white`의 규격 박스는 **100W × 385D × 400H mm**이고 뒷변에 물려 상판 안쪽으로 385mm 뻗으니 **키보드 자리가 그 띠 안**이다. 통짜 박스를 지지면으로 쓰면 그 자리의 아이템이 전부 상판 **+400mm(= 암 꼭대기)**로 초기화돼 공중에 뜬다. 캔틸레버라 폴·암 세그먼트에 물건을 얹을 수 없으므로 지지면이 없는 것이 맞다. **클램프 베이스만 내놓는 대안은 부결** — 그 치수는 리그 세그먼트(메쉬)에만 있고 규격 DB에 컬럼이 없다(읽으면 메쉬/스펙 분리 위반, 컬럼을 만들면 `erd.md` 언락). 암 폴과 겹치는 자리는 상판 높이로 초기화돼 관입하고 **파트별 OBB 충돌이 빨간색으로 잡는다** — 공중 부양보다 낫다. **VESA로 암에 결합된 모니터는 이미 빠져 있었다**(`resolveSupportY`의 `!i.mountedToId`) — 보고된 증상의 범인은 모니터가 아니라 암 자신이었다.
- **관입은 막지 않고 경고만 억제한다 (ADR-0023 결정 5).** 자유 높이·기울기는 필연적으로 규격 박스 관입을 만든다(아이패드를 거치대 홈에 넣는 것이 정상 조작이다). 하드 클램프도 전량 빨강도 아니고 **얹힘을 런타임 추론**한다 — XZ 겹침 + 밑면이 상대 박스 상단 근처/아래면 그 쌍의 충돌 경고만 억제한다(저장 없음, 로드 시 재추론). `collideItems`(`core/collider.ts`)는 순수 SAT이고 스태킹 예외가 없어 **새로 추가해야 한다** — 지금 매트 위 키보드가 안 걸리는 것은 예외가 있어서가 아니라 박스가 맞닿을 뿐 안 겹치기 때문이다(`shrinkForTolerance`가 맞닿음 오차를 흡수). 이 추론은 **자세를 정하지 않는다 — 경고만 정한다.** 틀려도 아이템 위치는 사용자 값 그대로라, 자세를 계산하던 두 세대(cradle 휴리스틱·접촉 솔버)를 반려시킨 실패 모드가 재현되지 않는다.
- ~~**표면 안착 = 접촉 솔버 하나 (2026-08-03 개정, ADR-0022 · DERO-393).**~~ **폐기 (2026-08-04, ADR-0023)** — 이 불릿과 다음 두 불릿(게이트 없음·결정성 계약)은 역사 기록이다. 게이트 없음만 유효하게 계승된다. 종전의 두 경로(거치대 요람 휴리스틱 + `supportTopY` 박스 스태킹)를 하나로 합쳤다: 아이템 **밑면(yaw 회전한 사각형) 7×7 격자**에서 아래로 레이를 쏴 표면 표본을 모으고, 그 위에 밑면을 평평한 강체 판으로 놓아 **관입 없는 안착 자세(높이 + 기울기)**를 기하로 계산한다. 판은 무게중심 XZ가 접촉 다각형 안에 들어올 때까지 상향 볼록 껍질을 굴러 내려가고, 기울기 상한(75°)을 넘으면 최고 표본 높이로 평평 폴백한다. 표본이 전부 1mm 안이면 평평 판정이라 **매트·라이저 스태킹 결과는 종전 `supportTopY`와 같다**. 순수 규칙은 `frontend/src/three/core/contact.ts`, 레이 수집은 `frontend/src/three/scene/contactSample.ts`, 회귀 테스트는 `frontend/tests/contact.test.ts`·`frontend/e2e/contact-solver.spec.ts`.
- **게이트 없음 (ADR-0022 결정 3).** 카테고리 표(`CRADLE_ACCEPTS`)와 `stackable` 지지 게이트는 폐기됐다 — **아래 표면이 있으면 앉는다.** 이상한 배치는 종전 소프트 블록(충돌 빨강 + 저장 게이트)이 피드백한다. 규격 footprint XZ 겹침으로 후보를 추리는 것은 **성능 게이트**일 뿐 판정이 아니다(드래그 프레임마다 전 아이템에 레이를 쏘지 않기 위한 것).
- **결정성 계약 (ADR-0022 결정 2).** 솔버는 (표본, 무게중심 XZ)의 순수 함수다 — 저장은 x/z/yaw만 하고 안착 자세는 로드 때 재계산한다. 그래서 물리엔진·미끄러짐은 부결이고, 모든 동률에 명시적 타이브레이크가 있다. **`position_y_mm`은 벽 아이템에만 되읽힌다**(상판·바닥 아이템의 y는 파생값). 수동 축은 yaw(저장)와 tilt(세션 한정 보정 오프셋)뿐이고 **lift(들어올림)는 삭제됐다** — 존재 이유가 솔버로 소멸했다(결정 6).
- **받침이 움직이면 위 아이템도 다시 앉는다.** 런타임 개념 `seatedOnId`를 따라 `resnap`이 연쇄로 재스냅한다(순환은 visited로 끊는다). 단 **받침을 이미 놓인 아이템 *밑으로* 밀어 넣는 경우는 안 잡힌다** — 그 아이템의 `seatedOnId`가 아직 비어 있어 재스냅 대상이 아니다(종전과 같은 한계).
- **지지 파트 경계 규칙.** 정적 소품은 자기 규격 footprint, 관절 에셋은 supportPart(클램프) footprint가 상판 안일 것. 머리 캔틸리버는 상판 밖 허용(옛 하드 클램프 폐기).
- **소프트 블록 + 저장 게이트.** 위치 클램프 없음(자유 이동) — 충돌·**상판** 경계 위반은 빨강 표시 + 저장 차단(`trySave`)만. 위반 시 경고 배너 표시. **상판 경계 관용치는 2mm이고 정적 소품에만 준다**(2026-08-04, `core/snap.ts` `DESK_BOUNDARY_EPS_M`) — 종전 1e-6(0.001mm)이라 규격 반올림 노이즈로도 저장이 막혔다. 관절 에셋(모니터암)은 0 유지: 엣지 스냅으로 상판 변에 물리는 것이 정상 자리라 판정 접점이 변 자체이고, 여유를 주면 실제로 못 물리는 물림이 통과된다. **cm 단위로 키우지 말 것** — 아래 캔틸리버 항의 벽 판정 실패 기록(3cm가 실측 1.5cm 진짜 위반을 같이 지웠다)이 근거다. 같이 들어간 것 둘: 배너가 위반 제품 이름을 대고(`'키보드'가 상판 경계를 벗어났습니다`), 상판 경계 + 위반 아이템의 판정 사각형을 선으로 그린다(`scene/boundaryGuide.ts` — 판정 입력이 화면 실루엣이 아니라 규격 박스라 안 보여주면 "여유 있어 보이는데 빨강"으로 읽힌다). **벽은 이 게이트 대상이 아니다** — 켜진 벽은 하드 클램프만 걸고 소프트 경고·저장 차단은 걸지 않는다 (2026-08-03 개정, 승인 박동규 — 근거는 `docs/CONTEXT.md` D22).
- **배치면은 규격 DB `prop.mount_surface`가 정한다 (2026-08-03 개정, DERO-375).** `TOP`은 상판(+ 그 위 아이템의 지지면 = 규격 박스 상단. 2026-08-04까지는 접촉 솔버가 판정했다), `FLOOR`는 월드 바닥 y=0이다 — 바닥 제품(풋레스트 등)은 상판 스냅을 안 타고 **상판 경계 판정에서도 빠진다**(책상 밑이 정당한 자리라 안 빼면 항상 빨강 + 저장 차단). **지지면 탐색은 배치면이 같은 것끼리 돈다 (2026-08-08 개정, DERO-517)** — 바닥 제품끼리는 얹힌다(러그 위 의자는 러그 상단에서 시작). 종전처럼 바닥 제품이 탐색을 통째로 건너뛰면 러그와 의자가 둘 다 y=0이라 규격 박스가 관통해 **항상 충돌 경고**가 뜬다. 배치면을 섞지 않는 것이 375 함정(상판 아이템 박스 상단이 바닥 기준 y를 덮어 도로 상판으로 올라감)의 방지책이다 — 정본은 `sharesMountPlane`. 벽 하드 클램프는 두 경우 다 걸린다. `raycastToSurface`도 아이템이 실제로 놓일 높이의 평면을 쓴다(안 그러면 커서와 배치 자리가 어긋난다). 규칙 정본은 `frontend/src/three/core/snap.ts`(`baseSupportY`·`usesDeskSnap`·`violatesDeskBoundary`), 저장은 `ItemSnapshot.surfaceType`에 그대로 실린다. **`WALL`도 2026-08-03에 개방됐다(같은 이슈 2차)** — 좌·전면·우 벽 메쉬에 직접 레이캐스트해 붙이고, 뒷면이 벽에 밀착하도록 yaw가 벽에 종속돼 고정된다(좌 90°·전면 0°·우 270°). 벽 이격은 규격 `depthMm`의 절반이다(메쉬 치수 금지). **벽 아이템만 `center.y`가 파생값이 아니라 저장값이다** — 지지면이 없으니 사용자가 포인터로 정하고 `positionYMm`으로 왕복하며, 바닥(0)~벽 높이(2.6m) 안으로 클램프된다. 수평 클램프는 벽 법선 축을 고정한 채 건다(안 그러면 벽에서 떨어진다). 상판 경계 판정과 접촉 표본 수집에서는 바닥 제품과 같이 빠지고, 저장 시 `ItemSnapshot.wallSide`에 어느 벽인지 싣는다(엔진 소문자 ↔ API 대문자 변환은 `utils/wallSide.ts` 한 곳). **`PEGBOARD`도 2026-08-08에 개방됐다(DERO-518)** — 다만 붙는 곳이 벽이 아니라 **다른 아이템의 앞면**이다. 벽에 붙은 타공판 패널에 후크가 붙고, 그 후크에 다시 제품이 걸린다(규칙이 하나라 체인 깊이에 제한이 없다). 붙은 아이템은 호스트의 `wallSide`를 물려받아 벽 아이템 갈래를 그대로 타고(`y`가 저장값·yaw 종속·지지면 탐색 없음), 호스트 링크는 새 필드 `pegboardHostId`다 — 모니터↔암의 `mountedToId`와 **합치지 않는다**(그쪽은 `removeItem`이 `detachMonitor`를 부르는 모니터 전용 프로토콜이다). 타공판을 지우면 붙어 있던 것이 체인째 같이 지워진다(후크는 내려놓을 상판 자리가 없다). **홀 격자에 정렬하지 않는다 — 연속 좌표다**: 홀 피치는 규격 DB에 컬럼이 없고 메쉬를 재는 것은 D7 위반이라, 패널이면 판 경계로 클램프하고 후크면 그 중심·상단에 맞춘다. 규칙 정본은 `core/snap.ts`(`resolvePegboardPose`·`resolveHookHangPose`), 회귀 테스트는 `tests/snap.test.ts` "타공판 부착". (옛 "배치 범위 = 책상 상판 한정, 바닥은 범위 밖" 2026-07-23 확인은 폐기.)
- **범위 밖**: 물리 시뮬레이션(중력·낙하 애니메이션)은 도입하지 않는다 — 스냅 기반 정적 배치만. 단 **드롭 착지 연출 트윈은 허용**(2026-07-22 개정): 사이드바에서 끌어다 놓을 때 최종 스냅 위치 4cm 위에서 140ms ease-out으로 내려앉는다. 솔버·중력·바운스·충돌 응답 없음, 최종 좌표는 스냅 결과와 동일 — 시각 연출이지 물리가 아니다 (`core/dropTween.ts`). 개별 에셋 결함(램프 덮개 내부 투명 등)은 코드가 아니라 에셋 검수(`asset-pipeline.md`) 소관.

**조명 무드 구현 모델 (2026-07-18 확정, 승인 박동규)**
- **방 조명(전역) = 중립 고정 base.** 전역 리그(directional·hemi·IBL)는 중립 색온도·고정 밝기로 고정 — 색온도/밝기 변조를 전역에 걸지 않는다. on/off 토글(끄면 배치 조명만 남아 무드 부각, 완전 암흑 방지용 낮은 ambient 유지).
- **방 조명 OFF의 ambient floor = 종전의 1/5** (2026-07-25 확정, 승인 박동규). 위 항의 "낮은 ambient"가 실제로는 낮지 않아 흰 벽이 중간 회색으로 남았고, 네온이 "회색 벽 위 색 얼룩"으로 읽혔다. floor를 1/5로 내린 컷만 목표 무드에 도달했다(Phase 0 스파이크 시각 QA). **이 값이 블룸 threshold와 짝이다** — floor를 다시 올리면 흰 벽이 문턱을 넘어 벽이 통째로 번진다. 한쪽만 만지지 말 것.
- **무드 변화 = 배치한 발광체의 로컬 광원만** (2026-07-25 개정 — 그전엔 "조명 에셋의". 발광은 `spec_type`과 직교한다, D5·ADR-0003). 전역 슬라이더로 화면 전체를 물들이던 구현은 폐기된 채로 유지되고, 로컬 광원이 두 갈래로 갈린다 — **2026-07-30 개정(DERO-258): 갈리는 기준이 제품 분류에서 `product_emitter.shape`로 바뀌었다**(222·223·230). 렌더 정본이 `product_emitter`이고 `light` 테이블은 카탈로그 표기 마커로 격하됐으니 **광학 값을 `light`에서 읽지 말 것.** `shape` 허용치는 POINT/SPOT뿐이다(AREA는 227이 부결):
  - **SPOT 배광**(`product_emitter.shape = SPOT`) — 배치 좌표에 실제 SpotLight. 색온도(K)→색, `product_emitter.lumens`→세기(사용자가 고른 배율·색온도는 `placed_item.emitter_brightness_scale`·`emitter_color_temperature_k`가 덮는다), decay+distance 국소 폴오프, **그림자 캐스터 후보**. `product_emitter.distribution` 프리셋에 따라 cone/penumbra 변화.
  - **POINT 배광**(`product_emitter.shape = POINT` — PC 본체 RGB·스트립·키보드 백라이트 등) — emissive + 블룸 + **그림자 없는 PointLight 1개**. 주변 표면만 물들이고 그림자 캐스터 캡에 들어가지 않는다 — **근거는 제품 분류가 아니라 렌더 비용이다**(POINT 그림자는 큐브맵이라 씬 6패스, 223). 그래서 밝은 장식 발광이 SPOT으로 저작되면 코드 수정 없이 그림자를 받는다. 위치는 bbox 중심이 기본이고 어긋나는 제품만 `product_emitter.point_x_mm`·`point_y_mm`·`point_z_mm`로 덮는다(셋 다 NULL이면 bbox 중심). 색은 `product_emitter.recolorable`이면 사용자가 고르고(`placed_item.emitter_color`, 배치 아이템당 1색), 아니면 `product_emitter.default_color`의 고정색을 쓴다.
- **발광체가 캡을 넘으면 카메라 근접순으로 PointLight를 배정하고 초과분은 emissive만 남긴다**(스필 없음). 램프 그림자와 달리 발광 스필은 국소(30~60cm)라 화면 밖 기여가 어차피 안 보이기 때문 — 램프 슬롯 배정이 실효 lm 순인 것과 대조된다. 캡 값은 측정으로 정하고 WebGL2 폴백은 별도의 낮은 캡을 둘 수 있다.
- **광원은 슬롯 풀이 소유한다 — 배치가 광원을 만들지 않는다** (2026-07-29 DERO-235 결정, 238 구현). 부팅 시 램프 SpotLight 6개 + 발광 PointLight를 캡만큼 만들어 두고(`three/scene/lightSlots.ts`), 배치·삭제·재배정은 슬롯의 색·각도·세기·위치만 갈아끼운다. 광원 개수와 `castShadow` 집합이 곧 셰이더 해시라 그걸 상수로 묶는 것이 목적이다(실기 스톨 1208~1729ms → 9.3ms, 상시 비용 +0.3~0.6ms). 따라 오는 규약 셋: ①**슬롯 수를 넘은 램프는 형상만 남고 빛을 못 낸다** — 경고 배너로 알린다(`lightingInfo().unlitLampCount`) ②램프 캐스터는 **2칸 상수**이고 방 조명 OFF에서도 key가 그 칸을 놓지 않는다(세기만 0) ③꺼짐은 언제나 `intensity/power = 0`이고 `visible`·`castShadow` 토글은 금지다.
- **블룸 threshold는 pre-tonemap 물리 스케일이다.** `CAMERA_EXPOSURE = 1/20` 하에서 흰 벽 L≈10~25, 배경 캔버스≈17, 램프 셰이드 emissive=18, 모니터 화면=11 — 공식 예제의 0.9 같은 값을 쓰면 **화면 전체가 백색 안개가 된다**(2026-07-25 실증). 장식 발광만 뽑으려면 그 위(35 전후)에 둔다. 기존 emissive가 전부 이 문턱 아래라, 모니터 화면을 빛나게 하려면 값을 올리거나 emissive MRT 선택 블룸으로 가야 한다.
- **그림자**: 방 조명 key + 배치 조명 SpotLight가 castShadow. 캐스터 캡 ~3(방 key 1 + 램프 2). 캐스터 2칸은 **실효 lm이 높은 램프**가 갖고(223), 남은 램프는 그림자 없이 발광한다(성능). 캡 재배정은 플래그 토글이 아니라 슬롯 배정이다(위 광원 슬롯 항).
- **벽 3면 토글 UI**: 좌·전면·우 개별 on/off 배선. 하단 무드 패널(웜/쿨·밝기 슬라이더)은 방 조명 토글 + 벽 토글로 교체.
- **RectAreaLight 금지** — 확산형은 넓은 cone SpotLight/PointLight로. **사유 정정(2026-07-28 실측)**: 종전에 적혀 있던 "WebGL2 폴백 미지원"은 **거짓**이다. r185 `WebGPURenderer({forceWebGL:true})` + SwiftShader에서 정상 조명된다(평균 휘도 55.79 vs 무광원 대조군 0). 실제 제약은 ①**그림자를 아예 못 만든다**(`castShadow=true`면 `TypeError`로 수신 재질이 통째로 렌더 안 됨) ②`RectAreaLightNode.setLTC()`를 안 부르면 화면 전체 검정 ③PBR/볼륨 재질에서만 반응. **재판정이 끝났다 — 227이 부결로 닫아 금지는 이제 무조건이다**(2026-07-30, `product_emitter.shape` 열거는 POINT/SPOT 확정). 사각 하이라이트는 실측으로 진짜였지만(aspect 12.0 대 SPOT 0.98) **프로덕션 카메라 프리셋 6개 중 어느 것도 보여주지 못하고**, 그림자가 영구 불가하며(위 ①), 600 lm에서 소실된다. 224가 들었던 "읽힐 표면이 없다"는 기각 사유는 폐기다 — 227이 상판을 광택화해 그 표면을 실제로 만들고도 부결했다. 정본 `lighting-map.md`, 판정 전문은 티켓 DERO-227.
- GLB 로드·관절(모니터암)·호환 attach·케이블 물리는 `asset-pipeline.md` 참조.

SwiftShader/WebGL2에서도 렌더·e2e green.
- **선택 외곽선**: WebGPU outline 노드를 postfx `RenderPipeline`에 삽입. 정본 예제 = three.js `webgpu_postprocessing_outline`. **classic `OutlinePass`(EffectComposer)는 WebGPU 노드 파이프라인과 비호환 — 쓰지 말 것.**
- 선택 로직: pointer raycast → 제품 root 노드 히트 → outline selection 배열 세팅(+scale/emissive 피드백 선택). 평소 off, 선택·호버 시만 on — outline 레이어 한정(상시 컨투어 라인은 위 항목대로 항상 켜짐, 2026-07-20 확장).

**3D 월드 → HTML 오버레이 브리지 (2026-08-14 이주 — 2026-08-10 DERO-546 스테이징분)**
- 아이템 추적 오버레이는 이 레시피를 재사용한다 — `@react-three/drei`가 없어 `<Html>`은 못 쓴다. `RenderLoop`(Canvas 안, `useFrame`)이 선택 아이템 `Box3` 상단 중심을 `camera.project()`로 CSS px로 바꿔 `src/three/scene/selectionAnchor.ts`(단일 리스너 publish/subscribe 브리지)로 싣고, Canvas 밖 형제 DOM인 툴바가 구독해 `style.transform`을 직접 쓴다. **이 좌표를 React state로 라우팅하지 말 것**(프레임마다 리렌더 — `src/three/CLAUDE.md`의 state-in-ref 규칙과 같은 근거이고, 금지문 정본은 `src/components/simulator/CLAUDE.md`다). 새 추적 오버레이에 `useFrame`을 하나 더 만들지 말고 이 브리지를 태워라.
- `Box3.setFromObject`는 `visible=false` 노드(숨긴 VESA 스탠드)까지 세므로 "상단"이 높게 읽힌다 — 시각 앵커로는 허용.
- `anchorPoint.project(camera).z`가 `[-1,1]`을 벗어나면 `null`을 publish한다.
- `position:fixed` 컨테이너에는 `backdrop-filter`/`transform` 조상이 없어야 한다 — `.glass`로 감싸면 컨테이닝 블록이 옮겨져 툴바가 어긋난다.
- 첫 유효 앵커까지 `visibility:hidden`(~1프레임)이라 프러스텀 밖 아이템은 아예 안 뜬다 — e2e에서는 카메라 프레이밍이 먼저다.
- **publish된 점은 transform 전에 `clampToolbarPos`(`utils/selectionToolbarPos.ts`)를 지난다** — 없으면 키 큰 아이템이나 `top` 프리셋에서 바가 화면 밖으로 밀려 닿을 수 없었다. `TOP_LIMIT_PX = 84`는 `.editor-topbar` 64px + 20px 파생값이다 — 동반 수정 규칙(4소비처)의 정본은 `.claude/rules/simulator/topbar-and-exit.md`다.
- 툴바 크기는 선택마다 한 번 ref에 재고 `resize`에서 무효화한다 — 프레임 콜백 안에서 `offsetWidth`를 읽으면 매 프레임 리플로가 강제된다.
- 이력: `selectionAnchor.ts`/`selectionToolbarPos.ts`는 2026-08-03에 플로팅 툴바와 함께 지워졌다가 2026-08-04 ADR-0023 결정 6으로 복구됐다.

**코치 투어 앵커 = 레일 버튼 (2026-08-14 이주 — rules 다이어트, 종전 `.claude/rules/simulator/coach-tour.md`)**
- 앵커는 `constants/simulatorTour.ts`의 `rail-product`·`rail-wall`·`rail-view`이고 플라이아웃 내용물이 아니다 — 타협이 아니라 결정이다. 패널(`hud-library`·`hud-wall`·`hud-camera`)은 레일 클릭 전에는 DOM에 없고 그 상태는 `EditorSidebar` 로컬이다.
- **플라이아웃 자동 열기는 기각**: ①투어가 끝나도 열린 채 남아 저장·복원이 필요하다 ②"이 버튼을 누르세요"가 아무 데나 클릭해 진행하는 규칙과 모순된다 ③딤 처리된 패널은 어차피 조작이 안 된다.
- 바꾸려면 `flyout`을 스토어로 올려야 한다(별건) — 그때 `src/components/simulator/CLAUDE.md`의 레일 항목도 같이 고친다.
- 옛 플로팅 `SelectionToolbar`는 프레임마다 transform이 바뀌어 앵커로 금지됐다 — 그 툴바가 복구된 뒤에도 **추적 오버레이는 앵커로 쓰지 않는다**는 규칙은 유효하다.

**검증·캡처 함정 (2026-08-14 이주 — 2026-08-10 DERO-546 스테이징분)**
- **real 모드에서 `__sim.placeProductAt`으로 GLB 제품을 배치하면 조용히 파라메트릭 박스가 놓인다 — rig/경계 검증은 이 훅으로 하면 안 된다** (2026-08-06 DERO-467). `placeAt`의 `assets?.instantiate(spec)`는 템플릿 미로드 시 null이고 훅 경로는 `ensureTemplate`을 타지 않아, 배치는 성공(collided/boundary 정상값)하지만 `joints: []`·지지 세그먼트 없음 — "rig 미배선"으로 오진하게 만든다(실제로 그렇게 오진함). 관절·클램프 검증은 실제 드래그 경로(합성 pointerdown→move→up, `dropSpec`→`ensureTemplate`)로 배치한 뒤 `placedItems()`의 `joints`가 채워졌는지 먼저 확인하라.
- **GLB 안의 `mesh_N` 이름은 메쉬가 아닐 수 있다 — rigManifest 세그먼트명은 raw GLB 노드명이 아니라 three가 로드한 씬의 `Mesh.name` 기준이다** (2026-08-06 DERO-467). CA-2 GLB는 이름 붙은 `mesh_0`~`mesh_9`가 전부 빈 그룹 노드고 실제 메쉬 노드는 무명 — GLTFLoader가 무명 메쉬에 `mesh_<index>`를 주려다 그룹명과 충돌해 dedupe 접미사 `mesh_N_1`을 부여한다. manifest(`mesh_1_1` 등)를 raw GLB 노드명과 비교하면 "불일치"로 오진하니, 검증은 반드시 GLTFLoader로 로드한 뒤 `traverse`의 `isMesh` 이름으로 하라(진단 스크립트 `qa-artifacts/ca2-glb-names.mjs`).
- **편집 전용 표시를 새로 만들면 `captureFullCanvas`(`store/simulatorStore.ts`)에서도 숨겨야 한다** (2026-08-04). 미리보기 PNG는 별도 씬이 아니라 **라이브 씬을 16:9로 다시 렌더**해서 뽑으므로, 선택 아웃라인(`postfx.setOutline`)·회전 링·관절 기즈모·**상판 경계 가이드선(`scene/boundaryGuide.ts`, 2026-08-04 추가)**이 그대로 찍혀 /craft 썸네일과 AI 상상도 입력에 편집 UI가 남았다. 캡처 함수는 `renderContactShadows`와 같은 visible 저장 → 끄기 → 복구 패턴으로 끄고, 원복은 `refreshOutline()` + 저장한 `group.visible`로 한다 — **스토어의 `selectedItemId`를 비워서 끄면 안 된다**(우측 선택 패널이 캡처 몇 프레임 동안 깜빡인다). 기즈모 복구에 `show()`를 다시 부르는 것도 불필요하다(핸들 재계산).
- **마감 장식을 "몇 면에 두를지"는 면 개수가 아니라 카메라에 들어오는 면으로 판단한다** (2026-08-04, 당시 `themes/oak-warm` — 지금은 `finishes/woodSlat.ts` + `presets.ts`의 면 배정). "찜질방 스킨"으로 읽힌 것을 고치려 슬랫을 3면에서 **2면(`['front','left']`)으로 줄였으나 화면 변화가 0이었다** — `hero` 프리셋이 보는 벽이 정확히 그 두 면이고 `right`는 프레임 밖이라 페인트 벽이 한 픽셀도 안 나온다. 액센트가 실제로 성립하는 최대치는 **전면 1면**이다. 스크린샷 전에는 "3면→2면이니 3분의 1 줄었다"가 그럴싸하게 들리므로, 면 집합을 바꾸는 변경은 `scripts/measure-room-themes.mjs`로 같은 카메라 스크린샷을 찍어 확인한다. 같은 이유로 **벽 바탕색을 밝게 올려도 슬랫이 그 면을 덮고 있으면 화면에 안 나온다.** 당시엔 배킹을 벽 재질에서 떼어 얕은 판으로 분리해 벽 페인트와 홈 배킹을 동시에 성립시켰지만, **2026-08-08(DERO-507) 계열이 면 단위가 된 뒤로는 그 면 전체가 슬랫 벽이라 벽 재질 자체가 배킹이다** — 얕은 판이 사라졌고 drawcall도 하나 줄었다. 한 면에 페인트와 슬랫을 섞고 싶어지면 그때 다시 판을 떼야 한다.

## 방 표면 — 벽면별 마감·시간대·창문 (REQ-ENV-08·09·10, ADR-0030·0031, D31 — 2026-08-09 구현 완료)

축은 셋이다: **면마다 마감**(계열 + 변형) · **시간대**(DAY/NIGHT) · **면마다 창문**(mm 4값). 옛 테마
1축(`theme_key`)은 코드에서 지웠다(컬럼 DROP은 V10) — 계열 5종 × 3면을 키 하나로 담으면 키가 125개가 된다.
**방 프리셋은 남지만 저장하지 않는다** — 클릭하면 벽면 값에 써넣는 프리필이라 정본이 하나다.

방 표면(벽 3면 + ground)의 룩은 **리포에 커밋된 TS 코드 모듈**이다. 텍스처 파일·GLB·DB 마스터가 없고 절차 지오메트리 + TSL로 계산한다.

- 배치: `frontend/src/three/finishes/{types,index,parts,nodes,presets}.ts` + 계열 파일 하나씩. `index.ts`가 **정적 import 맵**(`Record<WallMaterialFamily, WallFinishModule>`) — 새 계열 = 파일 하나 + 한 줄. 동적 `import()`·런타임 원격 코드 로드·`eval` 금지.
- 계약: `material(variant, ctx) -> NodeMaterial` (필수) / `decor(variant, side, ctx) -> Group | null` / `decorDepthM(variant) -> number`. 씬은 표면 하나씩 `buildWallSurface(finish, side, ctx)`·`buildFloorMaterial(finish, ctx)`로 받아 끼운다(`buildRoomSurfaces`는 네 표면을 한꺼번에 세우는 합성이고 부팅·테스트용이다).
- **프리셋(`presets.ts`)은 런타임에 three를 안 끌고 온다** — 순수 데이터라 시뮬레이터 밖 저장·복원 경로(`api/placement.ts`)가 3D 번들을 떠안지 않는다.
- **TSL은 `nodes.ts`에 `@ts-nocheck`로 격리한다.** 일반 파일에 노드 체이닝을 쓰면 tsc 인퍼런스가 ~70GB OOM으로 머신을 죽인다(2026-07-17 전례, `render/woodGrainNode.ts` 참조). export 시그니처만 명시 타입.

**권한 경계** — 벽은 배경이 아니라 기능 부품이다(`scene.pickWall`이 벽 메쉬를 raycast하고, 벽 좌표가 충돌 클램프 평면이며, 전면 벽 z는 책상 깊이를 추종한다).

| 허용 | 금지 |
|---|---|
| 벽·ground 재질 교체 | **광원 추가** — 창구는 `scene/lightSlots.ts` 하나이고 `EMITTER_LIGHT_CAP`이 걸려 있다. 마감이 만들면 사용자 램프 슬롯을 잡아먹는다 |
| 연속 부조 절차 지오메트리 — 슬랫·타일·몰딩·걸레받이·천장·러그 | **벽·바닥의 위치·크기·`visible` 변경** (씬 단독 소유) |
| emissive 메쉬 + 재질 노드 안의 가짜 바운스 그라디언트 | **이산 벽 장식**(선반·액자·벽등) — 벽걸이는 y 0~2.6m 어디든 가므로 안전 밴드가 없다. 관통은 "사기 전 검증"을 깎는다 |
| | **자유 hex tint** — 우드 슬랫에 초록을 먹이면 나무가 초록이 된다 |

가드: 연속 부조의 **방 안쪽 돌출 ≤ 20mm**(`finishes/types.ts` 상수). decor 메쉬는 `raycast = () => {}`이고 충돌·호환 판정에 들어가지 않는다.

**계열 5 + 3종** — 벽 `PAINT`·`WOOD_SLAT`·`BRICK`·`MARBLE`·`CONCRETE`, 바닥 `WOOD`·`TILE`·`CARPET`. 전부 절차 셰이더다(텍스처 파일 0개). 나무결은 `render/woodGrainNode.ts`의 `woodGrainColor` 재사용, 슬랫 판재는 InstancedMesh 강제. 프리셋 4종(`neutral`·`oak-warm`·`white-clean`·`dark-studio`)은 이 값들의 조합이다.

**기본 마감이 `PAINT/NEUTRAL` + `WOOD/OAK`여야 한다** — `e2e/lighting.spec.ts`가 벽 R/B를 0.9~1.12로 강제하고(샘플 전에 `applyRoomPreset('neutral')`로 벽면을 고정한다), 그 가드가 제품 색 판단(`render/environment.ts:5-8`)을 지킨다.

**전환**: `applyRoom(config)`가 단일 창구 — 표면마다 이전 decor 제거·dispose → 재질 교체 후 이전 재질 dispose → 새 decor 추가. **캐시하지 않는다**(셰이더 여러 벌 상주 방지). **마감이 바뀐 표면만 다시 짓는다**(면 단위 diff, 창문 `syncWindows`와 같은 모양) — 시간대만 바뀐 전환이나 바닥 변형 클릭에서 벽 계열 셰이더를 다시 컴파일하면 토글·클릭마다 스톨이다. 벽 아이템 재스냅도 `decorDepthM`이 실제로 바뀐 면에서만 돈다.

**시간대와 태양** — 광원 집합을 두 축으로 갈랐다: `roomRig` key(=태양)는 **시간대만**, fill/rim/hemi는 **방 조명만** 쥔다(ambient floor는 상시). 태양 방향은 `roomRig.setSunWindow(side|null)`이고 **창문 없는 방은 주간에도 세기 0**이다(그래서 기본 방 `shadowCasters`가 2다). 벽 메쉬 `castShadow=true`가 햇살을 구멍으로만 들인다. **광원 개수·`castShadow` 집합을 런타임에 바꾸면 실기 WebGPU가 1.2~1.9초 멈춘다** — 끄는 방법은 `intensity = 0`이고 `visible`은 절대 만지지 않는다.

**창문** — 순수 규칙 정본은 `core/window.ts`(슬롯→mm·사각형·`Shape`+`holes` 지오메트리·주 창문·퇴거). 개구부는 마감이 아니라 **씬**이 벽 지오메트리에 뚫는다: 진짜 구멍이라 raycast가 통과해 **회피가 공짜다**(판정 코드로 짜지 말 것). 모든 벽 포즈는 `wallPoseAt`에서 창문 밖으로 밀린다 — 히트-없는 기본 부착 경로 때문이다.

**창밖과 블라인드**(ADR-0031) — 창밖은 창 사각형 크기의 **포털**(셋백 2mm)이고 원근은 셰이더가 만든다(픽셀별 시선 탄젠트 + 가상 깊이 두 층, `render/windowNodes.ts`). 색은 두 슬롯에 갈라 낸다 — 하늘·켜진 창만 `emissiveNode`로 나가 램프와 같은 블룸을 타고 지면·건물은 `colorNode`다(근거는 아래 "근거·실측" ②). 해 원반은 없고 넓은 글로우가 방향을 말한다. 창 드레싱(포털 + `scene/blind.ts` 백색 베네시안 + `scene/windowTrim.ts` 창틀·창턱)은 **벽 메쉬의 자식 그룹 하나**라(`syncWindowDressing`, 창문 diff 안에서만 짓고 버린다) 벽 이동·표시가 공짜로 따라온다. 애니메이션 유니폼은 둘뿐 — `windowTime`(씬 `tick`)과 `nightMix`(`applyRoom`). 창밖 색에는 노출 보정 배율이 곱해져 있다 — **값 정본은 `render/windowNodes.ts`의 `DAY_SCALE`·`NIGHT_SCALE`**이고 씬 배경의 20과 다르다(20은 하늘이 ACES 어깨에 얹혀 파랑이 날아간다).

**저장** — `placement_wall` 3행(`is_on`·`material`·`variant`·`has_window` + 창문 mm 4값) + `placement.floor_material`·`floor_variant`·`time_of_day`. 마스터 테이블도 enum도 없고 WAS는 형식(`^[A-Z][A-Z0-9_]{0,29}$`)만 본다 — **미상 값은 에러 없이 그 계열 기본 변형으로 폴백**한다(계열 코드를 지웠다고 옛 배치가 안 열리면 안 된다). 저장 형식 ↔ `RoomConfig` 변환은 `utils/roomFinish.ts` 한 곳이다.

폐지: `setWallColor`·`setFloorColor`와 사이드바 색 프리셋·피커, `applyTheme(key)`·`themeKey`(DERO-514). 되살리지 말 것.

### 근거·실측 (2026-08-14 이주 — 2026-08-10 DERO-546 스테이징분)

위 압축 정본의 근거다. 룩 수치의 정본은 코드(`render/windowNodes.ts`)이므로 여기에 사본을 두지 않는다.

- **창문 개구부 (2026-08-09 DERO-511, ADR-0030 결정 5·6·7).** 개구부는 `core/window.ts` `buildWallGeometry`의 Shape+holes이고 계약 시험이 `tests/wallWindow.test.ts`다. 지오메트리 교체는 셰이더 해시와 무관해 스톨이 없다(재질 diff `sameFinish`는 창문을 안 본다 — `syncWindows`가 따로 diff). ① **창문 없는 방은 주간에도 태양 세기 0**이다(주 창문 = 켜진 벽 중 전면>좌>우, `roomRig.setSunWindow`) — 그래서 기본(neutral) 방의 `lightingInfo().shadowCasters`는 **2**이고, 3을 기대하는 코드·e2e는 창문을 먼저 넣어야 한다. rig를 안 부르면 부팅 기본(창문 있음 취급)이라 관리자 발광 프리뷰는 종전 그대로다. ② 벽 메쉬 `castShadow = true`는 광원이 아니라 메쉬 플래그라 셰이더 재빌드와 무관하다 — 끄면 창문 없는 벽을 태양이 그대로 관통한다. ③ 히트 없는 기본 부착과 창문 이동 후 재스냅이 `wallPoseAt`의 `evictAlongFromWindow` 한 곳으로 커버되므로, **새 벽 배치 경로를 만들면 반드시 `wallPoseAt`을 태워라.** ④ 저장은 mm 4값(`windowCenterXMm`…)이고 UI 슬롯(가로 3 × 크기 2, 창턱 900 고정)의 정본은 `core/window.ts`다. 종전의 "WOOD_SLAT 슬랫이 창문을 통째로 덮는다"는 알려진 한계는 2026-08-10에 슬랫 쪽에서 잘라 해결됐다(아래 항목이 정본).
- **창밖 포털·개구부 마감·블라인드 (2026-08-09 DERO-520, ADR-0031 — 512·513의 커튼·여백 판을 대체).** 창문이 생기면 그 벽 메쉬에 **자식 그룹 하나**가 붙는다(`scene/windowView.ts` 포털 1장 + `scene/windowTrim.ts` 창틀·창턱·밸런스 + `scene/blind.ts` 헤드레일 + 슬랫 `InstancedMesh` + 바텀레일(위에서 0.45만 내려온다 — 물리 비율이 아니라 화면 기준이다), 씬 `syncWindowDressing`). **부모가 벽인 것이 배선의 전부다.** 아홉을 지켜라: ① **애니메이션 유니폼은 `windowTime`·`nightMix` 둘뿐이다** — 여기에 새 재질·광원·`visible` 토글을 끼우면 셰이더 재빌드가 돌아온다(블라인드는 정적이라 유니폼이 없다). ② **창밖 색은 두 슬롯에 갈라 낸다** — 하늘·켜진 창만 `emissiveNode`, 지면·건물은 `colorNode`다(`windowSceneryNodes`가 둘을 돌려준다). emissive MRT가 이 씬의 블룸 소스라(`postfx.ts`) `colorNode`로만 내면 램프는 번지는데 창문만 못 번지고(1차 반려 사유), **거꾸로 전부 emissive로 내면 문턱 0·강도 1.2 블룸이 그림 전체를 흐려서 더해 창밖이 파스텔로 뭉갠다**(2026-08-09 "입체감 없다" 반려). 두 몫의 합은 원래 색이라 밝기는 안 변하고 번짐만 골라 간다. **밝기 배율(`DAY_SCALE`)로 번지게 하려 들지 말 것**: 글레어 문턱 50을 하늘 바탕이 통째로 넘는다. ③ **눈금은 전부 "창으로 보이는 고도(탄젠트)"다.** 셰이더는 픽셀별 시선을 `ang = dir.xy / −dir.z`로 쓰고 층 하나는 `P.xy + ang·깊이`, 높이는 `−camLocal.y`(수평선 = 눈높이)다. 실측 가시 범위는 히어로에서 **tan −0.26..+0.10**(HUD 툴바가 창 윗변을 가린다) · 전면에서 −0.08..+0.30뿐이라, 층 높이(m)를 그 층 깊이로 나눈 값이 그 안에 없으면 화면에 0px거나 창을 통째로 덮는다 — 우듬지 4m(깊이 20m)로 잡았다가 창이 전부 초록이었다. 상수를 고치기 전에 그 나눗셈부터 하라. **창 자체도 윗부분이 잘린다** — 표준 창(창턱 900mm·높이 1400mm)이면 윗변에서 **약 520mm(37%)가 HUD 툴바 뒤**다(front 프리셋 1600×1000 실측: 폭 1800mm=850px, 유리 밑변 y=475, 윗변 y=−186, 툴바 밑단 y=60). 창 위쪽에 매다는 것(블라인드·밸런스·헤드레일)은 그만큼 화면에 안 나온다 — 블라인드를 1/3만 내렸더니 8컷 전부에서 한 픽셀도 안 보였다. ④ **내림차순 `smoothstep`을 쓰지 말 것** — WGSL은 `edge0 > edge1`이 미정의다. `smoothstep(0, −0.03, elev)`로 지면 마스크를 짰더니 에러 없이 1로 붙어 창밖 전체가 지면색이 됐다. 반드시 `1 − smoothstep(작은쪽, 큰쪽, x)` 꼴로. ⑤ **판은 창 사각형 크기 그대로 벽면에 끼운다**(셋백 2mm) — 여백·셋백을 주면 위·바깥 시점에서 "떠 있는 하늘 광고판"이 보인다(반려 사유). 원근은 지오메트리가 아니라 셰이더 패럴랙스가 만든다. ⑥ 드레싱 돌출은 전부 20mm 캡(`MAX_RELIEF_PROTRUSION_M`) 아래이고(트림·밸런스 18mm · 기운 슬랫 9.2mm · 헤드레일 12mm — 밸런스보다 얕아야 앞면이 공면이 안 된다) 그룹 전체가 `raycast` 무력화·GLB 미사용이다(창밖 소품과 사용자 배치 제품이 화면에서 구분돼야 한다). 블라인드는 `castShadow`를 안 켠다 — 햇살 바닥 웅덩이가 개구부 전체로 들어와야 하고 22mm 피치 줄무늬는 그림자맵에서 에일리어싱만 된다. ⑦ **입체감은 층 수·가림·또렷한 가장자리에서 나오고, 시점 높이가 창밖 룩을 지배한다** — 지면이 눈높이 바로 아래면 건물이 전부 수평선 위로 솟아 창을 벽처럼 막는다(회색 벽 한 장 = 반려). 고층으로 내려야 옥상이 수평선 아래에 깔려 스카이라인이 생기고 하늘이 위 절반을 갖는다. 가장자리 램프를 뭉개면 건물이 아니라 얼룩이 되고, 하늘 파랑은 `DAY_SCALE`을 올리면 ACES 어깨에서 흰 판이 된다. 층 높이는 도시 지면 기준으로 넘기고 `cityLayer`가 눈높이 기준으로 바꾼다. **층 수·높이·램프·`DAY_SCALE`의 수치 정본은 `render/windowNodes.ts`다** — 2026-08-09 `/prototype` 판정에서 박동규가 슬라이더로 확정한 값을 구웠다(커밋 `4456369f`, ADR-0031 결정 5 개정). 지면은 각도가 아니라 **높이 평면에 투영**해(d = GROUND_H/elev) 미터 좌표로 얼룩·수렴선을 찍는다 — 각도 좌표 얼룩은 거리와 무관해 납작하다. 수렴선 주기가 너무 길면 가까운 지면 한 칸이 창을 덮어 줄이 안 보인다. ⑧ **실루엣 층은 위아래 둘 다 끊는다** — 마스크에 밑동이 없으면 창 밑변까지 이어져 지면 층이 통째로 가려지고, 야간에는 켜진 창까지 땅 밑에 박힌다. ⑨ **부팅 첫 `applyRoom`에 `currentRoom`을 그대로 넘기면 창문이 안 뚫린다** — `syncWindows`가 자기 자신과 diff한다. 계약 시험은 `tests/windowDressing.test.ts`, 픽셀 스모크는 `e2e/room-finish.spec.ts`.
- **마감 부조는 창문 개구부를 덮으면 안 된다 — 마감이 창문을 "읽을" 수 있게 된 이유 (2026-08-10).** 우드 슬랫이 창문을 통째로 가렸다(실측 개구부 b−r **30.7 → −12.6**, 밝기합 **624.3 → 415.2**; 사용자 보고 "창문이 벽에 먹혀버림"). 원인은 `buildSlats`가 `bottomY: SKIRT_H(90mm) → topY: wallHeightM`를 벽 전폭에 까는데 `FinishContext`에 창문 필드가 없어 마감이 개구부를 **구조적으로 못 봤다**는 것. 다섯을 지켜라: ① **증상은 WOOD_SLAT 전용이었다** — PAINT·CONCRETE·BRICK·MARBLE은 같은 창에서 중립 벽과 소수점까지 같다(Δ 0.0). 걸레받이(하단 90mm)·몰딩(상단 70mm)은 창턱 900mm 창과 높이대가 안 겹치기 때문이지 안전해서가 아니다 — 자유 mm 저장이라 벽 꼭대기까지 오는 창은 몰딩과 20mm 겹칠 수 있다(미해결, 슬롯 UI에서는 안 걸린다). ② **`FinishContext.windowRectM`은 읽기 전용이고 마감이 할 수 있는 일은 "안 덮는 것" 하나다** — 구멍은 여전히 씬이 뚫는다(ADR-0030 결정 5 유지). ③ **높이를 인스턴스 스케일로 주지 말 것** — 나뭇결(`nodes.ts` `woodGrainColor`)이 `positionLocal`을 미터로 읽으므로 단위 박스를 늘리면 짧은 토막의 결이 눌린다. 그래서 토막 길이(통짜·아래·위)마다 `BoxGeometry`를 따로 세운다. drawcall은 창문 있는 면에서만 최대 3이고 판재 수(60+)와는 무관하다. ④ **세 메쉬 모두 열 수만큼 인스턴스를 갖고 자기 몫이 아닌 열은 스케일 0으로 접는다** — `slatColor`의 색 흔들림 시드가 `instanceIndex`라, 인스턴스 번호가 열 번호와 어긋나면 같은 열의 위·아래 토막 색이 갈리고 이웃 열과도 겹친다. ⑤ **창문만 바뀐 면도 마감을 다시 세워야 한다** — `sameFinish`는 창문을 안 보므로 `syncWindows`가 바뀐 면을 돌려주고 `applyRoom`이 그 면을 `applyWallSurface` 대상에 넣는다. 안 하면 창문을 나중에 단 슬랫 벽에서 증상이 그대로 재발한다. 회귀 가드는 `tests/slatWindow.test.ts`(단위) + `e2e/room-finish.spec.ts`의 `no wall finish may cover the window opening`(픽셀). **픽셀 판정은 "마감을 바꿔도 개구부가 안 변한다"여야 한다** — "개구부가 옆 벽보다 파란가"로 짜면 슬랫 틈으로 새는 하늘이 갈색 벽보다는 여전히 파래서 버그가 있는데도 통과한다(1차 판정식이 그래서 초록이었다).
- **`Matrix4.decompose`는 3×3이 전부 0인 행렬에도 스케일 `1,1,1`을 돌려준다** (three r185 실측, 2026-08-10). 스케일 0으로 접은 `InstancedMesh` 인스턴스를 "안 그려지는 자리"로 골라내려고 `decompose`를 쓰면 전부 그려지는 것으로 세어져 검증이 조용히 무의미해진다(`tests/slatWindow.test.ts` 1차 작성에서 62/62 통과). 접힘 판정은 행렬 열 길이를 직접 읽어라 — `e[0]²+e[1]²+e[2]² === 0`.

## e2e — 시뮬레이터 스펙 운영 기록 (2026-08-14 이주 — 2026-08-10 DERO-546 스테이징분)

감축 정본은 `frontend/e2e/CLAUDE.md`(코치마크 시드 · 스위트 열화)이고, 여기 두 블록은 거기서 내린 원문이다.

```markdown
- **Specs that visit `/simulator` MUST call `seedCoachTourSeen(page)` (`helpers/tour.ts`) in `beforeEach`** — Playwright starts with empty localStorage so every simulator spec is a "first visit", and the coachmark overlay (`.sim-coach-root`, `z-index:15`) covers the viewport and eats any click as "next step". Symptom is not "element not found" but clicks that appear to land and do nothing (`rail-*`, `lib-card-*`, `save-layout`). Helper uses `page.addInitScript` to write `dero-simulator-tour` = `{"state":{"seen":true},"version":1}` (zustand persist envelope), so it must run **before the first `goto`** — next to `stubAuthenticatedSession`. 14 specs seed it as of 2026-08-03 (articulation, collision-ignore, collision-overhaul, desk-config, glb-library, lift-tilt, lighting, magnet-mount, manipulate, placement, screen-photo, screens, smoke, wall-boundary). **`simulator-tour.spec.ts` deliberately does not** (it reproduces first visit). New simulator spec = seed is part of the set. Exceptions: `oauth.spec.ts` anonymous `/simulator` case bounces to `/login` (no HUD); `/simulator/thumbnail-render` renders no `SimHud`.
- **Back-to-back full suites degrade `boot()`** — same code goes 13s/test on run 1 to over 60s on run 3, killing **untouched** specs with "Test timeout of 60000ms exceeded" at `waitForTimeout(100)`. Tell-tale: all bare timeouts (no assertion failures) and the failing specs move between runs — suspect the environment, not the code. Killing playwright with SIGTERM (e.g. an outer timeout) orphans the webServer and browsers and starves the next run. Recovery: `pkill -f "playwright test"`, check `lsof -ti:3000`, wait, then run specs in smaller batches (2026-07-26 DERO-160, 3 reproductions, 3 false alarms).
```
